推理系统：同时服务几百万人

模型结构决定理论上的计算量，真正决定成本和速度的是系统。一个线上服务同时处理成千上万个请求，它们长短不一、随时到达和结束，共享同一批 GPU 的算力和显存。这一章先跟着一个请求走完全程，用一个 70B 模型和一台 8 卡服务器把每一站的时间算出来；再讲为什么批处理能摊薄权重却摊不薄 KV 缓存，显存怎样决定能同时服务多少人，连续批处理、分页和前缀缓存各修了什么，负载接近容量时延迟为什么急剧上升，投机解码怎样在不改变输出的前提下加速；然后是预填充与解码的分块和分离、2026 年的宽专家并行与超节点，最后算一算一百万个 token 的成本从哪来。

第 章说单用户解码只能用到算力的零头，第 章把模型压小以减少要读的字节。另一个、也是更重要的杠杆，是让一次权重读取同时服务很多用户。

  • KV 缓存、GQA / MLA：第 章；MoE 与专家并行：第 章
  • 自回归生成、多 token 预测：第 章；张量并行：第 章

从零开始：跟着一个请求走一遍

这一节用一个具体的例子，把一次请求从到达到返回的每一站走一遍，每一站都算出时间的量级。后面每一节都在优化其中某一站。设定如下：

项目设定由此得到
模型Llama 3 70B 级稠密模型：70.6B 参数，80 层，64 个 Q 头、8 个 KV 头（GQA），头维 128BF16 权重 \(W\) = 141 GB
硬件一台 8×H100 SXM 服务器，用张量并行把每个矩阵切到 8 张卡上显存 640 GB，合计带宽 26.8 TB/s，BF16 稠密算力 7.9 PFLOPS
请求提示 4000 token，其中 3000 是所有用户共用的系统提示和工具说明；输出 1000 token—

下面的数字都是理想化的 roofline 估算：按峰值带宽和算力算，忽略卡间通信和内核开销。真实系统会慢一些，但量级和瓶颈的位置不变。

第一站：到达与排队

请求经过网关、分词，进入调度器的等待队列。调度器每一步（几到几十毫秒）检查一次：显存够不够放它的 KV 缓存，批里有没有空位。这一站的时间与模型无关，只取决于此刻有多少别人在用：空闲时是零，高峰时可以是几十秒（「排队」一节）。

第二站：预填充

预填充（prefill）：把整个提示一次性送进模型，算出所有位置的 KV 缓存和第一个输出 token。计算量约为“每个 token \(2N\) FLOPs × 提示长度”：

\[ 2\times 70.6\times 10^{9}\times 4000\approx 5.6\times 10^{14}\ \text{FLOPs} \] 注意力本身在 4000 token 时只再多 4%；上下文到十几万时它会和这一项相当

按 50% 的算力利用率，需要 \(5.6\times 10^{14}/(7.9\times 10^{15}\times 0.5)\approx 0.15\) 秒。这期间权重只读了一遍（141 GB ÷ 26.8 TB/s = 5.3 毫秒），每个权重被 4000 个 token 共用：大矩阵乘大矩阵，计算受限。从请求到达到第一个 token 返回的时间叫首 token 延迟（time to first token，TTFT），等于排队 + 预填充 + 网络，这里约 0.15 秒。

第三站：留下 KV 缓存

预填充顺带算出了提示里每个 token 在每一层的 K 和 V，存起来就是 KV 缓存。按第 章的公式，每 token \(\kappa = 2\times 80\times 8\times 128\times 2\) 字节 = 320 KB。4000 token 是 1.31 GB；生成完 1000 个 token 后涨到 1.64 GB。这块显存从预填充开始一直占到请求结束，后面每生成一个 token 都要把它完整读一遍。

第四站：逐个生成

解码（decode）：之后每步只生成 1 个 token。每一步都要把全部权重（141 GB）和这个请求自己的 KV（约 1.5 GB）读一遍，计算却只有 \(2N = 1.4\times 10^{11}\) FLOPs：

\[ \begin{aligned} t_{\text{读}} &\approx \frac{141 + 1.5\ \text{GB}}{26.8\ \text{TB/s}}\approx 5.3\ \text{ms} \\ t_{\text{计算}} &\approx \frac{1.4\times 10^{11}}{7.9\times 10^{15}}\approx 0.02\ \text{ms} \end{aligned} \]

GPU 99.7% 的时间在等数据，访存受限。第一个 token 之后平均每个 token 的间隔叫每 token 间隔（time per output token，TPOT），即 \((T_{\text{结束}} - T_{\text{首}})/(n_{\text{输出}} - 1)\)，就是用户看到的“打字速度”。这里 TPOT = 5.3 毫秒，每秒 188 个 token，1000 个 token 要 5.3 秒。

第五站：和别人拼成一批

算力闲着 99.7%，可以让 64 个用户的解码步拼在一起：权重读一遍，64 个 token 共用。KV 却各是各的，64 份都要读：

\[ t_{\text{步}} \approx \frac{141 + 64\times 1.47\ \text{GB}}{26.8\ \text{TB/s}} = \frac{141 + 94\ \text{GB}}{26.8\ \text{TB/s}}\approx 8.8\ \text{ms} \]

计算时间约 1.2 毫秒，仍然访存受限。整台服务器每秒产出 \(64/8.8\ \text{ms}\approx 7300\) 个 token，是单用户的 39 倍；每个用户的速度从 188 降到 114 token/s。注意 KV 的 94 GB 已经是权重的三分之二：权重能被批摊薄，KV 不能。这一点下一节展开。

第六站：显存够几个人用

640 GB 显存，减去权重 141 GB，再给激活和运行时留约 50 GB，剩下约 449 GB 放 KV。每个请求到结束时占 1.64 GB，最多同时服务 \(449/1.64\approx 274\) 个。到这个规模，每一步要读 141 GB 权重加约 400 GB KV，约 20 毫秒；整台每秒约 1.35 万 token，每人 49 token/s。如果像早期系统那样给每个请求按最大上下文 128K 预留空间（每个 43 GB），就只能同时服务 10 个。

第七站：返回、计费与服务目标

在 64 人一批时，这个请求从到达到最后一个 token 约 \(0.15 + 1000\times 8.8\ \text{ms}\approx 9\) 秒。它占用了服务器多少时间？预填充独占整台服务器 0.15 秒；解码阶段 1000 步、每步 8.8 毫秒，但由 64 人分摊，合 0.14 秒。合计约 0.29 秒，所以这台服务器每秒最多处理约 3.5 个这样的请求。预填充占了一半。如果 3000 token 的公共前缀已经算过（「前缀缓存」一节），预填充降到约 0.04 秒，容量升到每秒约 5.7 个。按每卡每小时 2 美元（整台 16 美元），每个请求的成本约 0.13 美分。

服务方会给延迟定一个目标，例如“90% 的请求首 token 不超过 2 秒、每 token 不超过 50 毫秒”（阶跃星辰的 Step-3 就按 TPOT ≤ 50 毫秒设计），这叫服务等级目标（service level objective，SLO）。满足 SLO 的那部分吞吐叫有效吞吐（goodput），它比单纯的吞吐更能反映服务质量：系统的目标就是在满足 SLO 的前提下，每秒处理尽量多的 token。

批处理的算术：权重能摊薄，KV 不能

上面的例子里，批从 1 增到 64，吞吐涨了 39 倍；再从 64 增到 274，只多涨了不到 1 倍。先看理想情况：如果每一步只读权重，批多大才“用满”算力？

\[ t_{\text{步}}(B) \approx \max\Big(\underbrace{\frac{N\,\htmlClass{sym-b}{b}}{\text{BW}}}_{\text{读权重}},\ \underbrace{\frac{2N\,B}{P}}_{\text{计算}}\Big)\qquad\Longrightarrow\qquad B^\ast = \frac{P\,b}{2\,\text{BW}} \]
一步解码的时间取两者中较大的：读一遍权重的时间（与批大小无关），和 \(B\) 个 token 的计算时间（随 \(B\) 增长）。批小于 \(B^\ast\) 时，增大批几乎不增加每步时间，吞吐随 \(B\) 线性上升；超过 \(B^\ast\) 后转为计算受限，每步时间开始变长，用户感到变慢。
\(b\)
每个权重的字节数
H100 跑 FP8 权重（\(b = 1\)）：\(B^\ast = 1979\times 10^{12}\times 1/(2\times 3.35\times 10^{12})\approx 295\)。与模型大小无关。实际中 KV 缓存的读取（随批和上下文增长）、注意力计算和显存容量会让最优批更小，通常在几十到一两百之间。

这张卡漏掉了一项：每个请求还要读自己的 KV。把它加进去：

\[ \begin{aligned} t_{\text{步}}(B) &\approx \max\Big(\frac{\htmlClass{sym-W}{W} + B\,\htmlClass{sym-n}{\bar n}\,\htmlClass{sym-k}{\kappa}}{\htmlClass{sym-BW}{\text{BW}}},\ \frac{2NB}{P}\Big) \\ \text{吞吐} = \frac{B}{t_{\text{步}}} &\ \le\ \frac{\text{BW}}{\bar n\,\kappa} \end{aligned} \] 权重一步只读一次，KV 每个请求读一份；批再大，吞吐也越不过“带宽 ÷ 每个请求的 KV”
每一步要读的字节 = 权重 + 批里每个请求各自的 KV。批小时权重占大头，加人几乎不加时间；批大了 KV 占大头，每加一个人就多读一份 KV，步长随之线性变长，吞吐趋于一个上限。
\(W\)
权重的字节数（参数量 × 每权重字节数）
\(\bar n\)
批里请求的平均上下文长度（提示 + 已生成）
\(\kappa\)
每 token 的 KV 字节数，\(2Lh_{kv}d_hb\)
\(\text{BW}\)
显存带宽（多卡时取合计）
上节的例子，\(\bar n = 4500\)：读权重 5.3 ms，每多一个请求多读 1.47 GB，即 0.055 ms。\(B = 64\)：8.8 ms；\(B = 274\)：20.3 ms。吞吐上限 \(26.8\ \text{TB/s}/1.47\ \text{GB}\approx 1.8\) 万 token/s：批无限大也越不过它。上下文涨到 32K，上限降到约 2500 token/s。
第 1 步：只读权重。单用户解码，时间几乎全花在读权重上。
第 2 步：加上每个请求的 KV。权重被 \(B\) 个请求共用，KV 不共用。
第 3 步：和计算时间取较大者。读数据和计算可以重叠，慢的那个决定步长。

MoE 模型还多一层：批越大，被用到的专家越多，“权重”这一项本身也随批增长（第 章）。

预填充与解码的算术强度：分成权重和注意力两部分

第 1 步，权重部分。一次前向要把 \(N\) 个参数（\(Nb\) 字节）读一遍，参与这次前向的每个 token 对每个参数做一次乘加（2 FLOPs）。一次前向里有 \(m\) 个 token 时，算术强度是

\[ I_{\text{权重}} = \frac{2Nm}{Nb} = \frac{2m}{b} \]

预填充 \(m = n\)（提示长度），解码 \(m = B\)（批大小）。令 \(I_{\text{权重}}\) 等于芯片的拐点 \(P/\text{BW}\)，就得到上面的 \(B^\ast\)。预填充 4000 token、BF16 时强度为 4000，远高于 H100 的 295：计算受限。

第 2 步，注意力部分（解码）。新 token 要和自己的 \(n\) 个历史 token 做注意力。每层每个 Q 头：打分 \(nd_h\) 次乘加，加权求和再 \(nd_h\) 次，所有头合计 \(4h_qd_hn\) FLOPs；要读的是这个请求自己的 KV，\(2h_{kv}d_hnb\) 字节：

\[ I_{\text{注意力}} = \frac{4h_qd_hn}{2h_{kv}d_hn\,b} = \frac{2}{b}\cdot\frac{h_q}{h_{kv}} \]

它与 \(B\) 和 \(n\) 都无关。原因是 KV 是每个请求私有的：批里有 64 个请求，就要读 64 份不同的 KV，没有任何共享。GQA-8、BF16 时 \(I_{\text{注意力}} = 8\)，不到拐点的 3%。

第 3 步，合起来。一个解码步的总强度：

\[ I_{\text{解码}} = \frac{2NB + 4Lh_qd_h\,\bar nB}{Nb + B\,\bar n\,\kappa} \]

\(B\) 小时分母由权重主导，强度约 \(2B/b\)，随批增长；\(B\) 大到 \(B\bar n\kappa\gg Nb\) 时，强度趋于 \(I_{\text{注意力}}\)，再也涨不上去。

第 4 步，预填充的注意力为什么不受限。预填充时同一个请求的 \(n\) 个 query 共用同一份 KV，FlashAttention 把它分块留在片上反复使用（第 章），强度随 \(n\) 增长，所以预填充始终是计算受限的。

这个推导告诉我们：批处理提高的只是权重部分的强度。上下文越长，解码越接近“每个请求各读各的 KV”，强度被钉在 \(2h_q/(h_{kv}b)\) 上。要再往上推，只能改这个比值：加大 GQA 的分组、用 MLA 让所有头共用一个潜向量、把 KV 存成 FP8。这是长上下文服务贵的根本原因。

显存账：能同时服务多少人

上一节说批越大越好，但批不能无限大：每个请求的 KV 都要在显存里待到它结束。能同时服务的请求数由显存决定：

\[ \htmlClass{sym-Bm}{B_{\max}} = \Big\lfloor \frac{\htmlClass{sym-M}{M_{\text{显存}}} - W - \htmlClass{sym-Mr}{M_{\text{运行时}}}}{\htmlClass{sym-n}{n}\,\kappa} \Big\rfloor \] 装满时每一步都要把几乎整块显存读一遍：步长 ≈ 显存容量 ÷ 带宽，H100 上约 24 毫秒
显存减去权重和运行时的开销，剩下的全给 KV；每个请求占“上下文长度 × 每 token 的 KV”，相除就是最多同时服务几个请求。
\(B_{\max}\)
显存允许的最大并发请求数
\(M_{\text{显存}}\)
所有卡的显存合计
\(M_{\text{运行时}}\)
激活、通信缓冲区等，这里按 50 GB 估
\(n\)
每个请求要占的上下文长度（提示 + 输出）
上节的例子：\((640 - 141 - 50)/1.64\approx 274\)。KV 改存 FP8：548。换成每层 576 维的 MLA：约 970。上下文 32K：只剩 42。显存装满时，步长 ≈ \((141 + 449)\ \text{GB}/26.8\ \text{TB/s}\approx 22\ \text{ms}\)，与注意力类型几乎无关；一张 H100 读完自己的 80 GB 也是 24 毫秒。

由此得到一个简单的结论：在访存受限的范围内，满载吞吐 ≈ \(B_{\max}\) ÷ 读一遍显存的时间，每个请求的 KV 越小，同一台机器就越便宜。下面的演示把三件事放在一起：显存怎么分，墙在哪里，墙之前吞吐怎样随批增长。

KV 的压缩比，以及它为什么同时改变容量、吞吐与强度

每 token 的 KV 是 \(\kappa = 2Lh_{kv}d_hb\)（第 章）。GQA 和 MLA 相对普通多头注意力（MHA，\(h_{kv} = h_q = h\)）的压缩比：

\[ \frac{\kappa_{\text{MHA}}}{\kappa_{\text{GQA}}} = \frac{h}{h_{kv}},\qquad \frac{\kappa_{\text{MHA}}}{\kappa_{\text{MLA}}} = \frac{2hd_h}{d_c + d_r} \]

\(d_c\) 是 MLA 的潜向量维度（512），\(d_r\) 是单独做 RoPE 的维度（64）。70B 级模型（\(h = 64\)，\(d_h = 128\)）：MHA 每 token 2.6 MB；GQA-8 是它的 1/8（328 KB）；MLA 是 \(576/(2\times 64\times 128)\approx 1/28\)（92 KB）。DeepSeek-V3 有 128 个头，压缩比是 57 倍。FP8 再减半。

容量与吞吐。代入上面两张卡：显存墙 \(B_{\max}\propto 1/\kappa\)；满载时步长约等于读一遍显存，与 \(\kappa\) 无关，所以满载吞吐 \(B_{\max}/t\) 也 \(\propto 1/\kappa\)；批无限大时的上限 \(\text{BW}/(n\kappa)\) 同样 \(\propto 1/\kappa\)。三个量一起按压缩比放大，每个用户的速度却不变。

强度。MLA 还改变了上一节的 \(I_{\text{注意力}}\)。矩阵吸收之后，每个头的 query 直接和 576 维的潜向量做点积（576 次乘加），再对其中 512 维加权求和（512 次）。每读一个历史 token 的潜向量（\(576b\) 字节），所有头一共做 \(2h(576 + 512)\) FLOPs：

\[ I_{\text{MLA}} = \frac{2h\,(d_c + d_r + d_c)}{(d_c + d_r)\,b}\approx \frac{3.8\,h}{b} \]

\(h = 128\)、BF16 时约 242，接近 H100 的拐点 295；KV 存 FP8 则超过拐点。GQA-8 只有 8。DeepSeek 开源的 FlashMLA 内核（2025-02）在 H800 上报告了 580 TFLOPS 的计算受限配置，与这个推导一致：MLA 的解码注意力已经不是在“搬数据”，而是在“算”。

这个推导告诉我们：KV 每小一倍，能同时服务的人数、满载吞吐和吞吐上限都翻一倍。这就是为什么推理成本低的模型几乎都在注意力结构上下了功夫（MLA、大分组 GQA、滑动窗口、线性注意力混合），而不只是在权重上做量化。

连续批处理与分页 KV 缓存

前两节假设批里的请求整齐划一。实际请求的输出长度差异很大，短的几个 token，长的几万 token。静态批处理（FasterTransformer 时代的做法）把一批请求一起送进去，要等最长的那个结束才能换下一批，其余槽位只能空转，新来的请求也只能等。连续批处理（Orca, 2022）把调度粒度从“请求”改成“迭代”：每个解码步都检查一次，有请求结束就立刻从队列补上新的请求。Orca 在 GPT-3 175B 上报告，同等延迟下吞吐是 FasterTransformer 的 36.9 倍。

连续批处理让批可以变大，接下来卡住的是显存。旧做法按最大长度给每个请求预留一整块连续显存，实际只用了一小部分，预留了却没存 token 的部分就是显存碎片。PagedAttention（vLLM, 2023）借鉴操作系统的分页：把 KV 缓存切成固定大小的块（比如每块 16 个 token），按需分配，用块表记录每个请求的块在哪里。vLLM 团队统计，此前的系统因碎片和过度预留浪费 60–80% 的 KV 显存，分页后浪费降到 4% 以下；论文报告同等延迟下吞吐是 FasterTransformer 和 Orca 的 2–4 倍。

\[ \text{浪费率}_{\text{预留}} = 1 - \frac{\htmlClass{sym-El}{\mathbb E[\ell]}}{\htmlClass{sym-Lm}{L_{\max}}},\qquad \text{浪费率}_{\text{分页}} \approx \frac{\htmlClass{sym-S}{S}/2}{\mathbb E[\ell]} \]
按最大长度预留时，浪费由“最坏情况有多长”决定；分页时，每个请求最多浪费最后一块没填满的部分，平均半块。
\(\mathbb E[\ell]\)
请求实际用到的平均长度
\(L_{\max}\)
预留的最大长度
\(S\)
分页的块大小（token 数）
平均 5000 token、按 128K 预留：浪费 \(1 - 5000/131072\approx 96\%\)，例子里只能放 10 个请求。分页、\(S = 16\)：平均浪费 8 个 token，即 0.16%，能放 274 个。
两种碎片，以及分页的期望浪费

按最大长度预留。每个请求预留 \(L_{\max}\) 个 token 的连续空间，实际只用 \(\ell\)。期望利用率是 \(\mathbb E[\ell]/L_{\max}\)：输出长度事先不知道，\(L_{\max}\) 只能按最坏情况取，\(\mathbb E[\ell]\) 却由大量短请求决定。这是内部碎片。预留的块大小不一，请求结束后释放出的空洞未必放得下下一个请求，这是外部碎片。vLLM 论文测得，当时的系统里只有 20.4%–38.2% 的 KV 显存真正存了 token。

分页。块大小 \(S\) 个 token，按需分配，只有每个请求的最后一块可能没填满。若 \(\ell\bmod S\) 近似均匀分布，最后一块平均空 \((S-1)/2\) 个位置，期望浪费率约 \((S-1)/(2\,\mathbb E[\ell])\)。所有块大小相同，任何空闲块都能分给任何请求，外部碎片为零。

副产品：共享。块表让“两个请求指向同一块物理显存”变得很自然：同一个提示采样多个回答时，提示部分的块只存一份，写入时才复制。vLLM 报告这让并行采样和束搜索的显存减少最多 55%。

代价。KV 在显存里不再连续，注意力内核要按块表间接寻址。块越小浪费越少，但寻址和调度的开销越大，所以块大小常取 16–64（FlashMLA 用 64）。

这个推导告诉我们：分页把浪费从“由最坏情况决定”变成了“每个请求最多半块”，与请求长度的分布无关。省下的显存直接变成更大的 \(B_{\max}\)，而上一节推导过，满载吞吐与 \(B_{\max}\) 成正比。

块表还带来一个更大的副产品：既然块可以共享，不同请求里内容相同的前缀也可以共用同一批块。这就是前缀缓存（prefix caching）：多个请求共享的前缀只计算一次 KV，之后直接复用。

前缀缓存：算过的不再算

系统提示、多轮对话的历史、智能体的工具说明、同一份长文档上的多个问题，都是许多请求共享的前缀。SGLang 的 RadixAttention（2023-12）用一棵基数树（radix tree）索引所有缓存过的 token 序列：新请求进来，沿树找到最长的已缓存前缀，只对剩下的部分做预填充；显存不够时按最近最少使用的顺序淘汰叶子。论文报告在智能体、多轮对话、少样本等任务上吞吐最多提高 6.4 倍；在 Chatbot Arena 的实际部署中，一个月的缓存命中率在 52%–74%。

\[ \text{输入成本} \propto (1 - \htmlClass{sym-h}{h}) + \htmlClass{sym-h}{h}\cdot\htmlClass{sym-r}{r} \]
命中率为 \(h\) 时，只有 \(1-h\) 的输入 token 要重新做预填充；命中的部分只需从缓存里读出来，成本是正常的 \(r\) 倍。
\(h\)
前缀缓存命中率：输入 token 中命中缓存的比例
\(r\)
命中部分相对正常输入的价格（或计算量）比例，各家 API 通常约为 0.1
\(h = 0.9\)、\(r = 0.1\)：输入成本降到原来的 \(0.1 + 0.09 = 19\%\)。DeepSeek 2025-02 公布的一天里，6080 亿输入 token 中 56.3% 命中缓存，输入成本约为不缓存时的一半。上文的例子：3000/4000 命中，预填充从 0.15 秒降到 0.04 秒，服务器容量从每秒 3.5 个请求升到 5.7 个。

各家 API 对缓存命中的输入 token 收费通常只有正常价格的十分之一，原因就在这里；这也是智能体 harness 极力保持前缀不变的原因（第 章）：在前缀中间插一个时间戳，后面所有 token 的缓存都会失效。命中率还取决于调度：模型部署在几十台机器上时，请求要发到缓存了它的前缀的那台，这叫 KV 感知路由（KV-aware routing），NVIDIA Dynamo（2025-03）和 llm-d（2025）都把它作为核心功能。缓存放不下时，还可以退到 CPU 内存和 SSD（下文的 Mooncake）。

排队：为什么不能把 GPU 跑满

到这里算的都是“一台服务器每秒最多处理多少”。可请求不是按节拍到达的：某一秒来了 6 个，下一秒 1 个也没有。上文的服务器每秒最多处理约 3.5 个请求，那么每秒来 3 个时，延迟会怎样？回答这个问题需要两个最基本的排队论结论。

第一个是利特尔定律（Little's law, 1961）：

\[ \htmlClass{sym-Nb}{\bar N} = \htmlClass{sym-lam}{\lambda}\,\htmlClass{sym-T}{\bar T} \] 对任何稳定的系统都成立，与到达和服务时间的分布无关
系统里平均有多少个请求，等于每秒来几个乘以每个平均待多久。
\(\bar N\)
系统里（排队 + 正在处理）的平均请求数
\(\lambda\)
到达率：每秒到达的请求数
\(\bar T\)
每个请求在系统里的平均停留时间
每秒来 3 个请求，每个请求解码 1000 个 token、每 token 约 9 毫秒，在系统里待约 9 秒：平均有 \(3\times 9 = 27\) 个请求在同时解码。下面的演示在 \(\lambda = 3\) 时显示约 26 个。反过来，知道并发数和到达率，就能算出平均延迟。

第二个回答“负载接近容量时会怎样”。最简单的模型是 M/M/1 队列：请求随机到达（泊松过程），服务时间随机（指数分布），一个服务台。到达率与最大服务率之比叫负载率 \(\rho\)：

\[ \htmlClass{sym-rho}{\rho} = \frac{\lambda}{\htmlClass{sym-mu}{\mu}},\qquad \bar T = \frac{1}{\mu - \lambda} = \frac{\htmlClass{sym-S}{S}}{1 - \rho} \] ρ = 0.5 时延迟是服务时间的 2 倍，ρ = 0.9 时 10 倍，ρ = 0.99 时 100 倍
平均停留时间等于服务一个请求本身需要的时间，除以“还剩多少余量”。余量趋于 0 时，延迟趋于无穷。
\(\rho\)
负载率：平均每秒来的工作量占服务能力的比例
\(\mu\)
最大服务率：服务台满负荷时每秒能处理的请求数
\(S = 1/\mu\)
服务一个请求的平均时间
上文的服务器 \(S\approx 0.29\) 秒（\(\mu\approx 3.5\)/秒）。\(\lambda = 1.75\)（\(\rho = 0.5\)）：0.57 秒；\(\lambda = 3.15\)（\(\rho = 0.9\)）：2.9 秒；\(\lambda = 3.4\)（\(\rho = 0.97\)）：9.7 秒。负载只多了 8%，延迟涨了 3 倍多。

所以服务不能按“平均负载 = 容量”来配机器，否则任何一点波动都会让队列失控。把 SLO 写进吞吐的定义，就得到有效吞吐的精确版本：

\[ \text{有效吞吐}(\lambda) = \lambda\cdot\Pr\big[\,\text{TTFT}\le \htmlClass{sym-T1}{T_1}\ \text{且}\ \text{TPOT}\le \htmlClass{sym-T2}{T_2}\,\big] \] DistServe（2024）把“能保证 90% 请求达标的最大到达率”作为衡量一个部署的指标
每秒来的请求里，首 token 延迟和每 token 间隔都达标的那些，才算数。
\(T_1\)
首 token 延迟的上限，例如 2 秒
\(T_2\)
每 token 间隔的上限，例如 30 毫秒
每秒来 4 个请求，其中 51% 达标：有效吞吐 2.0 个/秒，比每秒来 3.5 个、99% 达标时的 3.47 个/秒还低。过了拐点，多接请求反而让达标的请求变少。

演示里有两种不同的“变慢”：批没满时，负载上升表现为每 token 间隔缓慢变长；批满了（触到批上限或显存墙），新请求开始排队，首 token 延迟在很窄的负载范围内从零点几秒涨到几十秒。线上服务因此按 SLO 而不是按峰值吞吐配机器，过载时宁可拒绝一部分请求，也不让所有人一起超时。

M/M/1 的平均停留时间，以及连续批处理为什么更像“处理器共享”

设定。请求按泊松过程到达（平均每秒 \(\lambda\) 个，彼此独立），服务时间服从均值 \(1/\mu\) 的指数分布，一个服务台，先到先服务。用“系统里有几个请求” \(k\) 描述状态，\(\pi_k\) 是稳态下处于状态 \(k\) 的概率。

第 1 步，平衡方程。稳态下，从 \(k\) 跳到 \(k+1\)（来了一个）的频率，等于从 \(k+1\) 跳回 \(k\)（走了一个）的频率：\(\lambda\pi_k = \mu\pi_{k+1}\)。所以 \(\pi_{k+1} = \rho\,\pi_k\)，\(\pi_k = \pi_0\rho^k\)。

第 2 步，归一化。\(\sum_k\pi_k = \pi_0/(1-\rho) = 1\)，这要求 \(\rho < 1\)。得 \(\pi_k = (1-\rho)\rho^k\)：系统里的请求数服从几何分布。\(\rho = 0.9\) 时，有 20 个以上请求积压的概率是 \(0.9^{20}\approx 12\%\)。

第 3 步，平均人数。\(\bar N = \sum_k k(1-\rho)\rho^k = \rho/(1-\rho)\)。

第 4 步，代入利特尔定律。\(\bar T = \bar N/\lambda = \dfrac{\rho}{\lambda(1-\rho)} = \dfrac{1}{\mu-\lambda} = \dfrac{S}{1-\rho}\)。

连续批处理不是先到先服务。批里的请求同时推进，服务能力在所有在场的请求之间平分，更接近“处理器共享”（processor sharing）。M/G/1 处理器共享队列有一个漂亮的结论：平均停留时间仍是 \(S/(1-\rho)\)，而且与服务时间的分布无关。区别在表现形式：先到先服务时，变长的是“等着开始”，对应首 token 延迟；处理器共享时，变长的是“每一步”，对应每 token 间隔。真实系统两者都有：批没满时像处理器共享，批满了就像先到先服务。批处理还让服务能力随批增大，\(\mu\) 不是常数，所以演示里的曲线比 \(1/(1-\rho)\) 平缓，但拐点依然存在。

这个推导告诉我们：\(1/(1-\rho)\) 的发散不是哪个系统的缺陷，而是随机到达本身的性质：到达有波动，服务台总有一阵子来不及处理，负载越接近 1，这些积压越难消化。要稳定满足 SLO，就必须留余量。

投机解码：小模型先猜，大模型一次验证

解码受带宽限制，算力闲着。投机解码（Leviathan 等, 2022；Chen 等, 2023）利用这些闲置算力：用一个便宜的“草稿”连续猜 \(\gamma\) 个 token，大模型一次前向并行验证这 \(\gamma\) 个位置（与预填充一样，多个位置一起算几乎不比一个位置慢）。从第一个被拒绝的位置截断，并在那里补一个 token：

\[ \mathbb E[\text{每轮产出的 token 数}] = \frac{1 - \htmlClass{sym-al}{\alpha}^{\gamma + 1}}{1 - \alpha},\qquad \text{加速比}\approx\frac{1 - \alpha^{\gamma+1}}{(1-\alpha)(1 + \gamma\,\htmlClass{sym-c}{c})} \]
每个草稿 token 以概率 \(\alpha\) 被接受，接受到第一个拒绝为止，再加上补的那一个。分母中的 \(\gamma c\) 是生成草稿的额外开销。
\(\alpha\)
草稿 token 的平均接受率
\(\gamma\)
每轮猜几个
\(c\)
生成一个草稿 token 的成本相对大模型一次前向的比例
\(\alpha = 0.8\)，\(\gamma = 4\)：每轮期望产出 \((1 - 0.8^5)/0.2 = 3.36\) 个 token。草稿成本 \(c = 0.05\)，加速比约 \(3.36/1.2 = 2.8\) 倍。
为什么输出分布和大模型单独生成完全一样

设大模型在某个位置的分布为 \(p\)，草稿的分布为 \(q\)，草稿抽到了 token \(x\)。验证规则：

  • 以概率 \(\min\big(1,\ p(x)/q(x)\big)\) 接受 \(x\)；
  • 若拒绝，从“残差分布” \(r(y)\propto\max\big(0,\ p(y) - q(y)\big)\) 中重新抽一个 token。

最终输出 \(y\) 的概率是“草稿抽到 \(y\) 并被接受”加上“某次被拒绝后从残差中抽到 \(y\)”：

\[ \begin{aligned} P(y) &= q(y)\min\Big(1, \frac{p(y)}{q(y)}\Big) + \Big(1 - \sum_x q(x)\min\Big(1,\frac{p(x)}{q(x)}\Big)\Big)\,r(y)\\ &= \min\big(q(y), p(y)\big) + \max\big(0,\ p(y) - q(y)\big) = p(y) \end{aligned} \]

（中间一步用到：拒绝的总概率 \(1 - \sum_x\min(q(x), p(x))\) 恰好等于 \(\sum_y\max(0, p(y) - q(y))\)，即残差分布的归一化常数。）

这个推导告诉我们：投机解码是一种精确的加速，不是近似：无论草稿多差，输出分布都与大模型一致，草稿的质量只影响接受率，也就是速度。平均接受率 \(\alpha = \sum_x\min(p(x), q(x))\)，草稿与大模型越像越高。

期望接受长度，以及批大了以后还划不划算

第 1 步，接受长度的分布。设每个草稿 token 被接受的概率都是 \(\alpha\)，彼此独立。一轮产出的 token 数 \(X\) = 被接受的草稿数 + 1（被拒绝处补的那一个，或全部接受后大模型顺带算出的下一个）。“至少产出 \(k\) 个”等于“前 \(k-1\) 个草稿都被接受”：\(\Pr[X\ge k] = \alpha^{k-1}\)，\(k = 1,\dots,\gamma+1\)。

第 2 步，期望。对取正整数值的随机变量，\(\mathbb E[X] = \sum_{k\ge 1}\Pr[X\ge k]\)：

\[ \mathbb E[X] = \sum_{k=0}^{\gamma}\alpha^k = \frac{1-\alpha^{\gamma+1}}{1-\alpha}\ \xrightarrow{\ \gamma\to\infty\ }\ \frac{1}{1-\alpha} \]

\(\alpha = 0.8\) 时最多 5 个。猜得再长也越不过这个上限，而草稿的成本 \(\gamma c\) 线性增长，所以存在一个最优的 \(\gamma\)：\(\alpha\) 越高、草稿越便宜，它越大（上面的演示里从 3 到 10 不等）。

第 3 步，批大了以后。一轮验证要算 \(B(\gamma+1)\) 个位置，但只读一遍权重。只要 \(B(\gamma+1)\) 仍低于拐点 \(B^\ast\)，多算的位置就几乎免费；超过之后，验证的计算量随 \(\gamma\) 增长，加速比下降。H100、BF16、\(\gamma = 4\)：\(B(\gamma+1)\le 295\) 要求 \(B\le 59\)。vLLM 等框架因此提供“批超过某个大小就关掉投机解码”的选项。

第 4 步，长上下文把账翻了过来。第 3 步只看了权重。一轮验证里，每个请求的 KV 也只读一遍，却换来 \(\mathbb E[X]\) 个 token：KV 的读取被摊薄了 \(\mathbb E[X]\) 倍。而「批处理的算术」一节推导过，长上下文时每步的时间主要花在读 KV 上，批处理摊不薄它，投机解码却可以。

这个推导告诉我们：投机解码的收益取决于“验证时多算的那些位置是不是免费”，也就是这一步离拐点还有多远。短上下文、大批量时它不划算；长上下文时读 KV 让解码重新回到带宽受限，它又划算了。

草稿从哪来：独立的小模型；Medusa、EAGLE 在大模型上挂几个轻量的预测头，利用大模型自己的隐藏状态，接受率高，EAGLE-3 是 2025–26 年 vLLM、SGLang 的主力；DeepSeek-V3/V4 训练时就带多 token 预测头（第 章），推理时直接当草稿；prompt lookup 直接从上下文里找重复片段，改代码、引用原文时特别有效。

意外：批越大，投机解码反而可能越划算

原以为
投机解码只适合小批量、低延迟的场景：批大了 GPU 接近计算受限，验证不再免费（上面推导的第 3 步）。
实际发现
MagicDec（2024-08，ICLR 2025）在 8 张 A100 上、批大小 32–256 的长上下文生成中，测到 LLaMA-2-7B-32K 最多 2 倍、LLaMA-3.1-8B 1.84 倍的加速，而且加速比随批增大而上升。
为什么
推导的第 4 步：上下文够长时，每步的时间主要花在读 KV 上，大批量也重新变成带宽受限，验证一次读一遍 KV、产出好几个 token。它的草稿只保留最近一段和开头几个 token 的 KV，草稿成本几乎不随上下文增长。论文给出一个临界长度：短于它，加速比随批增大而下降；长于它，反而上升。
现在怎么看
结论依赖设置。MagicDec 自己指出，GQA 模型的注意力强度更高，收益会小一些；LongSpec（2025-02）在自己的设置下复现，\(\gamma\ge 3\) 时 MagicDec 只有约 0.7 倍。“投机解码在大批量下没用”这句话，只在短上下文时成立。

预填充与解码：先分块，再分开

回到第七站的账：预填充占了服务器一半的时间，而且它和解码的脾气相反，一个吃算力，一个吃带宽，混在一起会互相干扰。最直接的是“卡顿”：一个 4000 token 的新请求做预填充要 0.15 秒，这期间批里正在解码的 64 个用户全部停下，每人卡了相当于 17 个 token 的时间。DistServe 团队 2025 年的回顾写道，单个长提示能把每 token 间隔放大 2 到 30 倍。

第一种办法是分块预填充（chunked prefill）：把长提示切成几百到几千 token 的块，每一步只做一块，和正在解码的请求拼在同一步里（Sarathi, 2023；Sarathi-Serve, 2024；DeepSpeed-FastGen 同期独立提出，叫 Dynamic SplitFuse）。它利用的是解码步留下的空闲算力，见下面的推导。Sarathi-Serve 报告，与 vLLM 相比，同样满足延迟要求时，Mistral-7B 在单张 A100 上的服务能力提高 2.6 倍，Falcon-180B 最多 5.6 倍。现在它是 vLLM 和 SGLang 的默认调度方式。

分块预填充能免费塞进多少 token

解码步带宽受限时，算力有空闲。批里有 \(B\) 个解码 token，再塞进 \(c\) 个预填充 token：读的字节不变（权重 + 已有的 KV），计算多了 \(2Nc\)。只要总计算时间不超过读数据的时间，这一步就不会变慢：

\[ \frac{2N(B + c)}{P}\le\frac{W + B\bar n\kappa}{\text{BW}}\quad\Longrightarrow\quad B + c\le B^\ast\Big(1 + \frac{B\bar n\kappa}{W}\Big) \]

（右边用了 \(W = Nb\) 和 \(B^\ast = Pb/(2\,\text{BW})\)。）上文的例子：\(B = 64\)，KV 94 GB、权重 141 GB，BF16 的 \(B^\ast = 295\)，右边 \(= 295\times 1.67\approx 492\)，每步可以免费带上约 420 个预填充 token（按峰值算力；实际效率打折后约一半）。一个 4000 token 的提示分成 10 到 20 块，在 10 到 20 个解码步（0.1 到 0.2 秒）里顺带算完，正在解码的用户几乎感觉不到。

每步的 token 总预算是调参的旋钮。预算大，吞吐高，但每 token 间隔的波动大；预算小，间隔稳定，但长提示要拆成更多块，每一块都要把前面各块的 KV 再读一遍。

这个推导告诉我们：分块预填充不只是“把预填充切碎”，它把预填充的计算填进解码留下的算力空隙里：最合适的块大小，正是把每一步推到拐点附近的那个大小。

分块缓解了卡顿，但两类负载仍在同一批 GPU 上、用同一种并行方式，只能按其中一类来优化。第二种办法是彻底分开：预填充与解码分离（P/D 分离；DistServe、Splitwise, 2024）。预填充和解码放在不同的 GPU 池，预填充池算完 KV，经高速网络传给解码池。两个池可以分别扩容、分别选并行方式，甚至用不同的硬件：Splitwise 指出解码不需要最新 GPU 的算力，可以用更便宜、更省电的卡。DistServe 报告，同样保证 90% 请求达标，能承受的请求率比 vLLM 高 2.0–4.6 倍（ShareGPT 负载）。

代价是传 KV。传输时间 \(t_{\text{传}} = n\kappa/\text{BW}_{\text{网}}\)，预填充时间 \(t_{\text{预}}\approx 2Nn/(Pu)\)，两者都与 \(n\) 成正比，所以只要比较每个 token：上文的例子里每 token 的 KV 是 320 KB，经一块 400 Gb/s（50 GB/s）的网卡约 6.6 微秒，而每 token 的预填充约 36 微秒。传输比计算快 5 倍，还可以逐层边算边传。MLA 模型的 KV 小几倍，传输更不成问题；KV 越大、网络越慢，分离越不划算。

预填充与解码分离总是更好吗

支持
两类负载特性相反，分开后各自可以用最合适的批大小和并行方式，互不打扰，长提示不再拖慢正在解码的用户。Mooncake、DistServe 报告了数倍的有效吞吐提升；vLLM 2026 年的博客报告，即使在单台 8 卡服务器内做 P/D 分离，有效吞吐也提升约 2.5 倍。
反对
分离要在节点之间传输 KV 缓存，长上下文时数据量很大，需要高速网络；预填充池和解码池的配比要随流量动态调整，否则一边闲置一边拥堵；小规模部署时，分块预填充加连续批处理往往已经足够，分离只会增加复杂度。
现在怎么看
大规模服务（尤其是长上下文、智能体流量）普遍采用分离；中小规模部署按流量特征选择。它是规模和负载的函数，而不是普遍更优。

分离之后，KV 缓存从“显存里的临时数据”变成了要传输、存储、调度的对象。Kimi 的 Mooncake（2024-07，FAST 2025 最佳论文）把这一点推到底：以 KV 缓存为中心设计整个系统，利用 GPU 集群里闲置的 CPU 内存和 SSD 组成分布式的 KV 池，调度器按“哪里有这个请求的前缀 KV”来分配预填充，用更多存储换更少计算。论文报告在真实负载下让 Kimi 多处理了 75% 的请求。

2026 年的大规模推理架构

  • 宽专家并行（wide EP）：DeepSeek 式的大型 MoE，解码时把专家分散到几十到上百张卡，每张卡只放少数专家，注意力部分用数据并行，token 经 DeepEP 这类通信库做全对全通信送到专家所在的卡（第 章：批大时所有专家都要常驻）。DeepSeek 2025-03 公布的部署：预填充用 4 个节点、专家并行 32 路，解码用 18 个节点、144 路，每卡只放 2 个路由专家。开源框架随后跟上：SGLang 在 96 张 H100 上做到每节点每秒 2.23 万输出 token（2025-05），vLLM 报告每张 H200 每秒约 2200 个解码 token（2025-12）。
  • KV 缓存分层存储：GPU 显存 → CPU 内存 → SSD 与分布式存储，前缀命中时直接取回而不重算，配合 KV 感知路由。Dynamo（2026-03 发布 1.0）、llm-d、LMCache 都在做这一层；NVIDIA 2026-01 还为 KV 缓存推出了专门的存储平台（CMX），用 BlueField-4 管理以太网连接的闪存。
  • 注意力与 FFN 分离（AFD；第 章讲它在芯片上的新用法）：P/D 分离按时间切开一个请求，AFD 按层切开一个模型：注意力层（每个用户私有的 KV）吃显存容量和带宽，放在一组卡上；FFN（专家）层的权重是共享的，放在另一组卡上，在 GPU 集群里通常受算力限制，在小批、低延迟的部署里则受读权重的带宽限制，微批次在两组之间交替流动。字节的 MegaScale-Infer（2025-04）和阶跃星辰的 Step-3（2025-07）先后采用，后者把模型结构和这种部署一起设计。
  • 超节点：GB200 NVL72（72 张 GPU 共享一个 NVLink 域）、华为 CloudMatrix 384 等，把张量并行和专家并行的通信域扩大到整个机柜。Kimi K3 官方建议的部署是不少于 64 张加速卡的超节点。
  • 按阶段专门化的硬件：NVIDIA 2025-09 发布专做长上下文预填充的 Rubin CPX（用 GDDR7 而不是 HBM），2026-03 又发布承担解码的 Groq 3 LPX 机柜；据报道，CPX 随后被移出了路线图。华为昇腾 950 也分成面向预填充和面向解码的两款（第 章）。
  • 低精度推理：Blackwell 原生 FP4；Hopper 上用 Marlin、Machete 一类的内核做 4 位权重的反量化（第 章）。

这些架构有一条共同的线索：把一个请求、一个模型按“吃什么资源”拆开，每一块放到最合适的硬件上，再用网络和调度把它们拼回去。代价是系统越来越复杂，最优配置强烈依赖模型结构和流量。

一百万个 token 的成本从哪来

API 按百万 token 收费，背后的成本可以粗略算出：

\[ \text{每百万 token 成本} = \frac{\htmlClass{sym-gpu}{\text{每 GPU 小时的成本}}}{\htmlClass{sym-tp}{\text{每 GPU 每秒的 token 数}}\times 3600}\times 10^6 \]
一张卡一小时的成本（折旧、电费、机房）除以它一小时能产出多少 token。吞吐越高，单价越低：这就是批处理、量化、投机解码最终体现的地方。
每 GPU 小时成本
2025–26 年 H100 级别的租用价格约 2 美元
吞吐
一张卡在满足延迟要求时每秒总共产出的 token 数（所有用户合计）
每 GPU 小时 2 美元，每张卡每秒产出 3000 个输出 token：\(2/(3000\times 3600)\times 10^6\approx 0.19\) 美元 / 百万 token。上文的 8 卡服务器（每小时 16 美元）：只服务 1 个人时约 24 美元 / 百万 token；64 人一批约 0.61 美元；装满 274 人约 0.33 美元（只算解码）。输入 token 便宜得多，因为预填充一次处理成千上万个 token，效率高；命中前缀缓存的输入几乎不需要计算，所以再便宜一个数量级。

DeepSeek 在 2025 年 3 月公开过其推理服务的一天：平均约 226 个节点（每节点 8 张 H800），日成本约 8.7 万美元；每个节点每秒约处理 7.4 万个输入 token（含缓存命中）或产出 1.5 万个输出 token；每个用户看到的输出速度只有每秒 20–22 个 token，说明他们把批开得很大、用速度换成本。若全部按 R1 的价格计费，理论日收入约 56 万美元，理论利润率 545%（实际收入低得多，因为有免费服务、夜间折扣和更便宜的 V3）。这说明在大规模、高并发、优化到位的条件下，推理可以有很高的毛利。

推理越来越便宜，AI 的总成本会下降吗

便宜派
同等能力的推理价格大约每年下降一个数量级（a16z 称之为“LLMflation”，Epoch AI 测得不同能力门槛下每年下降几倍到几百倍不等）：硬件更快、模型更小、量化和系统优化层层叠加。
反方
单价下降，用量涨得更快：推理模型每个问题要想几千上万 token，智能体一个任务要跑上百轮，每次都带着几十万 token 的上下文。用户总是用更强、更贵的前沿模型，而不是用便宜下来的旧模型。这是经典的杰文斯悖论：效率提高反而增加总消耗。
现在怎么看
两者同时成立：每个 token 的价格在快速下降，而 token 的消耗量在更快地增长，AI 的总算力支出仍在上升（第 章）。对使用者而言，前缀缓存命中率、思考预算和模型选择，比单价更影响账单。

常见误解

  • 投机解码会降低输出质量。标准的接受规则保证输出分布与大模型完全相同；草稿差只会变慢，不会变差。
  • 批处理只提高吞吐，不影响单个用户。批越大，每步要读的 KV 越多、越接近计算受限，每步时间变长，用户感到“打字”变慢；批满之后新请求还要排队。服务要在吞吐和延迟之间取舍。
  • 上下文长度只影响显存，不影响速度。每生成一个 token 都要把整段上下文的 KV 读一遍：上下文从 4K 涨到 32K，同样的机器能同时服务的人数和总吞吐都降到约八分之一。本地部署也一样，长对话越聊越慢（第 章）。
  • 输入和输出 token 的成本一样。预填充效率高得多，命中缓存的输入几乎免费，所以输入价格通常是输出的几分之一。
  • GPU 利用率 100% 就是满负荷。系统监控的“利用率”只表示有内核在跑，不表示算力被用满；解码时它可能显示 100%，实际只用到峰值算力的个位数百分比。反过来，按平均负载把服务跑到接近容量，延迟会失控（「排队」一节）。

演进史

2022-07

Orca：调度粒度从“请求”改成“迭代”

卡在哪
FasterTransformer 等系统已有融合内核、KV 缓存和张量并行，但按请求组批：短请求结束后陪着最长的那个空转，新请求要等整批结束。
怎么解决
每个解码步重新组批（连续批处理）；不同位置的请求在线性层拼批，注意力各算各的。
代价
每个请求仍按最大长度预留连续的 KV 显存，\(B_{\max}\) 被碎片压得很小。
引出
瓶颈从调度转到了显存管理。
被淘汰按请求的静态批处理
实现简单，适合所有请求一开始就到齐的离线批量推理。在线服务里请求随时到达、长度差异巨大，它的空转和排队太浪费，2023 年以后的主流框架都换成了迭代级调度。
2023-06

vLLM 的 PagedAttention：像操作系统一样管理 KV

卡在哪
60–80% 的 KV 显存被碎片和过度预留浪费，显存墙很低，而满载吞吐正比于 \(B_{\max}\)。
怎么解决
固定大小的块按需分配、块表映射，浪费率从 \(1-\mathbb E[\ell]/L_{\max}\) 降到每个请求最多半块；同一提示的多个采样共享块。
代价
注意力内核要按块表间接寻址；不同请求里相同的前缀仍在各自重算。
引出
块既然能共享，相同的前缀能不能也共享？
另一条路投机解码：不拼更多人，而是每步多出几个 token
投机解码（2022-11）、Medusa、EAGLE 系列，到 DeepSeek-V3 把多 token 预测头训进模型（2024-12）。它与批处理正交，但两者争夺同一份空闲算力：批越大收益越小，长上下文时又重新划算（见上面的“意外”）。
2023-12

SGLang 的 RadixAttention：算过的前缀不再算

卡在哪
多轮对话、智能体、少样本提示共享很长的前缀，每次都重做预填充，而预填充本来就占服务器一半的时间。
怎么解决
基数树索引所有缓存过的序列，复用最长的已缓存前缀，输入成本降到 \((1-h) + hr\)。
代价
命中率取决于路由；缓存与并发数抢显存。
引出
没命中的长提示仍要整段预填充，期间所有正在解码的用户一起卡住。
2023-08 → 2024

分块预填充：把预填充填进解码的算力空隙

卡在哪
长提示的预填充让批里所有人停顿几百毫秒，每 token 间隔的尾部随负载急剧上升。
怎么解决
Sarathi 与 Sarathi-Serve 把提示切块、与解码拼在同一步，每步 token 预算约为 \(B^\ast(1 + B\bar n\kappa/W)\)，不中断正在进行的解码。
代价
首 token 延迟略增；两类负载仍挤在同一批 GPU、同一种并行方式上。
引出
能不能把两类负载彻底分开，各自优化？
同类DeepSpeed-FastGen 的 Dynamic SplitFuse
DeepSpeed 团队 2023-11 独立提出同样的思路：拆开长提示、合并短提示，让每一步的 token 数大致恒定。结论一致：调度的核心变量是每一步的 token 预算，而不是批里有几个请求。
2024

P/D 分离与以 KV 为中心的架构

卡在哪
同一批卡、同一种并行方式无法同时适合吃算力的预填充和吃带宽的解码；两个 SLO 互相牵制，只能一起多配机器。
怎么解决
DistServe、Splitwise 把两者放进不同的 GPU 池，KV 经网络传输（每 token 的传输时间远小于预填充时间）；Mooncake 再用 CPU 内存和 SSD 组成分布式 KV 池，按 KV 的位置调度。
代价
要高速网络；两个池的配比要随流量调整；系统复杂度大增。
引出
KV 成了要存储、传输、路由的一等公民；万亿参数的 MoE 还需要更大的通信域。
争论分离还是分块
一方认为中小规模部署里分块已消除大部分干扰，分离只增加复杂度；另一方认为只有分开才能让两类负载各选并行方式和硬件。到 2025 年主流框架都支持分离，而分块仍是单机的默认做法。
2025–2026

宽专家并行、KV 感知路由与按阶段专门化

卡在哪
推理模型和智能体让 token 消耗和上下文长度暴增；数千亿到万亿参数的 MoE 在一台 8 卡服务器上既放不下，也凑不出足够大的批。
怎么解决
宽专家并行把专家摊到上百张卡；超节点扩大 NVLink 域；KV 感知路由和分层 KV 存储；注意力与 FFN 分离；硬件按预填充、解码分工。
代价
模型、内核、网络、调度深度耦合，换任何一环都要重新调优。
引出
服务之外，训练这些模型需要怎样的系统？（第 章）
被淘汰TGI 进入维护模式
Hugging Face 的 Text Generation Inference 曾是开源推理服务的主力之一，2025-12 进入维护模式，建议新部署改用 vLLM 或 SGLang。上面这些优化需要持续大量投入，推理框架的竞争集中到了少数几个社区最大的项目上。
分支注意力与 FFN 分离
MegaScale-Infer（2025-04）、Step-3（2025-07）把 MoE 的注意力层和专家层放到不同的卡上，用微批次“乒乓”让两边都不空闲。DistServe 团队称之为 P/D 分离之后“自然的下一步”；它对稠密模型的收益还不明确。

自测

1. 一块芯片 FP8 算力 4500 TFLOPS、带宽 8 TB/s，跑 FP8 权重。解码时批大约多大开始转为计算受限（只考虑权重）？
\(B^\ast = P\,b/(2\,\text{BW}) = 4500\times 10^{12}\times 1/(2\times 8\times 10^{12})\approx 281\)。
2. 动手算：8×H100 跑 70B（BF16 权重 141 GB，KV 预算约 449 GB，每 token KV 320 KB，合计带宽 26.8 TB/s）。每个请求的上下文 32K 时最多同时服务多少个？满载时每步约多久、整台每秒多少 token？按每卡每小时 2 美元，每百万输出 token 多少钱？KV 改存 FP8 呢？
每个请求 \(32000\times 327680\approx 10.5\) GB，最多 \(449/10.5\approx 42\) 个。每步读 \(141 + 42\times 10.5\approx 581\) GB，约 21.7 毫秒，整台每秒约 \(42/0.0217\approx 1940\) token，每人约 46 token/s；成本 \(16/(1940\times 3600)\times 10^6\approx 2.3\) 美元 / 百万 token。FP8：每个请求 5.2 GB，85 个，每步仍约 22 毫秒，吞吐约 3900 token/s，成本减半到约 1.15 美元；每个人的速度不变。对比 5K 上下文时的 274 个并发，长上下文让同一台机器贵了 6 倍多。
3. 一个服务每秒最多处理 4 个请求。按 M/M/1 估算，到达率从每秒 2 个涨到 3.6 个，平均停留时间变成原来的几倍？系统里平均有几个请求？
\(S = 0.25\) 秒。\(\lambda = 2\)：\(\rho = 0.5\)，\(\bar T = 0.25/0.5 = 0.5\) 秒，由利特尔定律 \(\bar N = 2\times 0.5 = 1\)。\(\lambda = 3.6\)：\(\rho = 0.9\)，\(\bar T = 0.25/0.1 = 2.5\) 秒，\(\bar N = 9\)。负载涨了 80%，延迟涨了 5 倍，系统里的请求数涨了 9 倍。
4. 草稿接受率 \(\alpha = 0.6\)，每轮猜 \(\gamma = 3\) 个，草稿成本 \(c = 0.1\)。每轮期望产出多少 token？加速比约多少？如果批里有 100 个请求、跑在 \(B^\ast = 295\) 的芯片上，还能指望这个加速比吗？
\((1 - 0.6^4)/0.4 = (1 - 0.1296)/0.4\approx 2.18\)；加速比 \(2.18/(1 + 0.3)\approx 1.67\) 倍。批 100 时一轮验证要算 \(100\times 4 = 400\) 个位置，超过拐点 295，验证不再免费，加速比会明显低于 1.67；除非上下文很长、每步主要在读 KV（那时实际的拐点会上移）。
