推理系统：同时服务几百万人

解码被显存带宽卡住，所以线上服务要让很多人共用一次权重读取；共用的代价是每个人各自的 KV 缓存，它摊不薄，还要占显存。这一章用一个 70B 模型和一台 8 卡服务器，跟着一个请求把账算一遍，再按这个代价一层层讲系统怎么修：显存怎么管、批怎么组、算过的怎么复用、预填充和解码怎样互不干扰、MoE 怎样摊到上百张卡上，最后算一百万个 token 的成本。

第 章说单用户解码只能用到算力的零头，第 章把模型压小以减少要读的字节。另一个、也是更重要的杠杆，是让一次权重读取同时服务很多用户。

  • KV 缓存、GQA / MLA：第 章；MoE、专家并行与全对全通信：第 章
  • 自回归生成、多 token 预测：第 章；张量并行与全规约：第 章「互连」一节

从零开始：跟着一个请求走一遍

这一节用一个具体的例子，把一次请求从到达到返回的每一站走一遍，每一站都算出时间的量级。后面每一节都在优化其中某一站。设定如下：

项目设定由此得到
模型Llama 3 70B 级稠密模型：70.6B 参数，80 层，64 个 Q 头、8 个 KV 头（GQA），头维 128BF16 权重 \(W\) = 141 GB
硬件一台 8×H100 SXM 服务器，用张量并行把每层的矩阵按行或列切到 8 张卡上，每张卡算一部分，每层再做两次全规约把结果加起来（第 章）显存 640 GB，合计带宽 26.8 TB/s，BF16 稠密算力 7.9 PFLOPS

下面的数字都是理想化的 roofline 估算：按峰值带宽和算力算，忽略卡间通信和内核开销。真实系统会慢一些，但量级和瓶颈的位置不变。

第一站：到达与排队

请求经过网关、分词，进入调度器的等待队列。调度器每一步（几到几十毫秒）检查一次：显存够不够放它的 KV 缓存，批里有没有空位。这一站的时间与模型无关，只取决于此刻有多少别人在用：空闲时是零，高峰时可以是几十秒（「排队」一节）。

第二站：预填充

预填充（prefill）：把整个提示一次性送进模型，算出所有位置的 KV 缓存和第一个输出 token。计算量约为“每个 token \(2N\) FLOPs × 提示长度”：

\[ 2\times 70.6\times 10^{9}\times 4000\approx 5.6\times 10^{14}\ \text{FLOPs} \] 注意力本身在 4000 token 时只再多 4%；上下文到十万左右时它会和这一项相当

按 50% 的算力利用率，需要 \(5.6\times 10^{14}/(7.9\times 10^{15}\times 0.5)\approx 0.15\) 秒。这期间权重只读了一遍（141 GB ÷ 26.8 TB/s = 5.3 毫秒），每个权重被 4000 个 token 共用：大矩阵乘大矩阵，计算受限。从请求到达到第一个 token 返回的时间叫首 token 延迟（time to first token，TTFT），等于排队 + 预填充 + 网络，这里约 0.15 秒。

第三站：留下 KV 缓存

预填充顺带算出了提示里每个 token 在每一层的 K 和 V，存起来就是 KV 缓存。按第 章的公式，每 token \(\kappa = 2\times 80\times 8\times 128\times 2\) 字节 ≈ 328 KB（本章一律用十进制的 KB、GB）。4000 token 是 1.31 GB；生成完 1000 个 token 后涨到 1.64 GB。这块显存从预填充开始一直占到请求结束，后面每生成一个 token 都要把它完整读一遍。

第四站：逐个生成

解码（decode）：之后每步只生成 1 个 token。每一步都要把全部权重（141 GB）和这个请求自己的 KV（约 1.5 GB）读一遍，计算却只有 \(2N = 1.4\times 10^{11}\) FLOPs：

\[ \begin{aligned} t_{\text{读}} &\approx \frac{141 + 1.5\ \text{GB}}{26.8\ \text{TB/s}}\approx 5.3\ \text{ms} \\ t_{\text{计算}} &\approx \frac{1.4\times 10^{11}}{7.9\times 10^{15}}\approx 0.02\ \text{ms} \end{aligned} \]

GPU 99.7% 的时间在等数据，访存受限。第一个 token 之后平均每个 token 的间隔叫每 token 间隔（time per output token，TPOT），即 \((T_{\text{结束}} - T_{\text{首}})/(n_{\text{输出}} - 1)\)，就是用户看到的“打字速度”。这里 TPOT = 5.3 毫秒，每秒 188 个 token，1000 个 token 要 5.3 秒。

第五站：和别人拼成一批

算力闲着 99.7%，可以让别的用户的解码步拼进来。先取一个中等的批，64 人：权重读一遍，64 个 token 共用。KV 却各是各的，64 份都要读：

\[ t_{\text{步}} \approx \frac{141 + 64\times 1.47\ \text{GB}}{26.8\ \text{TB/s}} = \frac{141 + 94\ \text{GB}}{26.8\ \text{TB/s}}\approx 8.8\ \text{ms} \]

计算时间约 1.2 毫秒，仍然访存受限。整台服务器每秒产出 \(64/8.8\ \text{ms}\approx 7300\) 个 token，是单用户的 39 倍；每个用户的速度从 188 降到 114 token/s。注意 KV 的 94 GB 已经是权重的三分之二：权重能被批摊薄，KV 不能。这一点下一节展开。

第六站：显存够几个人用

640 GB 显存，减去权重 141 GB，再给激活和运行时留约 50 GB，剩下约 449 GB 放 KV。每个请求到结束时占 1.64 GB，最多同时服务 \(\lfloor 449/1.64\rfloor = 273\) 个。到这个规模，每一步要读 141 GB 权重加约 400 GB KV，约 20 毫秒；整台每秒约 1.35 万 token，每人 49 token/s。如果像早期系统那样给每个请求按最大上下文 128K 预留空间（每个 43 GB），就只能同时服务 10 个。

第七站：返回、计费与容量

在 64 人一批时，这个请求从到达到最后一个 token 约 \(0.15 + 1000\times 8.8\ \text{ms}\approx 9\) 秒。它占用了服务器多少时间？预填充独占整台服务器 0.15 秒；解码阶段 1000 步、每步 8.8 毫秒，但由 64 人分摊，合 0.14 秒。合计约 0.29 秒，所以批上限取 64 时，这台服务器每秒最多处理约 3.5 个这样的请求。预填充占了一半。如果 3000 token 的公共前缀已经算过（「前缀缓存」一节），预填充降到约 0.04 秒，容量升到每秒约 5.7 个。按每卡每小时 2 美元（整台 16 美元），每个请求的成本约 0.13 美分。

和第六站对一下账。第六站的“满载 273 人、每秒 1.35 万 token”只算了解码，换算成请求是每秒 13 个；可每个请求还有 0.15 秒的预填充要独占整台机器。把它算进去，273 人一批时每个请求占服务器约 \(0.15 + 1000\times 20.3\ \text{ms}/273\approx 0.22\) 秒，容量约每秒 4.5 个，只比 64 人一批的 3.5 个高三成，每个请求的成本从 0.13 美分降到约 0.10 美分。批处理把解码摊薄了，预填充成了新的大头：后面的前缀缓存、分块和分离，修的都是这一块。

用户感受到的是两个延迟：首 token 延迟（TTFT）和每 token 间隔（TPOT）。服务方给它们定的目标、以及只算达标请求的吞吐，留到「排队」一节再定义，那里才用得上。

批处理的算术：权重能摊薄，KV 不能

上面的例子里，批从 1 增到 64，吞吐涨了 39 倍；再从 64 增到 273，只多涨了不到 1 倍。原因在于一步解码要读的两类数据性质不同。权重是所有人共用的一份矩阵：64 个人的 token 拼成一个 64 行的矩阵，和同一份权重做一次矩阵乘法，权重读一遍就够。KV 是每个人自己的历史：64 个人就是 64 份不同的数据，一份也省不掉。

如果只有权重，第 章已经推过：批要大到 \(B^\ast = Pb/(2\,\text{BW})\) 才能用满算力（\(P\) 是峰值算力，\(b\) 是每个权重的字节数，即那一章的 \(m^\ast\)）。H100 无论 BF16 权重配 BF16 计算，还是 FP8 权重配 FP8 计算（W8A8），\(B^\ast\) 都约为 295；只有权重是 FP8、计算仍按 BF16 时，它降到约 148。把每个请求的 KV 加进去：

\[ \begin{aligned} t_{\text{步}}(B) &\approx \max\Big(\frac{\htmlClass{sym-W}{W} + \htmlClass{sym-B}{B}\,\htmlClass{sym-n}{\bar n}\,\htmlClass{sym-k}{\kappa}}{\htmlClass{sym-BW}{\text{BW}}},\ \frac{2\htmlClass{sym-N}{N}B}{\htmlClass{sym-P}{P}}\Big) \\ \text{吞吐} = \frac{B}{t_{\text{步}}} &\ \le\ \frac{\text{BW}}{\bar n\,\kappa} \end{aligned} \] 权重一步只读一次，KV 每个请求读一份；批再大，吞吐也越不过“带宽 ÷ 每个请求的 KV”
每一步要读的字节 = 权重 + 批里每个请求各自的 KV。批小时权重占大头，加人几乎不加时间；批大了 KV 占大头，每加一个人就多读一份 KV，步长随之线性变长，吞吐趋于一个上限。

\(B\)
批大小：这一步同时解码的请求数
\(\bar n\)

\(\kappa\)

\(\text{BW}\)
显存带宽（多卡时取合计）
\(N\)

上节的例子，\(\bar n = 4500\)：读权重 5.3 ms，每多一个请求多读 1.47 GB，即 0.055 ms。\(B = 64\)：8.8 ms；\(B = 273\)：20.3 ms。吞吐上限 \(26.8\ \text{TB/s}/1.47\ \text{GB}\approx 1.8\) 万 token/s：批无限大也越不过它。上下文涨到 32K，上限降到约 2500 token/s。
第 1 步：只读权重。单用户解码，时间几乎全花在读权重上。
第 2 步：加上每个请求的 KV。权重被 \(B\) 个请求共用，KV 不共用。
第 3 步：和计算时间取较大者。读数据和计算可以重叠，慢的那个决定步长。

用算术强度的话说（推导见下面的折叠）：批处理只抬高了权重那一部分的强度。KV 那一部分的强度是一个与批大小无关的常数，GQA-8、BF16 时只有 8，不到 H100 拐点 295 的 3%。批大到 KV 占满读取量时，整步的强度停在“权重的计算摊到 KV 字节上”加上这个常数：例子里约 104，仍远低于 295，所以这台机器无论批多大都是访存受限。上下文越长，第一项越小，强度越接近 8。

预填充与解码的算术强度：分成权重和注意力两部分

第 1 步，权重部分。一次前向要把 \(N\) 个参数（\(Nb\) 字节）读一遍，参与这次前向的每个 token 对每个参数做一次乘加（2 FLOPs）。一次前向里有 \(m\) 个 token 时，算术强度是

\[ I_{\text{权重}} = \frac{2Nm}{Nb} = \frac{2m}{b} \]

预填充 \(m = n\)（提示长度），解码 \(m = B\)（批大小）。令它等于芯片的拐点 \(P/\text{BW}\)，就是上面的 \(B^\ast\)（第 章的 \(m^\ast\)）。预填充 4000 token、BF16 时强度为 4000，远高于 H100 的 295：计算受限。

第 2 步，注意力部分（解码）。新 token 要和自己的 \(n\) 个历史 token 做注意力。每层每个 Q 头：打分 \(nd_h\) 次乘加，加权求和再 \(nd_h\) 次，所有头合计 \(4h_qd_hn\) FLOPs；要读的是这个请求自己的 KV，\(2h_{kv}d_hnb\) 字节：

\[ I_{\text{注意力}} = \frac{4h_qd_hn}{2h_{kv}d_hn\,b} = \frac{2}{b}\cdot\frac{h_q}{h_{kv}} \]

它与 \(B\) 和 \(n\) 都无关。原因是 KV 是每个请求私有的：批里有 64 个请求，就要读 64 份不同的 KV，没有任何共享。GQA-8、BF16 时 \(I_{\text{注意力}} = 8\)，不到拐点的 3%。

第 3 步，合起来。一个解码步的总强度：

\[ I_{\text{解码}} = \frac{2NB + 4Lh_qd_h\,\bar nB}{Nb + B\,\bar n\,\kappa} \]

\(B\) 小时分母由权重主导，强度约 \(2B/b\)，随批增长。\(B\) 大到 \(B\bar n\kappa\gg Nb\) 时，分母里权重的字节被摊薄了，但分子里权重的 FLOPs（每 token \(2N\)）还在，分子分母同除以 \(B\bar n\kappa\)：

\[ I_{\text{解码}}\ \xrightarrow{\ B\to\infty\ }\ \frac{2N}{\bar n\,\kappa} + \frac{4Lh_qd_h}{\kappa} = \frac{2N}{\bar n\,\kappa} + I_{\text{注意力}} \]

（第二项用了 \(\kappa = 2Lh_{kv}d_hb\)。）它不再随 \(B\) 增长。例子里 \(\bar n = 4500\)：\(1.41\times 10^{11}/(4500\times 3.28\times 10^{5}) + 8\approx 96 + 8 = 104\)，仍低于拐点 295。第一项随上下文变短而变大，随上下文变长而变小：只有 \(\bar n\) 远大于 \(2N/(\kappa I_{\text{注意力}})\approx 5.4\) 万时，强度才接近 \(I_{\text{注意力}} = 8\)。

第 4 步，预填充的注意力为什么不受限。预填充时同一个请求的 \(n\) 个 query 共用同一份 KV，FlashAttention 把它分块留在片上反复使用（第 章），强度随 \(n\) 增长，所以预填充始终是计算受限的。

这个推导告诉我们：批处理提高的只是权重部分的强度，而且批再大，强度也有一个上限 \(2N/(\bar n\kappa) + I_{\text{注意力}}\)。上下文越长，解码越接近“每个请求各读各的 KV”，强度向 \(2h_q/(h_{kv}b)\) 靠拢。要再往上推，只能改这个比值：加大 GQA 的分组、用 MLA 让所有头共用一个潜向量、把 KV 存成 FP8。这是长上下文服务贵的根本原因。

显存账：能同时服务多少人

上一节说批越大越好，但批不能无限大：每个请求的 KV 都要在显存里待到它结束。能同时服务的请求数由显存决定：

\[ \htmlClass{sym-Bm}{B_{\max}} = \Big\lfloor \frac{\htmlClass{sym-M}{M_{\text{显存}}} - W - \htmlClass{sym-Mr}{M_{\text{运行时}}}}{\htmlClass{sym-n}{n}\,\kappa} \Big\rfloor \] 显存减去权重和运行时开销，除以每个请求的 KV

\(M_{\text{显存}}\)

\(M_{\text{运行时}}\)

上节的例子：\(\lfloor(640 - 141 - 50)/1.64\rfloor = 273\)。KV 改存 FP8：547。换成每层 576 维的 MLA：约 970。上下文 32K：只剩 41。一张 H100 读完自己的 80 GB 要 24 毫秒，这是满载步长的上限。

显存装满时，每一步都要把几乎整块显存（权重加全部 KV）读一遍，步长约等于“显存容量 ÷ 带宽”：例子里 \((141 + 449)\ \text{GB}/26.8\ \text{TB/s}\approx 22\) 毫秒，和注意力是哪一种几乎无关。由此得到一个简单的结论：在访存受限的范围内，满载吞吐 ≈ \(B_{\max}\) ÷ 读一遍显存的时间，每个请求的 KV 越小，同一台机器能同时服务的人越多，也就越便宜。

KV 的压缩比，以及它为什么同时改变容量、吞吐与强度

每 token 的 KV 是 \(\kappa = 2Lh_{kv}d_hb\)（第 章）。GQA 和 MLA 相对普通多头注意力（MHA，\(h_{kv} = h_q = h\)）的压缩比：

\[ \frac{\kappa_{\text{MHA}}}{\kappa_{\text{GQA}}} = \frac{h}{h_{kv}},\qquad \frac{\kappa_{\text{MHA}}}{\kappa_{\text{MLA}}} = \frac{2hd_h}{d_c + d_r} \]

\(d_c\) 是 MLA 的潜向量维度（512），\(d_r\) 是单独做 RoPE 的维度（64）。70B 级模型（\(h = 64\)，\(d_h = 128\)）：MHA 每 token 2.6 MB；GQA-8 是它的 1/8（328 KB）；MLA 是 \(576/(2\times 64\times 128)\approx 1/28\)（92 KB）。128 个头的 DeepSeek-V3 压缩比更大（第 章算过）。FP8 再减半。

容量与吞吐。代入上面两张卡：显存墙 \(B_{\max}\propto 1/\kappa\)；满载时步长约等于读一遍显存，与 \(\kappa\) 无关，所以满载吞吐 \(B_{\max}/t\) 也 \(\propto 1/\kappa\)；批无限大时的上限 \(\text{BW}/(n\kappa)\) 同样 \(\propto 1/\kappa\)。三个量一起按压缩比放大；只要仍是访存受限，每个用户的速度不变（KV 小到墙之前就算力受限时，每人的速度反而会降一点）。

强度。MLA 还改变了上一节的 \(I_{\text{注意力}}\)。矩阵吸收之后，每个头的 query 直接和 576 维的潜向量做点积（576 次乘加），再对其中 512 维加权求和（512 次）。每读一个历史 token 的潜向量（\(576b\) 字节），所有头一共做 \(2h(576 + 512)\) FLOPs：

\[ I_{\text{MLA}} = \frac{2h\,(d_c + d_r + d_c)}{(d_c + d_r)\,b}\approx \frac{3.8\,h}{b} \]

\(h = 128\)、BF16 时约 242，接近 H100 的拐点 295；KV 存 FP8 则超过拐点。GQA-8 只有 8。DeepSeek 开源的 FlashMLA 内核（2025-02）在 H800 上报告了 580 TFLOPS 的计算受限配置，与这个推导一致：MLA 的解码注意力已经不是在“搬数据”，而是在“算”。

这个推导告诉我们：在访存受限的范围内，KV 每小一倍，能同时服务的人数、满载吞吐和吞吐上限都翻一倍。这就是为什么推理成本低的模型几乎都在注意力结构上下了功夫（MLA、大分组 GQA、滑动窗口、线性注意力混合），而不只是在权重上做量化。

连续批处理与分页 KV 缓存

前两节假设批里的请求整齐划一。实际请求的输出长度差异很大，短的几个 token，长的几万 token。静态批处理（FasterTransformer 时代的做法）把一批请求一起送进去，要等最长的那个结束才能换下一批，其余槽位只能空转，新来的请求也只能等。连续批处理（Orca, 2022）把调度粒度从“请求”改成“迭代”：每个解码步都检查一次，有请求结束就立刻从队列补上新的请求。Orca 在 GPT-3 175B 上报告，同等延迟下吞吐是 FasterTransformer 的 36.9 倍。补进来的新请求要先做一次预填充才能加入解码，这会打断批里其他人（「预填充与解码」一节要处理的问题）。

演示的左右两边同时换了两件事：调度（静态 → 连续）决定槽位利用率，显存分配（按最大长度预留 → 分页）决定 KV 显存利用率。下面讲第二件。

连续批处理让批可以变大，接下来卡住的是显存。旧做法按最大长度给每个请求预留一整块连续显存，实际只用了一小部分，预留了却没存 token 的部分就是显存碎片。PagedAttention（vLLM, 2023）借鉴操作系统的分页：把 KV 缓存切成固定大小的块（比如每块 16 个 token），按需分配，用块表记录每个请求的块在哪里。vLLM 团队统计，此前的系统因碎片和过度预留浪费 60–80% 的 KV 显存，分页后浪费降到 4% 以下；论文报告同等延迟下吞吐是 FasterTransformer 和 Orca 的 2–4 倍。

\[ \text{浪费率}_{\text{预留}} = 1 - \frac{\htmlClass{sym-El}{\mathbb E[\ell]}}{\htmlClass{sym-Lm}{L_{\max}}},\qquad \text{浪费率}_{\text{分页}} \approx \frac{(\htmlClass{sym-Sb}{S_{\text{块}}} - 1)/2}{\mathbb E[\ell]} \]
按最大长度预留时，浪费由“最坏情况有多长”决定；分页时，每个请求最多浪费最后一块没填满的部分，平均半块。
\(\mathbb E[\ell]\)
请求实际用到的平均长度
\(L_{\max}\)
预留的最大长度
\(S_{\text{块}}\)
分页的块大小（token 数）
平均 5000 token、按 128K 预留：浪费 \(1 - 5000/131072\approx 96\%\)，例子里只能放 10 个请求。分页、\(S_{\text{块}} = 16\)：平均浪费 7.5 个 token，即 0.15%，能放 273 个。
两种碎片，以及分页的期望浪费

按最大长度预留。每个请求预留 \(L_{\max}\) 个 token 的连续空间，实际只用 \(\ell\)。期望利用率是 \(\mathbb E[\ell]/L_{\max}\)：输出长度事先不知道，\(L_{\max}\) 只能按最坏情况取，\(\mathbb E[\ell]\) 却由大量短请求决定。这是内部碎片。预留的块大小不一，请求结束后释放出的空洞未必放得下下一个请求，这是外部碎片。vLLM 论文测得，当时的系统里只有 20.4%–38.2% 的 KV 显存真正存了 token。

分页。块大小 \(S_{\text{块}}\) 个 token，按需分配，只有每个请求的最后一块可能没填满。若 \(\ell\bmod S_{\text{块}}\) 近似均匀分布，最后一块平均空 \((S_{\text{块}}-1)/2\) 个位置，期望浪费率约 \((S_{\text{块}}-1)/(2\,\mathbb E[\ell])\)。所有块大小相同，任何空闲块都能分给任何请求，外部碎片为零。

副产品：共享。块表让“两个请求指向同一块物理显存”变得很自然：同一个提示采样多个回答时，提示部分的块只存一份，写入时才复制。vLLM 报告这让并行采样和束搜索的显存减少最多 55%。

代价。KV 在显存里不再连续，注意力内核要按块表间接寻址。块越小浪费越少，但寻址和调度的开销越大，所以块大小常取 16–64（FlashMLA 用 64）。

这个推导告诉我们：分页把浪费从“由最坏情况决定”变成了“每个请求最多半块”，与请求长度的分布无关。省下的显存直接变成更大的 \(B_{\max}\)，而上一节推导过，满载吞吐与 \(B_{\max}\) 成正比。

分页还有一个副作用：输出长度事先不知道，按需分配意味着显存可能在请求中途耗尽。这时调度器要暂停某些请求，把它们的 KV 换出到 CPU 内存，或者干脆丢掉、之后重算。

前缀缓存：算过的不再算

系统提示、多轮对话的历史、智能体的工具说明、同一份长文档上的多个问题，都是许多请求共享的前缀。分页的块表让“两个请求指向同一块物理显存”变得很自然，于是内容相同的前缀也可以共用同一批块：这就是前缀缓存（prefix caching），共享的前缀只计算一次 KV，之后直接复用。能复用的原因是因果注意力：位置 \(i\) 的 K、V 只取决于第 1 到第 \(i\) 个 token，前缀不变，它们就不变；反过来，必须逐 token 完全相同，中间任何一个 token 变了，它后面的缓存全部作废。SGLang 的 RadixAttention（2023-12）用一棵基数树（radix tree）索引所有缓存过的 token 序列：新请求进来，沿树找到最长的已缓存前缀，只对剩下的部分做预填充；显存不够时按最近最少使用的顺序淘汰叶子。论文报告在智能体、多轮对话、少样本等任务上吞吐最多提高 6.4 倍；在 Chatbot Arena 的实际部署中，一个月的缓存命中率在 52%–74%。

\[ \text{输入成本} \propto (1 - \htmlClass{sym-eta}{\eta}) + \htmlClass{sym-eta}{\eta}\cdot\htmlClass{sym-r}{r} \]
命中率为 \(\eta\) 时，只有 \(1-\eta\) 的输入 token 要重新做预填充；命中的部分只需从缓存里读出来，成本是正常的 \(r\) 倍。
\(\eta\)

\(r\)

\(\eta = 0.9\)、\(r = 0.1\)：输入成本降到原来的 \(0.1 + 0.09 = 19\%\)。DeepSeek 2025-03 公布的一天里，6080 亿输入 token 中 56.3% 命中缓存，输入成本约为不缓存时的一半。上文的例子：3000/4000 命中，预填充从 0.15 秒降到 0.04 秒，服务器容量从每秒 3.5 个请求升到 5.7 个。

各家 API 对缓存命中的输入 token 收费通常只有正常价格的十分之一，原因就在这里；智能体怎样为此保持前缀不变，见第 章。命中率还取决于调度：模型部署在几十台机器上时，请求要发到缓存了它的前缀的那台，这叫 KV 感知路由（KV-aware routing），NVIDIA Dynamo（2025-03）和 llm-d（2025）都把它作为核心功能。缓存放不下时，还可以退到 CPU 内存和 SSD（下文的 Mooncake）。

投机解码：小模型先猜，大模型一次验证

解码受带宽限制，算力闲着。投机解码（Leviathan 等, 2022；Chen 等, 2023）利用这些闲置算力：用一个便宜的“草稿”连续猜 \(\gamma\) 个 token，大模型一次前向并行验证这 \(\gamma\) 个位置（与预填充一样，多个位置一起算几乎不比一个位置慢）。从第一个被拒绝的位置截断，并在那里补一个 token。最简单的是贪心解码：大模型在每个草稿位置自己的 argmax 若等于草稿的词，就接受；第一个不等的位置换成大模型自己的词，后面的草稿全部作废。采样时的接受规则稍复杂，见下面第一个折叠，它保证输出分布不变。

草稿从哪来？可以是独立的小模型；Medusa、EAGLE 在大模型上挂几个轻量的预测头，利用大模型自己的隐藏状态，接受率高，EAGLE-3 是 2025–26 年 vLLM、SGLang 的主力；DeepSeek-V3/V4 训练时就带多 token 预测头（第 章），推理时直接当草稿；prompt lookup 直接从上下文里找重复片段，改代码、引用原文时特别有效。

每轮产出的 token 数和加速比：

\[ \mathbb E[\text{每轮产出的 token 数}] = \frac{1 - \htmlClass{sym-al}{\alpha}^{\gamma + 1}}{1 - \alpha},\qquad \text{加速比}\approx\frac{1 - \alpha^{\htmlClass{sym-g}{\gamma}+1}}{(1-\alpha)(1 + \htmlClass{sym-g}{\gamma}\,\htmlClass{sym-c}{c})} \]
每个草稿 token 以概率 \(\alpha\) 被接受，接受到第一个拒绝为止，再加上补的那一个。分母中的 \(\gamma c\) 是生成草稿的额外开销。
\(\alpha\)
草稿 token 的平均接受率
\(\gamma\)
每轮猜几个
\(c\)
生成一个草稿 token 的成本相对大模型一次前向的比例
\(\alpha = 0.8\)，\(\gamma = 4\)：每轮期望产出 \((1 - 0.8^5)/0.2 = 3.36\) 个 token。草稿成本 \(c = 0.05\)，加速比约 \(3.36/1.2 = 2.8\) 倍。

这个加速比有一个前提：验证时多算的那几个位置几乎不要钱。一轮验证要为批里每个请求算 \(\gamma+1\) 个位置，共 \(B(\gamma+1)\) 个，权重却只读一遍。只要这个数还没超过拐点 \(B^\ast\)（上文的机器约 295），多出来的位置吃的是闲置的算力；批大到把算力吃满，验证就开始变慢，加速比随之缩水，甚至低于 1。投机解码和批处理争的是同一份闲置算力：\(\gamma = 4\) 时，批超过约 59 就不再免费，所以短上下文、大批量的服务常常把它关掉。下面的演示里可以拖动批大小看到这一点（只算权重，即短上下文的情形）。长上下文时账会翻过来，见后面的意外框。

为什么输出分布和大模型单独生成完全一样

设大模型在某个位置的分布为 \(p\)，草稿的分布为 \(q\)，草稿抽到了 token \(x\)。验证规则：

  • 以概率 \(\min\big(1,\ p(x)/q(x)\big)\) 接受 \(x\)；
  • 若拒绝，从“残差分布” \(r(y)\propto\max\big(0,\ p(y) - q(y)\big)\) 中重新抽一个 token。

最终输出 \(y\) 的概率是“草稿抽到 \(y\) 并被接受”加上“某次被拒绝后从残差中抽到 \(y\)”：

\[ \begin{aligned} P(y) &= q(y)\min\Big(1, \frac{p(y)}{q(y)}\Big) + \Big(1 - \sum_x q(x)\min\Big(1,\frac{p(x)}{q(x)}\Big)\Big)\,r(y)\\ &= \min\big(q(y), p(y)\big) + \max\big(0,\ p(y) - q(y)\big) = p(y) \end{aligned} \]

（中间一步用到：拒绝的总概率 \(1 - \sum_x\min(q(x), p(x))\) 恰好等于 \(\sum_y\max(0, p(y) - q(y))\)，即残差分布的归一化常数。）

这个推导告诉我们：投机解码是一种精确的加速，不是近似：无论草稿多差，输出分布都与大模型一致，草稿的质量只影响接受率，也就是速度。平均接受率 \(\alpha = \sum_x\min(p(x), q(x))\)，草稿与大模型越像越高。

期望接受长度，以及批大了以后还划不划算

第 1 步，接受长度的分布。设每个草稿 token 被接受的概率都是 \(\alpha\)，彼此独立。一轮产出的 token 数 \(X\) = 被接受的草稿数 + 1（被拒绝处补的那一个，或全部接受后大模型顺带算出的下一个）。“至少产出 \(k\) 个”等于“前 \(k-1\) 个草稿都被接受”：\(\Pr[X\ge k] = \alpha^{k-1}\)，\(k = 1,\dots,\gamma+1\)。

第 2 步，期望。对取正整数值的随机变量，\(\mathbb E[X] = \sum_{k\ge 1}\Pr[X\ge k]\)：

\[ \mathbb E[X] = \sum_{k=0}^{\gamma}\alpha^k = \frac{1-\alpha^{\gamma+1}}{1-\alpha}\ \xrightarrow{\ \gamma\to\infty\ }\ \frac{1}{1-\alpha} \]

\(\alpha = 0.8\) 时最多 5 个。猜得再长也越不过这个上限，而草稿的成本 \(\gamma c\) 线性增长，所以存在一个最优的 \(\gamma\)：\(\alpha\) 越高、草稿越便宜，它越大（上面的演示里，批为 1 时从 1 到 10 不等）。

第 3 步，批大了以后（只看权重）。普通解码一步的时间正比于 \(\max(1, B/B^\ast)\)：批低于拐点时由读权重决定，高于拐点时由计算决定。一轮验证要算 \(B(\gamma+1)\) 个位置，时间正比于 \(\max\big(1, B(\gamma+1)/B^\ast\big)\)。两者之比就是验证相对一步普通解码多花的时间，加速比要再除以它：

\[ \text{加速比}(B)\approx\frac{\mathbb E[X]}{(1+\gamma c)}\cdot\frac{\max(1,\ B/B^\ast)}{\max\big(1,\ B(\gamma+1)/B^\ast\big)} \]

H100、\(B^\ast = 295\)、\(\gamma = 4\)：\(B\le 59\) 时第二个因子是 1；\(B = 128\) 时是 \(295/640\approx 0.46\)；\(B = 256\) 时约 0.23，\(\alpha = 0.75\)、\(c = 0.05\) 的 2.5 倍加速变成 0.6 倍，比不用还慢。演示里的“批大小”滑块就是这个公式。vLLM 等框架因此提供“批超过某个大小就关掉投机解码”的选项。

第 4 步，长上下文把账翻了过来。第 3 步只看了权重。一轮验证里，每个请求的 KV 也只读一遍，却换来 \(\mathbb E[X]\) 个 token：KV 的读取被摊薄了 \(\mathbb E[X]\) 倍。而「批处理的算术」一节推导过，长上下文时每步的时间主要花在读 KV 上，批处理摊不薄它，投机解码却可以。

这个推导告诉我们：投机解码的收益取决于“验证时多算的那些位置是不是免费”，也就是这一步离拐点还有多远。短上下文、大批量时它不划算；长上下文时读 KV 让解码重新回到带宽受限，它又划算了。

意外：批越大，投机解码反而可能越划算

原以为
投机解码只适合小批量、低延迟的场景：批大了 \(B(\gamma+1)\) 超过拐点，验证不再免费（见上文）。
实际发现
MagicDec（ICLR 2025 版）报告，Llama-3.1-8B 在批大小 32–256 的中长序列生成中最多加速 2.51 倍（多种硬件与任务），而且加速比随批增大而上升。
为什么
上文只算了权重。一轮验证里，每个请求的 KV 也只读一遍，却换来好几个 token：KV 的读取被摊薄了。而「批处理的算术」一节说过，上下文够长时每步的时间主要花在读 KV 上，批处理摊不薄它，大批量也仍是带宽受限，投机解码却能摊薄它。它的草稿只保留最近一段和开头几个 token 的 KV，草稿成本几乎不随上下文增长。论文给出一个临界长度：短于它，加速比随批增大而下降；长于它，反而上升。
现在怎么看
结论依赖设置。MagicDec 自己指出，GQA 模型的注意力强度更高，收益会小一些。反过来，它的收益依赖大批量：LongSpec（2025-02）在单批（batch = 1）设置下测得 \(\gamma\ge 3\) 时 MagicDec 约 0.7 倍，小批量时草稿开销占了上风。“投机解码在大批量下没用”这句话，只在短上下文时成立。

排队：为什么不能把 GPU 跑满

到这里算的都是“一台服务器每秒最多处理多少”。可请求不是按节拍到达的：某一秒来了 6 个，下一秒 1 个也没有。上文的服务器在批上限 64 时每秒最多处理约 3.5 个请求，那么每秒来 3 个时，延迟会怎样？

先说清楚“延迟达标”指什么。服务方会给两个延迟各定一个目标，例如“90% 的请求首 token 不超过 2 秒、每 token 不超过 30 毫秒”（阶跃星辰的 Step-3 按 TPOT ≤ 50 毫秒设计），这叫服务等级目标（service level objective，SLO）。只把达标的请求算进吞吐，就是有效吞吐（goodput）：

\[ \text{有效吞吐}(\lambda) = \lambda\cdot\Pr\big[\,\text{TTFT}\le \htmlClass{sym-T1}{T_1}\ \text{且}\ \text{TPOT}\le \htmlClass{sym-T2}{T_2}\,\big] \] DistServe（2024）把“能保证 90% 请求达标的最大到达率”作为衡量一个部署的指标
每秒来的请求里，首 token 延迟和每 token 间隔都达标的那些，才算数。
\(T_1\)
首 token 延迟的上限，例如 2 秒
\(T_2\)
每 token 间隔的上限，例如 30 毫秒
下面的演示里：每秒来 4 个请求，其中 51% 达标，有效吞吐 2.0 个/秒，比每秒来 3.5 个、99% 达标时的 3.47 个/秒还低。过了拐点，多接请求反而让达标的请求变少。

系统的目标是在满足 SLO 的前提下，让有效吞吐尽量高。要知道离拐点有多远，需要两个最基本的排队论结论。第一个是利特尔定律（Little's law, 1961）：

\[ \htmlClass{sym-Nb}{\bar N} = \htmlClass{sym-lam}{\lambda}\,\htmlClass{sym-T}{\bar T} \] 对任何稳定的系统都成立，与到达和服务时间的分布无关（指按时间平均）
系统里平均有多少个请求，等于每秒来几个乘以每个平均待多久。
\(\bar N\)
系统里（排队 + 正在处理）的平均请求数，按时间平均
\(\lambda\)
到达率：每秒到达的请求数
\(\bar T\)
每个请求在系统里的平均停留时间
每秒来 3 个请求，每个请求在系统里待约 9 秒（上文 64 人一批时的数）：平均要有 \(3\times 9 = 27\) 个请求同时在服务。

它最有用的读法是：\(\lambda\bar T\) 就是需要的并发数。拿它和批上限、显存墙 \(B_{\max}\) 比，就知道在多大的到达率下会撞墙：并发需求超过 64（批上限）或 273（显存墙），新请求就只能排队。

第二个回答“负载接近容量时会怎样”。最简化的模型是 M/M/1 队列：请求随机到达（泊松过程），服务时间随机（指数分布），一个服务台，先到先服务。到达率与最大服务率之比叫负载率 \(\rho\)：

\[ \htmlClass{sym-rho}{\rho} = \frac{\lambda}{\htmlClass{sym-mu}{\mu}},\qquad \bar T = \frac{\htmlClass{sym-S}{S}}{1 - \rho},\qquad \htmlClass{sym-Wq}{W_q} = \bar T - S = \frac{\rho\,S}{1 - \rho} \] ρ = 0.5 时停留时间是服务时间的 2 倍，ρ = 0.9 时 10 倍，ρ = 0.99 时 100 倍

套到上文的服务器要小心：\(S\approx 0.29\) 秒（\(\mu\approx 3.5\)/秒）是每个请求占用整台服务器的时间，不是它的延迟；请求本身要待约 9 秒（预填充 0.15 秒加 1000 步解码）。M/M/1 只能描述“排队等着开始”那一段：\(\lambda = 1.75\)（\(\rho = 0.5\)）时 \(W_q\approx 0.29\) 秒，\(\lambda = 3.15\)（\(\rho = 0.9\)）时 2.6 秒，\(\lambda = 3.4\)（\(\rho = 0.97\)）时 9.7 秒，加在约 9 秒之上。负载只多了 8%，排队时间涨了近 4 倍。

所以服务不能按“平均负载 = 容量”来配机器，否则任何一点波动都会让队列失控。M/M/1 只是最简化的单服务台：连续批处理让很多请求同时推进，服务能力还随批变化，真实的曲线形状要看模拟。下面的演示把上文的服务器放进一个模拟里：请求随机到达，调度器做连续批处理，每一步的时间按前面的公式计算。默认的调度是“预填充优先”：新请求一进批，先把它的整段提示算完，这期间正在解码的人全部停下。图里的 p90 指 90% 的请求不超过的值。拖动到达率，看两种延迟和有效吞吐怎样变化。

演示里有两种不同的“变慢”。批没满时，负载上升表现为每 token 间隔缓慢变长：每个请求的平均停留时间在 \(\lambda = 1.75\)、3.15、3.4 时是 7.6、12.3、13.6 秒，比 M/M/1 的估计平缓，增长主要来自间隔变长（同时解码的人多了，插进来的预填充也多了），而不是排队，此时首 token 延迟的 p90 还在 0.6 秒以内。批满了（触到批上限或显存墙），新请求才真正开始排队，首 token 延迟在很窄的负载范围内从零点几秒涨到几秒、十几秒：\(\lambda = 3.5\) 时 p90 是 0.6 秒，4 时 4.4 秒，4.5 时 12 秒。统计栏里的并发数是按时间平均的：\(\lambda = 3\) 时每个请求平均待约 12 秒，系统里平均约 33 个请求，与利特尔定律的 \(3\times 11.7\approx 35\) 大致相符（模拟只有 400 个请求，有限窗口有几个百分点的误差）。线上服务因此按 SLO 而不是按峰值吞吐配机器，过载时宁可拒绝一部分请求，也不让所有人一起超时。

M/M/1 的平均停留时间，以及连续批处理为什么更像“处理器共享”

设定。请求按泊松过程到达（平均每秒 \(\lambda\) 个，彼此独立），服务时间服从均值 \(1/\mu\) 的指数分布，一个服务台，先到先服务。用“系统里有几个请求” \(k\) 描述状态，\(\pi_k\) 是稳态下处于状态 \(k\) 的概率。

第 1 步，平衡方程。稳态下，从 \(k\) 跳到 \(k+1\)（来了一个）的频率，等于从 \(k+1\) 跳回 \(k\)（走了一个）的频率：\(\lambda\pi_k = \mu\pi_{k+1}\)。所以 \(\pi_{k+1} = \rho\,\pi_k\)，\(\pi_k = \pi_0\rho^k\)。

第 2 步，归一化。\(\sum_k\pi_k = \pi_0/(1-\rho) = 1\)，这要求 \(\rho < 1\)。得 \(\pi_k = (1-\rho)\rho^k\)：系统里的请求数服从几何分布。\(\rho = 0.9\) 时，有 20 个以上请求积压的概率是 \(0.9^{20}\approx 12\%\)。

第 3 步，平均人数。\(\bar N = \sum_k k(1-\rho)\rho^k = \rho/(1-\rho)\)。

第 4 步，代入利特尔定律。\(\bar T = \bar N/\lambda = \dfrac{\rho}{\lambda(1-\rho)} = \dfrac{1}{\mu-\lambda} = \dfrac{S}{1-\rho}\)。

连续批处理不是先到先服务。批里的请求同时推进，服务能力在所有在场的请求之间平分，更接近“处理器共享”（processor sharing）。M/G/1 处理器共享队列有一个漂亮的结论：平均停留时间仍是 \(S/(1-\rho)\)，而且与服务时间的分布无关。区别在表现形式：先到先服务时，变长的是“等着开始”，对应首 token 延迟；处理器共享时，变长的是“每一步”，对应每 token 间隔。真实系统两者都有：批没满时像处理器共享，批满了就像先到先服务。批处理还让服务能力随批增大，\(\mu\) 不是常数，所以演示里的曲线比 \(1/(1-\rho)\) 平缓，但拐点依然存在。

这个推导告诉我们：\(1/(1-\rho)\) 的发散不是哪个系统的缺陷，而是随机到达本身的性质：到达有波动，服务台总有一阵子来不及处理，负载越接近 1，这些积压越难消化。要稳定满足 SLO，就必须留余量。

预填充与解码：先分块，再分开

回到第七站的账：预填充占了服务器一半的时间，而且它和解码的脾气相反，一个吃算力，一个吃带宽，混在一起会互相干扰。最直接的是“卡顿”：一个 4000 token 的新请求做预填充要 0.15 秒，这期间批里正在解码的 64 个用户全部停下，每人卡了相当于 17 个 token 的时间。DistServe 团队 2025 年的回顾写道，单个长提示能把每 token 间隔放大 2 到 30 倍。

第一种办法是分块预填充（chunked prefill）：把长提示切成几百到几千 token 的块，每一步只做一块，和正在解码的请求拼在同一步里（Sarathi, 2023；Sarathi-Serve, 2024；DeepSpeed-FastGen 同期独立提出，叫 Dynamic SplitFuse）。它利用的是解码步留下的空闲算力：上文 64 人一批、每步 8.8 毫秒的例子里，按峰值算力每步可以免费带上约 420 个预填充 token（推导见下面的折叠），一个 4000 token 的提示在 10 到 20 步（0.1 到 0.2 秒）里顺带算完，正在解码的人几乎感觉不到。「排队」一节的演示里把调度换成“分块预填充”，就能看到 90% 达标的最大到达率从 3.5 提高到 4。Sarathi-Serve 报告，与 vLLM 相比，同样满足延迟要求时，Mistral-7B 在单张 A100 上的服务能力提高 2.6 倍，Falcon-180B 最多 5.6 倍。现在它是 vLLM 和 SGLang 的默认调度方式。

分块预填充能免费塞进多少 token

解码步带宽受限时，算力有空闲。批里有 \(B\) 个解码 token，再塞进 \(m_{\text{预}}\) 个预填充 token：读的字节不变（权重 + 已有的 KV），计算多了 \(2Nm_{\text{预}}\)。只要总计算时间不超过读数据的时间，这一步就不会变慢：

\[ \frac{2N(B + m_{\text{预}})}{P}\le\frac{W + B\bar n\kappa}{\text{BW}}\quad\Longrightarrow\quad B + m_{\text{预}}\le B^\ast\Big(1 + \frac{B\bar n\kappa}{W}\Big) \]

（右边用了 \(W = Nb\) 和 \(B^\ast = Pb/(2\,\text{BW})\)。）上文的例子：\(B = 64\)，KV 94 GB、权重 141 GB，BF16 的 \(B^\ast = 295\)，右边 \(= 295\times 1.67\approx 492\)，每步可以免费带上约 420 个预填充 token（按峰值算力；实际效率打折后约一半）。一个 4000 token 的提示分成 10 到 20 块，在 10 到 20 个解码步（0.1 到 0.2 秒）里顺带算完，正在解码的用户几乎感觉不到。

每步的 token 总预算是调参的旋钮。预算大，吞吐高，但每 token 间隔的波动大；预算小，间隔稳定，但长提示要拆成更多块，每一块都要把前面各块的 KV 再读一遍。

这个推导告诉我们：分块预填充不只是“把预填充切碎”，它把预填充的计算填进解码留下的算力空隙里：最合适的块大小，正是把每一步推到拐点附近的那个大小。

分块缓解了卡顿，但两类负载仍在同一批 GPU 上、用同一种并行方式，只能按其中一类来优化。第二种办法是彻底分开：预填充与解码分离（P/D 分离；DistServe、Splitwise, 2024）。预填充和解码放在不同的 GPU 池，预填充池算完 KV，经高速网络传给解码池。两个池可以分别扩容、分别选并行方式，甚至用不同的硬件：Splitwise 指出解码不需要最新 GPU 的算力，可以用更便宜、更省电的卡。DistServe 报告，同样保证 90% 请求达标，能承受的请求率比 vLLM 高 2.0–4.6 倍（ShareGPT 负载）。

代价是传 KV。传输时间 \(t_{\text{传}} = n\kappa/\text{BW}_{\text{网}}\)，预填充时间 \(t_{\text{预}}\approx 2Nn/(Pu)\)（\(u\) 是算力利用率，这里按 50%），两者都与 \(n\) 成正比，所以只要比较每个 token：上文的例子里每 token 的 KV 是 328 KB，经一块 400 Gb/s（50 GB/s）的网卡约 6.6 微秒，而每 token 的预填充约 36 微秒。传输比计算快 5 倍，还可以逐层边算边传。MLA 模型的 KV 小几倍，传输更不成问题；KV 越大、网络越慢，分离越不划算。

支持
两类负载特性相反，分开后各自可以用最合适的批大小和并行方式，互不打扰，长提示不再拖慢正在解码的用户。Mooncake、DistServe 报告了数倍的有效吞吐提升；AMD 在 vLLM 博客（2026-04）报告，单台 8×MI300X 上跑 Qwen3-235B-A22B，4 卡做预填充、4 卡做解码，在其测试负载下（输入 2000、输出 1000 token，每秒 8 个请求）达标请求是两个普通 4 卡实例的约 2.5 倍（100 个请求中 73 对 30）。
反对

分离之后，KV 缓存从“显存里的临时数据”变成了要传输、存储、调度的对象。Kimi 的 Mooncake（2024-07，FAST 2025 最佳论文）把这一点推到底：以 KV 缓存为中心设计整个系统，利用 GPU 集群里闲置的 CPU 内存和 SSD 组成分布式的 KV 池，调度器按“哪里有这个请求的前缀 KV”来分配预填充，用更多存储换更少计算。论文报告在真实负载下让 Kimi 多处理了 75% 的请求。

MoE 的大规模部署：宽专家并行与注意力–FFN 分离

前面的账都按稠密模型算：每个 token 用到全部权重。2025–26 年被大规模服务的前沿模型多是 MoE，账要改两处。第一，每个 token 只走 \(E\) 个专家里的 \(k\) 个，一步里 \(B\) 个 token 平均只给每个专家 \(Bk/E\) 个；要让每个专家的矩阵乘法达到稠密模型批为 \(B\) 时的强度，总批得放大 \(E/k\) 倍（第 章）。DeepSeek-V3 是 \(E = 256\)、\(k = 8\)，放大 32 倍：按 295 算，一步要凑约 9400 个 token，也就是约 9400 个同时在解码的请求。第二，批一大几乎所有专家都会被用到，671B 的权重必须全部常驻显存，FP8 也要约 671 GB，一台 8 卡服务器（640 GB）连权重都放不下，更别说 9400 个请求的 KV（每人 5000 token、按 V3 每 token 约 70 KB 的 MLA 缓存算，约 3.3 TB）。

宽专家并行（wide expert parallelism，wide EP）就是对这笔账的回答：用专家并行把专家摊到几十到上百张卡上，每张卡只放少数几个专家。权重在每张卡上只占一小块，剩下的显存全给 KV，这正是 \(B_{\max}\) 公式里 \(W\) 变小的效果；所有卡的 token 加起来，每个专家又能分到足够多的 token。注意力层不一样：它读的 KV 是每个请求私有的，没法摊，所以注意力用数据并行，每张卡各管自己那批请求的注意力。到了每个 MoE 层，token 要经两次全对全通信送到专家所在的卡、再取回来（DeepSeek 开源的 DeepEP 就是做这件事的通信库）。代价就是这笔通信：跨机做专家并行时，通信时间可以是计算的数倍，这是 NVL72 这类大 NVLink 域对 MoE 推理格外有用的原因（第 章「互连」）。

DeepSeek 给过两组数字，口径不同，要分开看。V3 技术报告（2024-12）写的是最小部署单元：预填充 4 个节点 32 张卡（专家并行 32 路）；解码 40 个节点 320 张卡，每张卡只放 1 个专家，其中 64 张卡放冗余专家和共享专家。2025-03 公开的线上部署则是：预填充仍是 4 个节点、专家并行 32 路；解码用 18 个节点、144 路，每张卡放 2 个路由专家。按 V3 的结构估算，2 个路由专家在 58 个 MoE 层里合计约 51 亿参数，加上注意力和共享专家等约 170 亿，FP8 下每张卡的权重约 22 GB，80 GB 显存的大半留给了 KV。开源框架随后跟上：SGLang 在 96 张 H100 上做到每节点每秒 2.23 万输出 token（2025-05），vLLM 报告每张 H200 每秒约 2200 个解码 token（2025-12）。

再往前一步是注意力与 FFN 分离（attention–FFN disaggregation，AFD）。P/D 分离按时间切开一个请求，AFD 按层切开一个模型：注意力层（吃每个请求自己的 KV，要显存容量和带宽）放在一组卡上，FFN 和专家层（吃所有人共用的权重）放在另一组卡上。一组 FFN 卡可以汇集许多组注意力卡送来的 token，凑出宽专家并行要的大批：这是本章“权重能摊、KV 不能”在系统层面的直接应用。两组之间每层都要交换一次激活，所以把一批切成几个微批次交替流动：注意力组算第二个微批次时，FFN 组在算第一个，谁也不必等谁。字节的 MegaScale-Infer（2025-04）和阶跃星辰的 Step-3（2025-07）先后采用，后者把模型结构和这种部署一起设计；DistServe 团队称它是 P/D 分离之后“自然的下一步”，对稠密模型的收益还不明确。在 GPU 集群里，汇成大批的 FFN 一侧通常是计算受限；在小批、低延迟的部署里，FFN 每步都要把权重读一遍，瓶颈变成带宽，这是 NVIDIA 把它搬到 SRAM 芯片上的原因（第 章的 LPX）。

2026 年其余几条线索，本章只点到为止。KV 缓存分层存储：GPU 显存 → CPU 内存 → SSD 与分布式存储，前缀命中时直接取回而不重算，配合 KV 感知路由；Dynamo（2026-03 发布 1.0）、llm-d、LMCache 都在做这一层，NVIDIA 2026-01 还为 KV 缓存推出了专门的存储平台 CMX。超节点把专家并行的通信域扩大到整个机柜（第 章），Kimi K3 官方建议的部署就是不少于 64 张加速卡的超节点。硬件也按阶段分工：NVIDIA 2025-09 发布专做长上下文预填充的 Rubin CPX，2026-03 的 GTC 上又发布承担解码的 Groq 3 LPX 机柜，并表示暂停 CPX、先把精力放在用 LPU 做解码上；据报道，郭明錤 2026-08 底称 CPX 将改用 HBM4 重新设计、2027 年一季度投产，NVIDIA 未确认。低精度推理（Blackwell 原生 FP4，Hopper 上的 4 位权重反量化 W4A16）见第 章。

这些架构有一条共同的线索：把一个请求、一个模型按“吃什么资源”拆开，每一块放到最合适的硬件上，再用网络和调度把它们拼回去。代价是系统越来越复杂，最优配置强烈依赖模型结构和流量。

每 GPU 小时 2 美元，每张卡每秒产出 3000 个输出 token：\(2/(3000\times 3600)\times 10^6\approx 0.19\) 美元 / 百万 token。上文的 8 卡服务器（每小时 16 美元）：只算解码时，只服务 1 个人约 24 美元 / 百万输出 token；64 人一批约 0.61 美元；装满 273 人约 0.33 美元。把每个请求 0.15 秒的预填充也摊进 1000 个输出 token（第七站的对账），64 人一批约 1.3 美元（每个请求 0.13 美分），273 人约 1.0 美元：批开大了只便宜两成多，不是一半。

输入为什么比输出便宜，本章自己的数字就能说明：预填充每个 token 占用整台服务器约 36 微秒；解码每个输出 token 约 137 微秒（64 人一批，8.8 毫秒 ÷ 64）到 74 微秒（273 人）。两者之比 1:2 到 1:4，和各家 API 输入价是输出价几分之一的定价大致吻合；命中前缀缓存的输入几乎不需要计算，再便宜一个数量级。

DeepSeek 在 2025 年 3 月公开过其推理服务的一天：平均约 226 个节点（每节点 8 张 H800），日成本约 8.7 万美元；每个节点每秒约处理 7.4 万个输入 token（含缓存命中）或产出 1.5 万个输出 token；每个用户看到的输出速度只有每秒 20–22 个 token，说明他们把批开得很大、用速度换成本。若全部按 R1 的价格计费，理论日收入约 56 万美元，理论利润率 545%（实际收入低得多，因为有免费服务、夜间折扣和更便宜的 V3）。这说明在大规模、高并发、优化到位的条件下，推理可以有很高的毛利。

推理越来越便宜，AI 的总成本会下降吗

便宜派
同等能力的推理价格大约每年下降一个数量级（a16z 称之为“LLMflation”，Epoch AI 2025-03 的分析测得，不同能力门槛下每年下降 9 倍到 900 倍不等）：硬件更快、模型更小、量化和系统优化层层叠加。
反方
单价下降，用量涨得更快：推理模型每个问题要想几千上万 token，智能体一个任务要跑上百轮，每次都带着几十万 token 的上下文。用户总是用更强、更贵的前沿模型，而不是用便宜下来的旧模型。这是经典的杰文斯悖论：效率提高反而增加总消耗。
现在怎么看
两者同时成立：每个 token 的价格在快速下降，而 token 的消耗量在更快地增长，AI 的总算力支出仍在上升（第 章）。对使用者而言，前缀缓存命中率、思考预算和模型选择，比单价更影响账单。

常见误解

  • 投机解码会降低输出质量。标准的接受规则保证输出分布与大模型完全相同；草稿差只会变慢，不会变差。
  • 批处理只提高吞吐，不影响单个用户。批越大，每步要读的 KV 越多，步长随之变长（仍是访存受限，只是要读的字节多了），用户感到“打字”变慢；批满之后新请求还要排队。服务要在吞吐和延迟之间取舍。
  • 上下文长度只影响显存，不影响速度。每生成一个 token 都要把整段上下文的 KV 读一遍：上下文从 4K 涨到 32K，同样的机器能同时服务的人数和总吞吐都降到约八分之一。本地部署也一样，长对话越聊越慢（第 章）。
  • 输入和输出 token 的成本一样。预填充效率高得多，命中缓存的输入几乎免费，所以输入价格通常是输出的几分之一。
  • GPU 利用率 100% 就是满负荷。系统监控的“利用率”只表示有内核在跑，不表示算力被用满；解码时它可能显示 100%，实际只用到峰值算力的个位数百分比。反过来，按平均负载把服务跑到接近容量，延迟会失控（「排队」一节）。

演进史

2022-07

Orca：调度粒度从“请求”改成“迭代”

卡在哪
FasterTransformer 等系统已有融合内核、KV 缓存和张量并行，但按请求组批：短请求结束后陪着最长的那个空转，新请求要等整批结束。
怎么解决
每个解码步重新组批（连续批处理）；不同位置的请求在线性层拼批，注意力各算各的。
代价
每个请求仍按最大长度预留连续的 KV 显存，\(B_{\max}\) 被碎片压得很小。
引出
瓶颈从调度转到了显存管理。
被淘汰按请求的静态批处理
实现简单，适合所有请求一开始就到齐的离线批量推理。在线服务里请求随时到达、长度差异巨大，它的空转和排队太浪费，2023 年以后的主流框架都换成了迭代级调度。
2023-06

vLLM 的 PagedAttention：像操作系统一样管理 KV

卡在哪
60–80% 的 KV 显存被碎片和过度预留浪费，显存墙很低，而满载吞吐正比于 \(B_{\max}\)。
怎么解决
固定大小的块按需分配、块表映射，浪费率从 \(1-\mathbb E[\ell]/L_{\max}\) 降到每个请求最多半块；同一提示的多个采样共享块。
代价
注意力内核要按块表间接寻址；只有人工指定的共享前缀能复用，任意请求之间的公共前缀仍在重算。
引出
显存不再是最紧的约束，批可以开得很大。同一时期，另一个问题被单独提了出来：连续批处理把新请求的预填充和别人的解码塞进同一步，长提示会让全批停顿。
并行的一条线前缀缓存：算过的不再算
SGLang 的 RadixAttention（2023-12）用基数树索引所有缓存过的序列，自动复用任意请求之间最长的公共前缀，输入成本降到 \((1-\eta) + \eta r\)。它修的是重复计算，和分页、分块是三件并行的事：分页让共享块变得容易，但没有引出它，它也没有引出分块。此后 vLLM 也加了自动前缀缓存，跨机器时再配上 KV 感知路由。
另一条路投机解码：不拼更多人，而是每步多出几个 token
投机解码（2022-11）、Medusa、EAGLE 系列，到 DeepSeek-V3 把多 token 预测头训进模型（2024-12）。它与批处理正交，但两者争夺同一份空闲算力：批越大收益越小，长上下文时又重新划算（见上面的“意外”）。
2023-08 → 2024

分块预填充：把预填充填进解码的算力空隙

卡在哪
连续批处理让新请求的预填充和别人的解码挤进同一批。一个 4000 token 的提示要算 0.15 秒，这期间批里 64 个正在解码的用户全部停下，每 token 间隔的尾部随负载急剧变差。
怎么解决
Sarathi（2023-08）与 Sarathi-Serve（2024）把提示切块、与解码拼在同一步，每步 token 预算约为 \(B^\ast(1 + B\bar n\kappa/W)\)，不中断正在进行的解码。
代价
首 token 延迟略增；两类负载仍挤在同一批 GPU、同一种并行方式上。
引出
能不能把两类负载彻底分开，各自优化？
同类DeepSpeed-FastGen 的 Dynamic SplitFuse
DeepSpeed 团队 2023-11 独立提出同样的思路：拆开长提示、合并短提示，让每一步的 token 数大致恒定。结论一致：调度的核心变量是每一步的 token 预算，而不是批里有几个请求。
2024

P/D 分离与以 KV 为中心的架构

卡在哪
同一批卡、同一种并行方式无法同时适合吃算力的预填充和吃带宽的解码；两个 SLO 互相牵制，只能一起多配机器。
怎么解决
DistServe、Splitwise 把两者放进不同的 GPU 池，KV 经网络传输（每 token 的传输时间远小于预填充时间）；Mooncake 再用 CPU 内存和 SSD 组成分布式 KV 池，按 KV 的位置调度。
代价
要高速网络；两个池的配比要随流量调整；系统复杂度大增。
引出
KV 成了要存储、传输、路由的一等公民。
争论分离还是分块
一方认为中小规模部署里分块已消除大部分干扰，分离只增加复杂度；另一方认为只有分开才能让两类负载各选并行方式和硬件。到 2025 年主流框架都支持分离，而分块仍是单机的默认做法。
2025–2026

宽专家并行与注意力–FFN 分离：把 MoE 摊开

卡在哪
数千亿到万亿参数的 MoE 要把批放大 \(E/k\) 倍才摊得薄专家的权重，所有专家又必须常驻；一台 8 卡服务器既放不下，也凑不出这么大的批。
怎么解决
宽专家并行把专家摊到上百张卡，注意力用数据并行，专家层用全对全通信（DeepSeek 2025-03 公开的解码部署是 18 个节点、144 路）；注意力与 FFN 分离把两类层放到不同的卡上，用微批次交替流动。
代价
通信成为瓶颈，需要大的 NVLink 域；模型、内核、网络、调度深度耦合，换任何一环都要重新调优。
引出
服务之外，训练这些模型需要怎样的系统？（第 章）
分支KV 分层存储与按阶段专门化的硬件
同一时期，KV 缓存从显存扩展到 CPU 内存、SSD 和专门的存储平台（Dynamo、llm-d、LMCache、NVIDIA CMX），配合 KV 感知路由提高前缀命中率；硬件也开始按预填充、解码分工（Rubin CPX、Groq 3 LPX、昇腾 950 的两款）。这两条线和宽专家并行互相配合，但各有各的动机。

自测

1. 动手算：8×H100 跑 70B（BF16 权重 141 GB，KV 预算约 449 GB，每 token KV 约 328 KB，合计带宽 26.8 TB/s）。每个请求的上下文 32K（32768 token）时最多同时服务多少个？满载时每步约多久、整台每秒多少 token？按每卡每小时 2 美元、只算解码，每百万输出 token 多少钱？KV 改存 FP8 呢？
每个请求 \(32768\times 327680\approx 10.7\) GB，最多 \(\lfloor 449/10.7\rfloor = 41\) 个。每步读 \(141 + 41\times 10.7\approx 581\) GB，约 21.7 毫秒，整台每秒约 \(41/0.0217\approx 1890\) token，每人约 46 token/s；成本 \(16/(1890\times 3600)\times 10^6\approx 2.35\) 美元 / 百万 token。FP8：每个请求 5.4 GB，83 个，每步仍约 22 毫秒，吞吐约 3800 token/s，成本减半到约 1.17 美元；每个人的速度不变。对比 5K 上下文时 273 个并发、0.33 美元，长上下文让同一台机器贵了约 7 倍。
2. 一个服务每秒最多处理 4 个请求。按 M/M/1 估算，到达率从每秒 2 个涨到 3.6 个，平均停留时间变成原来的几倍？系统里平均有几个请求？
\(S = 0.25\) 秒。\(\lambda = 2\)：\(\rho = 0.5\)，\(\bar T = 0.25/0.5 = 0.5\) 秒，由利特尔定律 \(\bar N = 2\times 0.5 = 1\)。\(\lambda = 3.6\)：\(\rho = 0.9\)，\(\bar T = 0.25/0.1 = 2.5\) 秒，\(\bar N = 9\)。负载涨了 80%，延迟涨了 5 倍，系统里的请求数涨了 9 倍。
3. 草稿接受率 \(\alpha = 0.6\)，每轮猜 \(\gamma = 3\) 个，草稿成本 \(c = 0.1\)。每轮期望产出多少 token？加速比约多少？如果批里有 100 个请求、跑在 \(B^\ast = 295\) 的芯片上，还能指望这个加速比吗？
\((1 - 0.6^4)/0.4 = (1 - 0.1296)/0.4\approx 2.18\)；加速比 \(2.18/(1 + 0.3)\approx 1.67\) 倍。批 100 时一轮验证要算 \(100\times 4 = 400\) 个位置，超过拐点 295，验证不再免费。按「投机解码」第二个折叠的公式（只看权重），要再乘 \(\max(1, 100/295)/\max(1, 400/295) = 295/400\approx 0.74\)，加速比降到约 1.2 倍。除非上下文很长、每步主要在读 KV：那时一步的读取时间变长，能免费塞进去的计算也变多，验证又重新接近免费。
