本地与端侧部署：给定一台设备，能跑什么、跑多快

16 GB 的 Mac 能跑多大的模型？12 GB 的显卡能不能放下 27B？手机上为什么只有 3B 左右的模型，而且跑几分钟就变慢？这一章用三台常见的机器把内存、带宽、算力三道约束算一遍，给出一套拿到任何设备都能用的估算方法，再用它解释专家卸载、投机解码、低比特取舍和手机降频。

第五部分前面几章讲的是数据中心：上万张卡、几百个用户拼一批。本地部署是另一个极端：通常只有一个用户，批大小为 1，内存和带宽都有限，而且要和操作系统、其他程序共享。决定能不能跑、跑多快的，几乎全是第 章的访存和第 章的位数。

从零开始：在一台 16 GB 的设备上跑一个模型

这一节不讲新算法，只做算术。用三台常见的设备和一个 8B 模型，一步步算出“装不装得下、每秒生成几个 token、读一段提示要多久”。四笔账归成三道约束：装得下（权重 + KV）、生成多快（带宽）、读提示多久（算力）。后面每一节，都是在改这里某个式子的某一项。

贯穿全章的例子：三台设备、一个模型

设备 A 是一张 16 GB 显存的消费级显卡（RTX 5060 Ti 16 GB 这一档，2025-04），设备 B 是一台 16 GB 统一内存的 M3 MacBook，设备 C 是最常见的一种机器：没有独立显卡、只有 CPU（或核显）的笔记本，配 32 GB 双通道 DDR5。模型是一个 8B 稠密模型，结构按 Llama 3.1 8B：32 层，每层 8 个 KV 头、头维度 128，共约 80.3 亿参数。描述一台设备只要三个数：

  • 容量：能放模型的内存有多大。显卡就是显存；Mac 的 CPU 和 GPU 共用一块内存，macOS 默认只允许 GPU 用其中约三分之二到四分之三，16 GB 的机器约 11 GB（可以用系统参数调高，但系统会开始换页）；只有 CPU 的机器，是内存减去系统和浏览器占掉的 4–6 GB。
  • 带宽：每秒能从内存读出多少字节。A 是 448 GB/s，B 是 100 GB/s，C 的双通道 DDR5 约 90–96 GB/s。
  • 算力：每秒能做多少次运算。规格表上的峰值意义不大，下面直接用 llama.cpp 公开跑分折算的“有效算力”。

第一笔账：权重要多少字节

每个参数存成若干位。每权重位数（bpw，含缩放因子等开销）乘以参数量、再除以 8，就是权重的字节数：

  • BF16（16 位）：\(8.03\times 10^9\times 2\approx 16.1\) GB。A 放不下（还要留 KV 和缓冲区），B 更放不下；C 放得下，但下面会看到它慢得没法用。
  • Q8_0（8.5 bpw）：8.5 GB。A 放得下；B 放下之后只剩约 2 GB。
  • Q4_K_M（约 4.9 bpw）：4.9 GB（实际文件 4.92 GB）。三台都放得下，这是本地部署的默认选择。

加上下一小节要算的 KV 缓存和运行时缓冲区，就是第一本账：

第二笔账：KV 缓存随上下文线性增长

生成时，每个已经读过的 token 在每一层都留下一对 K、V 向量，这就是 KV 缓存。每个 token 占 \(\kappa = 2Lh_{kv}d_hb_{\text{KV}}\) 字节（第 章，\(b_{\text{KV}}\) 是每个数的字节数）：

\[ \kappa = 2\times 32\times 8\times 128\times 2\ \text{字节} = 131{,}072\ \text{字节}\approx 0.13\ \text{MB} \] 乘 2 是因为 K 和 V 各一份；最后的 2 是 FP16 每个数 2 字节

每个 token 只有 0.13 MB，但它要乘上下文长度：

设备 A 放下 4.9 GB 权重和 1 GB 缓冲区后还剩约 10 GB，FP16 的 KV 能撑到约 7.7 万 token；KV 改存 Q8_0，模型支持的 128K 全部用上也只要 9.1 GB。设备 B 只剩约 5.5 GB：FP16 约 4.2 万 token，要用满 128K 得用 Q4_0。设备 C 内存大，FP16 也能用满 128K，它的问题在速度（下一小节）。

表里后两列用的是 KV 量化：把缓存里的 K、V 也存成 8 位或 4 位，读出来参与注意力时再还原。它和权重量化是两回事：权重是训练好就固定的，可以离线慢慢挑缩放因子；KV 是推理时边生成边写入的激活，只能在线、按小块量化。难点在 K：它有几个通道的数值一直偏大（通道方向的离群值），而 llama.cpp 的 Q8_0、Q4_0 是沿每个 token 的向量分块取缩放因子，离群通道会把同块其他数的精度挤掉；V 没有这个问题。所以论文里的做法是 K 按通道、V 按 token 分别量化（KIVI、KVQuant，2024），本地常见的折中是 K 留 8 位、V 降到 4 位。效果上，Q8_0 的 KV 在困惑度上几乎与 FP16 没有差别；Q4_0 据报道困惑度高约 0.5–1%，社区也报告过长上下文检索掉点。代价有两项：还原要额外计算，长上下文时生成可能反而比 FP16 慢一些（据报道）；llama.cpp 里量化 V 缓存需要同时打开 FlashAttention。

不同模型的 \(\kappa\) 差别很大，取决于层数和 KV 头数：同样 8 个 KV 头，32 层的 8B 是 0.13 MB，64 层的 Qwen3-32B 是 0.26 MB；混合了线性注意力的模型只有少数层随上下文存 KV，长上下文便宜得多。

第三笔账：每秒能生成几个 token

解码一次只产出一个 token。为了这一个 token，每一层的每个权重矩阵都要和当前向量乘一遍：每个权重从内存读出来，只做一次乘加就用完了，也没有别的 token 来分摊这次读取（数据中心靠拼批分摊，第 章）。另外还要把前面所有 token 的 KV 读一遍。所以生成一个 token 的时间，下限是“这一步要读的字节 ÷ 带宽”。实际能用到的带宽与规格带宽之比，叫带宽利用率 \(\eta\)：

\[ \text{token/s} \approx \frac{\htmlClass{sym-eta}{\eta}\cdot\htmlClass{sym-BW}{\text{BW}}}{\htmlClass{sym-W}{W_{\text{激活}}} + \htmlClass{sym-n}{n}\,\htmlClass{sym-k}{\kappa}} \]
分母是生成一个 token 要读的字节：激活的那部分权重，加上整段上下文的 KV。分子是实际能用到的带宽。公式里没有算力：单用户解码时，算力大部分时间在等数据（下一节）。

带宽利用率。llama.cpp 跑分里显卡多在 65–85%，Mac 在 40–85%（芯片越大越难用满）
BW
规格带宽，字节 / 秒
\(W_{\text{激活}}\)
每个 token 要读的权重字节：激活参数 × bpw / 8。嵌入表每次只查一行，不计
\(n\)
当前上下文长度
\(\kappa\)
每个 token 的 KV 字节数
8B 的 Q4_K_M 每个 token 读约 4.6 GB 权重（4.9 GB 减去只查一行的嵌入表约 0.3 GB）。设备 A：上下文很短时 \(357/4.6\approx 78\) token/s；8K 时 \(357/(4.6 + 1.1)\approx 63\)；32K 时 \(357/(4.6 + 4.3)\approx 40\)，慢了一半。设备 B：短上下文 \(82/4.6\approx 18\) token/s，32K 时约 9。设备 C：短上下文 \(58/4.6\approx 13\) token/s，32K 时约 6.5。
第 1 步：权重要读多少。每个激活参数读一遍；位数减半，要读的字节减半。
第 2 步：加上 KV。当前 token 要和前面 \(n\) 个 token 做注意力，它们的 K、V 全部读一遍。
第 3 步：除到带宽里。每秒能读多少字节，就能生成多少个“这么多字节”的 token。

\(\eta\) 达不到 1，是因为每生成一个 token 要启动几百个小内核，每个都有固定开销（第 章的“开销受限”），解量化和注意力也要算。上下文越长，KV 在分母里占得越多，这就是“聊得越久越慢”的原因。人读中文大约每秒 5–10 个 token，所以 C 的 13 token/s 还算能用，32K 时就开始跟不上了。

第四笔账：读一段提示要多久

预填充不一样：提示里的几千个 token 可以一起算，一次读出的权重被几千个 token 共用，瓶颈变成算力。每个 token 大约要 \(2N\) 次运算（每个参数一次乘、一次加）：

\[ t_{\text{预填充}} \approx \frac{2\htmlClass{sym-N}{N}\times\htmlClass{sym-L}{n_{\text{提示}}}}{\htmlClass{sym-P}{P_{\text{eff}}}} \]
读入一个长度为 \(n_{\text{提示}}\) 的提示，计算量约 \(2N\) 乘以提示长度，除以设备的有效算力。提示很长时，注意力还要多算一项，随长度的平方增长。
\(N\)
激活参数量（不含嵌入表）
\(n_{\text{提示}}\)
提示的 token 数（文档、代码、智能体的上下文）
\(P_{\text{eff}}\)
有效算力，按读提示的跑分折算，等于峰值乘利用率。注意口径：llama.cpp 读量化模型的提示时多用 INT8 矩阵核，所以折算出的值可以超过 FP16 峰值。RTX 4090 的 FP16 峰值约 165 TFLOPS（FP32 累加），INT8 稠密约 660 TOPS，按跑分折算的有效值约 199 TFLOPS；M3 GPU 的 FP16 峰值约 3.6 TFLOPS，有效约 2.5
8B 模型读一个 8K token 的提示：按不含嵌入表的 75 亿参数算，\(2\times 7.5\times 10^9\times 8192\approx 1.2\times 10^{14}\) FLOPs，注意力再多约 14%，合计约 \(1.4\times 10^{14}\)。设备 A（有效约 55 TFLOPS）约 2.6 秒；设备 B（有效约 2.5 TFLOPS）约 57 秒；设备 C（约 1 TFLOPS）两分多钟。

M3 的生成速度只比 A 慢 4.4 倍，读提示却慢 22 倍。读长文档、跑智能体时，Mac 和 CPU 机器的用户等的主要是首 token 延迟。这也是 Apple 在 M5 的 GPU 里加入矩阵加速单元的原因（下一节）。

这个例子说明三件事。第一，内存是硬墙：差 1 GB 也装不下，要么换更低的位数，要么把一部分放到更慢的内存里（速度断崖式下降，见「MoE 在端侧」一节）。第二，生成速度几乎完全由“带宽 ÷ 每个 token 读的字节”决定：C 的内存是 A 的一倍半，带宽却只有它的六分之一，能装下的大模型都跑不动。第三，读提示由算力决定，Mac、手机和 CPU 在这上面差得最多。C 这类机器最合适的是 MoE：Qwen3-30B-A3B 的 4 位版本（18.6 GB）整块放得进 26 GB，每个 token 却只读约 1.9 GB，下面的计算器给出短上下文约 17 token/s，比它跑 8B 稠密模型还快。

拿到一台机器，按这个顺序算

  1. 可用内存。独立显卡看显存；Mac 取总内存的三分之二到四分之三；只有 CPU 或核显，是内存减去系统和浏览器占的 4–6 GB。
  2. 依次放进去：权重（从 Q4_K_M 起步）、你真要用的上下文的 KV、约 1 GB 缓冲。放不下，先降 KV 的位数，再降权重的位数，再换小模型或 MoE；把稠密模型的层放到更慢的内存里是最后的办法。
  3. 生成速度 ≈ 0.6–0.8 × 带宽 ÷ 每个 token 读的字节。低于每秒 5 个 token，就比阅读速度慢了。
  4. 读提示 ≈ 2N × 提示长度 ÷ 有效算力。常读长文档、跑智能体，而这一项超过一分钟，就换激活参数更少的 MoE 或更小的模型。
  5. 确认运行时支持这个格式（「格式与运行时」一节的意外框）。

上面的 \(\eta\) 和有效算力，都可以在自己的机器上测出来：用 llama.cpp 自带的 llama-bench 跑一次，它报告两个数，生成速度（默认生成 128 个 token）和读提示速度（默认 512 个 token 一批）。前者乘每个 token 读的字节得到实际带宽，后者乘 \(2N\) 得到有效算力，「投机解码」一节的 \(m^\ast\) 是两者之比。

解码的上限：为什么端侧几乎总在等内存

第三笔账用了一个结论：单用户解码只看字节，不看算力。第 章用 Roofline 讲过为什么，第 章也用它解释了量化为什么提速。这里把数字代到三台设备上：解码时每个权重读一次、做一次乘加，算术强度只有 \(16/\text{bpw}\)，Q4_K_M 约 3.3 FLOPs/字节；设备 A 的拐点约 150，M3 约 30，设备 C 约 17。解码的强度只有拐点的几十分之一到五分之一，生成时绝大部分算力在等数据，所以是访存受限，速度只看分母里的字节。

这条结论在四种情况下不成立，后面几节用的正是这些例外：

  • 位数低到解包成了主要开销。低位格式的每个权重要先解包、乘缩放因子，这些整数指令不算在 FLOPs 里，却占用计算单元。llama.cpp 文档里 Llama-3.1-8B 的一组实测：从 Q8_0 到 Q4_K_M，字节少 42%，生成从 51 提到 72 token/s，快 1.4 倍（按字节应为 1.7 倍）；再到 IQ2_XXS，文件又小一半，速度只到 80。PrismML 的三值格式在 H100 和 Blackwell 上，字节更少的那种打包反而更慢。
  • 设备算力本身很弱。CPU 和手机的拐点低，上面这个转折来得更早。
  • 一次算不止一个 token。预填充、投机解码的验证、拼批，都让一次读出的权重服务多个 token，强度按 token 数成倍增长，直到碰上拐点。预填充因此是计算受限的（第四笔账）；投机解码就是利用这段空档（「投机解码」一节）。
  • MoE。强度不变（每个激活参数仍是一次乘加），但专家的矩阵小、还要路由，带宽更难用满：RTX 3090 上 Qwen3-30B-A3B 只用到带宽上限的约 37%。算 MoE 的速度时，\(\eta\) 要打折（计算器里按 0.55 折）。

一个干净的自然实验是 Apple M5 对 M4（2025-10）。M5 的内存带宽从 120 GB/s 提到 153 GB/s（+28%），同时在每个 GPU 核心里加了矩阵加速单元，AI 峰值算力约为 M4 的 4 倍。Apple 用 MLX 测了 6 个模型：生成速度快了 19–27%，跟着带宽走；首 token 时间快了 3.3–4.1 倍，跟着算力走。

推导：单用户解码的算术强度，以及拼批怎样改变它

第 1 步，数运算。生成一个 token，每个激活参数参与一次乘加，共 \(2N_{\text{激活}}\) 次运算。注意力里，当前 query 要和 \(n\) 个历史 token 的 K 做点积、再对 V 加权求和，每层每个 query 头 \(4d_hn\) 次，共 \(4Lh_qd_hn\)。

第 2 步，数字节。权重 \(N_{\text{激活}}\cdot\text{bpw}/8\)；KV \(2Lh_{kv}d_hb_{\text{KV}}\,n\)。

第 3 步，算强度。两部分分开看：

\[ I_{\text{权重}} = \frac{2N_{\text{激活}}}{N_{\text{激活}}\cdot\text{bpw}/8} = \frac{16}{\text{bpw}},\qquad I_{\text{KV}} = \frac{4Lh_qd_hn}{2Lh_{kv}d_hb_{\text{KV}}\,n} = \frac{2G}{b_{\text{KV}}} \]

\(G = h_q/h_{kv}\) 是每个 KV 头被几个 query 头共用（GQA）。Q4_K_M 的 \(I_{\text{权重}}\approx 3.3\)，三值（1.75 bpw）约 9；8B 例子里 \(G = 4\)，FP16 的 KV 强度为 4。都只有个位数。

第 4 步，和拐点比。用「从零开始」的有效值：设备 A 的拐点约 \(55\ \text{TFLOPS}/357\ \text{GB/s}\approx 150\) FLOPs/字节，M3 约 \(2.5/0.082\approx 30\)，设备 C 约 \(1/0.058\approx 17\)。解码的强度是它们的几十分之一到五分之一。

第 5 步，低位格式的例外。位数越低，\(16/\text{bpw}\) 越大，而且解包的整数指令同样占用计算单元。上面那组实测里 IQ2_XXS 写作 2.4 bpw：它名义上是 2.06 bpw，但文件里部分张量（如嵌入和输出层）保留更高位数，整个文件平均在 2.2–2.8 之间。PrismML 有两种三值打包：PTQ1_0 把三值密排，每权重 1.75 bpw；PQ2_0 每个值占 2 位，2.13 bpw（第 章）。PTQ1_0 少读约 17% 的字节，在 RTX 4090、L4 这类 Ada 代显卡上更快，在 H100 和 Blackwell 上反而更慢；PrismML 的解释是那里批大小为 1 的解码已经卡在指令吞吐和内核启动上。

第 6 步，拼批。同时跑 \(B\) 个请求（几个智能体、批量处理文档），一次读权重服务 \(B\) 个 token，\(I_{\text{权重}}\) 变成 \(16B/\text{bpw}\)，总吞吐几乎按 \(B\) 增长；但每个请求的 KV 各读各的，\(I_{\text{KV}}\) 不变，所以上下文长时，KV 先把这份收益吃掉，然后是内存装不下。llama-server 显式指定 4 个并发槽时，总上下文在槽之间平分（64K 每槽 16K）；打开统一的 KV 池（并发槽数自动时默认打开）则所有槽共享一个池。

这个推导告诉我们：端侧单用户解码的强度只有个位数，比常见设备的拐点低几倍到几十倍，所以位数、激活参数、上下文长度都直接写在速度里。只有一次算多个 token（预填充、投机验证、拼批），或者位数低到解包成为主要开销、设备算力很弱时，算力才重新变成瓶颈。

格式与运行时：选什么、在哪里跑

本地部署的工具链变化很快（历史见章末演进史），但每一种技巧动的都是前面四笔账里的一项：

  • 权重字节（\(N\cdot\text{bpw}/8\)）：Q4_0 → K-quants 与 imatrix → 官方 QAT → 三值（第 章）。
  • KV（\(n\kappa\)）：KV 量化、滑动窗口、线性注意力。
  • 容量（\(M_{\text{可用}}\)）：统一内存、MoE 专家卸载、逐层嵌入外置。
  • 每读一遍权重产出的 token 数：拼批、投机解码。
  • 预填充的算力（\(P_{\text{eff}}\)）：M5 的矩阵单元、手机 NPU 做预填充。
  • 兼容性：GGUF 把量化方式、张量布局、分词器和超参数写进一个文件；新格式仍要等运行时支持。

MoE 在端侧：专家放在哪里

MoE 有一个不对称（第 章）：内存要装下全部专家，每个 token 却只读其中几个。在内存小、带宽也小的设备上，这两件事可以分开处理：每个 token 都要用的部分放在最快的内存里，专家放在更大、更慢的内存里。

例子是 Qwen3-30B-A3B（2025-04）：305 亿参数，48 层，每层 128 个专家、每个 token 选 8 个，激活约 33 亿。Q4_K_M 文件 18.6 GB，设备 A 装不下。参数里约 290 亿（95%）是专家，注意力、路由器、嵌入和输出层约 15 亿。每生成一个 token 要读：非专家部分约 0.75 GB，被选中的专家约 1.1 GB。

把放不下的专家放进 CPU 内存，叫专家卸载。llama.cpp 可以按名字把专家张量指定给 CPU（2025 年又加了“前 N 层的专家放 CPU”的快捷选项）：注意力、KV 和路由器留在显卡上，专家留在内存里，由 CPU 直接计算。每生成一个 token 的时间，是每层存储各自花掉的时间之和：

\[ t_{\text{token}} \approx \frac{\htmlClass{sym-Wg}{W_{\text{显存}}}}{\eta\,\htmlClass{sym-Bg}{\text{BW}_{\text{显存}}}} + \frac{\htmlClass{sym-Wr}{W_{\text{内存}}}}{\htmlClass{sym-Br}{\text{BW}_{\text{内存}}}} + \frac{\htmlClass{sym-Ws}{W_{\text{SSD}}}}{\htmlClass{sym-Bs}{\text{BW}_{\text{SSD}}}} \]
每个 token 要读的字节按放在哪里分成三份，各自除以那一层的带宽，再相加。每一层先在显卡上算注意力，再交给 CPU 算专家，两边轮流等，所以是相加而不是取最大值。
\(W_{\text{显存}}\)
每个 token 从显存读的字节：非专家部分、KV、放在显卡上的那部分专家
\(\text{BW}_{\text{显存}}\)
显存带宽。MoE 的小矩阵和路由让利用率更低：RTX 3090 上这个模型 4K 上下文实测约 154 token/s，约为带宽上限的 37%
\(W_{\text{内存}}\)
每个 token 从 CPU 内存读的专家字节
\(\text{BW}_{\text{内存}}\)
双通道 DDR5-6000 理论 96 GB/s，实际按六成计约 58 GB/s
\(W_{\text{SSD}}\)
每个 token 要临时从固态硬盘读入的专家字节
\(\text{BW}_{\text{SSD}}\)
PCIe 4.0 固态硬盘顺序读约 7 GB/s；按专家零散读取更低，下面按约 5 GB/s 计
设备 A 加 32 GB DDR5 内存，8K 上下文，显存利用率按 40%。专家全放内存：显卡部分（0.75 GB 权重 + 0.8 GB KV）约 9 ms，CPU 部分 \(1.1\ \text{GB}/58\ \text{GB/s}\approx 19\) ms，合计约 28 ms，约 36 token/s。用剩下的显存装下约 75% 的专家：显卡 13 ms + CPU 5 ms，约 55 token/s。若只有 16 GB 内存（系统和其他程序占约 6 GB），又一个专家都不放进显存，约 43% 的专家只能留在硬盘上，每个 token 平均要从硬盘读 0.48 GB，按约 5 GB/s 要约 96 ms，速度掉到约 9 token/s；同样 16 GB 内存，先用显存装下 75% 的专家，剩下的约 4.5 GB 放得进内存，硬盘那一段消失，仍有约 55 token/s。

所以专家放哪里的顺序是：先把显存装满，再放内存，硬盘是最后的退路。只要有专家每个 token 都可能要从硬盘读，速度就掉一个数量级；显存装满之后仍有专家落盘，加内存才是最管用的升级。llama.cpp 默认用内存映射（mmap）加载模型：把模型文件直接映射成一段内存地址，用到哪一页，操作系统才从硬盘读哪一页，内存紧张时再把不常用的页丢掉。所以模型比内存大时它也能“跑起来”，但每次缺页都要等硬盘，速度由硬盘决定。

上面算的是生成。读提示时情况反过来：一批几百个 token 一起算，CPU 变成计算受限，llama.cpp 会把内存里的专家经 PCIe 搬到显卡上算。推导的第 2–3 步说明为什么，以及为什么 MoE 的搬运门槛比稠密模型高 \(E/k\) 倍。

推导：专家放在内存里时，为什么生成时让 CPU 算，读提示时却要搬到显卡上

第 1 步，生成（一批 1 个 token）。一块放在内存里的权重有 \(W\) 字节。让 CPU 就地算，时间约 \(W/\text{BW}_{\text{内存}}\)；经 PCIe 搬到显卡再算，时间至少 \(W/\text{BW}_{\text{PCIe}}\)。PCIe 4.0 ×16 理论 32 GB/s、实际约 25 GB/s，比双通道 DDR5 的约 58 GB/s 窄。被选中的 1.1 GB 专家：就地算约 19 ms，搬运约 44 ms。权重只用一次，搬过去不划算。Fiddler（ICLR 2025）的出发点就是这个：让 CPU 算专家，比把专家搬上显卡快。

第 2 步，读提示（一批 \(m\) 个 token）。CPU 的计算量随 \(m\) 线性增长，\(m\) 一大就从访存受限变成计算受限，时间约 \(2N_Wm/P_{\text{cpu}}\)（\(N_W\) 是这块权重的参数量）；搬运的时间与 \(m\) 无关，显卡计算又快得多，可以忽略。两者相等处：

\[ \frac{2N_Wm_\times}{P_{\text{cpu}}} = \frac{W}{\text{BW}_{\text{PCIe}}}\quad\Longrightarrow\quad m_\times = \frac{P_{\text{cpu}}}{2\,\text{BW}_{\text{PCIe}}}\cdot\frac{\text{bpw}}{8} \]

台式机 CPU 跑量化矩阵乘法的有效算力按 1 TFLOPS 量级估，4.9 bpw、25 GB/s：\(m_\times\approx 12\)。llama.cpp 的默认做法与此一致：一批达到 32 个 token（读提示时），就把内存里的权重经 PCIe 搬到显卡上算；生成时留在 CPU 上算。

第 3 步，MoE 要把门槛乘上 \(E/k\)。一批 \(m\) 个 token 分摊到 \(E\) 个专家上，每个专家平均只分到 \(mk/E\) 个 token，CPU 那边每个专家的计算量少了 \(E/k\) 倍；搬运却要把整层的专家都搬过去。所以：

\[ m_\times^{\text{MoE}} \approx \frac{E}{k}\,m_\times \]

Qwen3-30B-A3B 的 \(E/k = 128/8 = 16\)，门槛约 200 个 token。固定的 32 对 MoE 偏低：一批 32 个 token 时，被用到的专家约占 87%（第 章的公式 \(1-(1-k/E)^B\)），CPU 读这些专家约 0.27 秒；搬运却要把 17.7 GB 全部传一遍，约 0.7 秒。llama.cpp 的议题里也有人提出把这个门槛做成可调的。读长提示时，加大一次处理的 token 数（ubatch），让一次搬运分摊给更多 token，是常见的调优建议。

第 4 步，硬盘。固态硬盘比内存慢一个数量级，按页缺页读取时更慢。只要有一部分专家每个 token 都可能要从硬盘读，速度就由这部分决定。缓存能救一部分：最近用过的专家留在内存里。若路由均匀随机，命中率等于缓存能装下的比例；真实路由有偏好，相邻 token 常选相同的专家，命中率更高。Apple 的 LLM in a flash（2023-12）把类似的技巧（只读预测会被激活的行、把要一起读的数据排在一起）用在稠密模型上，跑起了两倍于内存的模型，比直接加载快 4–5 倍（CPU）和 20–25 倍（GPU）。

这个推导告诉我们：卸载后的速度由最慢的那一层存储和它承担的字节决定，而不是由显卡决定。生成时专家放内存、让 CPU 就地算是最优解；读提示时反过来，要把权重搬上显卡，而 MoE 的搬运门槛比稠密模型高 \(E/k\) 倍。只要有专家落到硬盘上，速度就掉一个数量级，所以先用满显存，仍有专家落盘时再加内存。

投机解码：把闲着的算力用起来

第 章的投机解码：草稿先猜 \(\gamma\) 个 token，大模型一次前向并行验证。数据中心里，闲置的算力已经被拼批用掉了，投机解码要和拼批争；端侧通常只有一个用户，批大小多为 1，上一节说过，大部分算力本来就闲着。一次前向能“免费”多算几个位置，可以直接从跑分读出来：

\[ \htmlClass{sym-ms}{m^\ast} \approx \frac{\htmlClass{sym-pp}{v_{\text{读提示}}}}{\htmlClass{sym-tg}{v_{\text{生成}}}} \]
读提示时每秒处理的 token 数，除以生成时每秒产出的 token 数。一次前向里同时算不超过 \(m^\ast\) 个位置，耗时和只算一个位置差不多。
\(m^\ast\)
一次前向能免费多算的位置数，相当于设备的拐点换算成“token 个数”
\(v_{\text{读提示}}\)
预填充速度，token/s（计算受限）
\(v_{\text{生成}}\)
生成速度，token/s（访存受限）
7B 的 4 位版本：设备 A 约 \(4200/93\approx 45\)；RTX 4090 约 \(14800/189\approx 78\)；M3 约 \(187/21\approx 9\)；M4 Pro 约 \(364/50\approx 7\)。显卡上一次验证 4–8 个草稿几乎不花额外时间；Mac 上验证超过 7–9 个位置就不再免费。

所以投机解码在端侧比在数据中心更划算，而能用多长的草稿由设备决定：显卡的 \(m^\ast\) 有几十，Mac 十左右，CPU 只有几个。推导里给出加速比的估算式，并说明为什么端侧偏好挂在大模型上的轻量草稿头，而不是另放一个小模型。

推导：为什么 m* 等于两种速度之比，以及投机解码在哪些设备上划算

第 1 步，一次前向同时算 \(m\) 个位置。权重只读一遍，运算量按 \(m\) 倍增长，时间约为两者中较大的那个：\(t(m)\approx\max\big(W/\text{BW}_{\text{eff}},\ 2Nm/P_{\text{eff}}\big)\)。

第 2 步，用跑分表示。生成是 \(m = 1\)、访存受限：\(v_{\text{生成}} = \text{BW}_{\text{eff}}/W\)。读提示是 \(m\) 很大、计算受限：\(v_{\text{读提示}} = P_{\text{eff}}/(2N)\)。令 \(t(m)\) 的两项相等：

\[ \frac{2Nm^\ast}{P_{\text{eff}}} = \frac{W}{\text{BW}_{\text{eff}}}\quad\Longrightarrow\quad m^\ast = \frac{P_{\text{eff}}/(2N)}{\text{BW}_{\text{eff}}/W} = \frac{v_{\text{读提示}}}{v_{\text{生成}}} \]

跑分里的读提示速度是 512 个一批测的，几个一批时内核效率更低，所以这是偏乐观的估计。

第 3 步，加速比。草稿每个 token 被接受的概率为 \(\alpha\)，每轮期望产出 \(\mathbb E[X] = (1-\alpha^{\gamma+1})/(1-\alpha)\) 个 token（第 章推导过）。代价是一次验证，加上 \(\gamma\) 个草稿 token 的成本 \(\gamma c\)（\(c\) 是一个草稿 token 相对大模型一步的成本）。验证的位置数 \(\gamma + 1\) 不超过 \(m^\ast\) 时，验证约等于一步；超过时约为 \((\gamma+1)/m^\ast\) 步：

\[ S \approx \frac{\mathbb E[X]}{\max\!\big(1,\ (\gamma+1)/m^\ast\big) + \gamma c} \]

\(\alpha = 0.7\)、\(\gamma = 3\)、\(c = 0.05\)：\(\mathbb E[X] = (1 - 0.7^4)/0.3\approx 2.53\)。显卡和 Mac 上 \(4\le m^\ast\)，\(S\approx 2.53/1.15\approx 2.2\)。

第 4 步，算力弱的设备。CPU 的 \(m^\ast\) 往往只有几。设 \(m^\ast = 2\)，同样的设置下验证 4 个位置要约 2 步，\(S\approx 2.53/2.15\approx 1.2\)；如果草稿也在同一颗 CPU 上串行生成，\(c\) 变大，加速可能变成减速。

第 5 步，内存。草稿本身要占内存，每一步也要读它的权重。所以端侧偏好挂在大模型上的轻量草稿头（MTP、EAGLE 一类），它们复用大模型的 KV 和隐藏状态，而不是另外放一个小模型。

这个推导告诉我们：投机解码在端侧更划算，是因为单用户解码闲着的算力本来就浪费掉了；能免费验证的宽度 \(m^\ast\) 就是“读提示速度 ÷ 生成速度”，显卡几十，Mac 十左右，CPU 只有几。设备算力越弱，能用的草稿越短，收益越小。

2026 年的例子：Gemma 4 发布了配套的 多 token 预测草稿模型（2026-05），Google 称最多快 3 倍。草稿是一个 4 层的小 Transformer，直接读主模型的 KV；它的成本 \(c\) 主要花在给 26 万个词打分的输出层上，所以端侧版本 E2B、E4B 的草稿先选 token 簇、再在簇里取 top-k，把这一层缩小约 64 倍。Unsloth 实测 GGUF 版快 1.4–2.2 倍，并提到带宽较低的设备（如老一些的 Mac）收益更小。按上面的推导，关键不是带宽低，而是这类设备的算力相对带宽低：老 Mac 的 \(m^\ast\) 只有 8 左右，显卡有几十。据报道，社区在安卓 CPU 上运行时建议关掉草稿。

以上都按稠密模型算。MoE 不一样：单个 token 只读 \(k/E\) 的专家，验证 \(\gamma+1\) 个位置时，这些 token 各选各的专家，被读到的比例是 \(1-(1-k/E)^{\gamma+1}\)。Qwen3-30B-A3B（\(k/E = 1/16\)）验证 4 个位置，约读到 23% 的专家，是单个 token 的 3.6 倍（假设路由独立；真实路由相邻 token 有重叠，会少一些）。验证不再“只读一遍权重”，专家在 CPU 内存里时，这笔额外字节要由内存带宽来付。所以 MoE 配草稿头的收益常常小于同等激活参数的稠密模型，要用实测来定。

同样的内存：大模型低比特，还是小模型高比特

6 GB 可以放 Q8_0 的 5–6B，也可以放 Q4_K_M 的 10B，或者三值的 27B（Bonsai 2）。先看一件容易漏掉的事：不管装哪一个，每生成一个 token 都要读这 6 GB，所以生成速度几乎一样，都是带宽 ÷ 6 GB。几种选择只在三处不同：

  • 质量：参数少一点，能力差一点（规模定律，第 章）；位数少一点，量化误差大一点（第 章）。
  • 读提示的时间：计算量按 \(2N\) 算，与位数无关，27B 读提示比 9B 慢约 3 倍。
  • KV：模型越大，层数和 KV 头通常越多，同样的上下文占的内存越多。

结论先说：有官方 QAT 版本时，选能放下的最大模型的 QAT 版；只有训练后量化时，4 位左右最好，低于 3 位要专门测推理任务；常读长提示的场景（智能体、长文档）要把预填充时间算进去，大模型低位不一定划算。厂商数据和这个结论一致。PrismML 报告（Qwen3.8-27B，14 个思考模式评测，均为自报）：常规的 IQ2_XXS 只保留 84.1% 的成绩，损失集中在长推理上；它的三值版保留 98.2%，与 5.2 bpw、17.6 GB 的 4 位版（98.7%）只差 0.5 个百分点。三值版表示上是 1.72 bpw，PTQ1_0 文件 1.75 bpw、5.95 GB。IQ2_XXS 的体积 PrismML 两张模型卡写得不一样：GGUF 卡写 2.16 bpw、7.27 GB，MLX 卡写 2.8 bpw、9.4 GB；按 GGUF 卡，三值版的体积约是 IQ2_XXS 的 82%，优势主要在质量而不在体积。

为什么训练后量化停在 4 位、QAT 能推到 2 位以下？两种误差在竞争，可以放进一个玩具模型：

\[ \Delta L(\htmlClass{sym-b}{b}) \approx \underbrace{\htmlClass{sym-A}{A}\Big(\frac{8\htmlClass{sym-M}{M}}{\htmlClass{sym-b}{b}}\Big)^{-\htmlClass{sym-al}{\alpha}}}_{\text{参数少了}} + \underbrace{\htmlClass{sym-c}{c_q}\cdot 4^{-\htmlClass{sym-b}{b}}}_{\text{量化误差}} \]
内存 \(M\) 固定时，位数 \(b\) 越高，能放下的参数 \(N = 8M/b\) 越少，规模定律的参数项越大；位数越低，量化误差越大，而且每少一位大约翻 4 倍。两项相加有一个最低点。

给权重的内存（字节）
\(b\)

\(A\)

\(\alpha\)

\(c_q\)
量化误差的系数：模型对扰动越敏感、取整方法越粗糙，它越大；QAT 让它小得多。这是示意值
位数翻倍（4 → 8），\(N\) 减半，参数项变为 \(2^{0.348}\approx 1.27\) 倍；位数从 4 降到 3，量化项变为 4 倍。高位时少一位几乎白赚，低位时少一位代价陡增。
第 1 步：内存换参数。每个参数 \(b/8\) 字节，\(M\) 字节能放 \(8M/b\) 个参数。
第 2 步：参数项。规模定律里参数不够造成的那部分损失，随 \(b\) 缓慢上升。
第 3 步：量化项。量化步长 \(\Delta\propto 2^{-b}\)，误差方差 \(\Delta^2/12\propto 4^{-b}\)，随 \(b\) 指数下降。

这个玩具模型能带走的是结构，不是“4 位最好”这个具体数：参数项随位数变化很慢（幂次 0.348），量化项变化很快（指数），所以最优点总在量化项只占参数项百分之几的地方；内存每大 10 倍，最优位数只增加约 0.6 位，几乎不随设备变。最优点落在几位，由 \(c_q\) 决定：Dettmers 与 Zettlemoyer（2022）的实测显示常见训练后量化落在 4 位附近，对应 \(c_q\) 大致在 2 的量级；QAT 把 \(c_q\) 压低很多（演示里取 1/8，示意），最优点左移约两位。PrismML 的三值版方向与此一致，但训练细节未公开，机制无法验证。

推导：最优位数在哪，它怎样随内存和训练方式移动

第 1 步，量化误差怎样变成损失。训练好的模型处在损失的极小值附近，梯度约为 0。给权重加一个小扰动 \(\boldsymbol\delta\)，损失按二阶展开增加 \(\tfrac12\boldsymbol\delta^\top H\boldsymbol\delta\)。量化误差各分量近似独立、方差 \(\sigma_q^2 = \Delta^2/12\)，期望增加 \(\tfrac12\sigma_q^2\operatorname{tr}H\propto 4^{-b}\)。所以 \(c_q\) 里装着“模型对扰动有多敏感”（\(\operatorname{tr}H\)）和“取整方法有多好”。

第 2 步，求极值。对 \(b\) 求导并令其为 0：

\[ \frac{\alpha}{b}\,A\Big(\frac{8M}{b}\Big)^{-\alpha} = \ln 4\cdot c_q\,4^{-b}\quad\Longrightarrow\quad \frac{\text{量化项}}{\text{参数项}} = \frac{\alpha}{b\ln 4} \]

\(b\approx 4\) 时右边约 0.063：在最优点上，量化造成的损失只有“参数不够”造成的约 6%。参数项随 \(b\) 变化很慢（幂次 0.348），量化项变化很快（指数），所以只要量化项还不到参数项的几个百分点，继续减位、换更多参数就划算。

第 3 步，最优位数随内存怎样变。两边取对数、整理：

\[ b^\ast \approx \frac{1}{\ln 4}\Big[\alpha\ln(8M) + \ln\frac{c_q\ln 4}{\alpha A} + (1-\alpha)\ln b^\ast\Big] \]

内存每大 10 倍，\(b^\ast\) 只增加约 \(\alpha\ln 10/\ln 4\approx 0.58\) 位（右边的 \(\ln b^\ast\) 项再添一点，6 GB 到 60 GB 时是 3.85 → 4.50，约 0.65 位）。这一条与 \(c_q\) 无关：最优位数对内存不敏感。

第 4 步，训练方式怎样移动它。QAT 让模型在训练时适应量化网格，相当于把 \(c_q\) 降低 \(k\) 倍，\(b^\ast\) 大约减少 \(\log_4 k\) 位（\(\ln b^\ast\) 项让它再多减一点）：\(c_q\) 降为 1/8，6 GB 时最优点从约 3.85 位左移到约 2.05 位。反过来，Kumar 等（2024）发现训练数据越多，训练后量化的损失越大，过度训练的小模型相当于 \(c_q\) 变大，最优点右移（\(c_q\) ×4 时右移约 1.1 位）。

这个推导告诉我们：同样的内存，最优点在参数项远大于量化项的地方；它的位置随内存只按对数缓慢移动，主要由 \(c_q\) 决定。想把最优点推到 2 位以下，要让模型在训练中适应量化网格（降低 \(c_q\)），换更好的取整方法只能推一点。“落在 4 位”不是玩具模型推出来的，而是实测：Dettmers 与 Zettlemoyer（2022）在 1900 万到 1760 亿参数、3.5 万次实验中发现，固定模型总位数时，4 位几乎总是零样本准确率最优的选择。

Mac 与统一内存

Apple 芯片的 CPU 和 GPU 共享同一块内存（统一内存），这带来两个特点。好处是容量：M3 Ultra 可以配 512 GB，能放下独立显卡远远放不下的模型，一些万亿参数级 MoE 的 4 位版本可以在一两台 Mac Studio 上运行。限制是带宽和算力：M3 约 100 GB/s，M3 Max 约 300–400 GB/s，M3 Ultra 约 819 GB/s，都低于同价位的高端显卡（RTX 4090 约 1 TB/s），而 GPU 算力更是差一个数量级，长提示的预填充很慢。

Mac 没有“显存 / 内存”之分，但 GPU 默认只能用到其中一部分（「从零开始」一节）：36 GB 以下约三分之二，更大的机型约四分之三。按 4 位、留出 KV 和缓冲区估算，各档内存能放下的典型模型是：

手机：3B 左右是甜点

手机的约束更紧：内存 8–16 GB 且大部分要留给系统和应用，能给模型的通常只有几 GB；带宽约 60–80 GB/s；还有电池和发热。用本章的账算一遍：4 位的 3B 约 1.7 GB，放得下，生成上限约 \(70/1.7\approx 40\) token/s；4 位的 7B 约 3.9 GB，已经挤占系统内存，上限也只有约 18 token/s；再扣掉下一小节的发热，长时间运行还要打五六折。所以手机上的模型通常在 1–4B 之间，并且大量使用 QAT 和极低位量化：

  • Apple Foundation Models（iOS 26，2025）：约 3B 的端侧模型，用 2 位 QAT 训练，并在层之间共享 KV 缓存；开放给第三方开发者，支持结构化输出和 LoRA 适配器。
  • Gemma 3n / Gemma 4 的 E2B、E4B：“E”表示有效参数。总参数更多，但每一层都有一张自己的嵌入表，叫逐层嵌入（per-layer embeddings, PLE）：按 token 编号查表，不参与矩阵乘法，可以放在闪存或 CPU 内存里按需读取。常驻加速器内存的只相当于 2B 或 4B 的模型（Gemma 4 E2B 有效 2.3B、总参数约 5B）；MatFormer 结构还允许从大模型中切出小模型按需使用。据报道 Gemma 4 E2B 在新一代旗舰手机上可达每秒约 40 个 token。
  • NPU 的角色：手机的 NPU（几十 TOPS）擅长计算受限的预填充，联发科 NPU 上 Gemma 3n E2B 的预填充超过每秒 1600 token；但解码仍受内存带宽限制，NPU 帮不上太多。NPU 的算子集合封闭、编程门槛高，很多应用仍在 GPU 上运行。

功耗与发热：为什么跑几分钟就变慢

手机的另一道墙是热。芯片温度接近上限时，系统主动降低频率和电压来减少发热，叫热降频。2026 年的一项测量（Tummalapalli 等，2026-06 修订版）让 iPhone 16 Pro 连续运行 4 位的 Qwen2.5 1.5B：峰值约 40.5 token/s，三轮之内损失约 40%，最后稳定在约 23.7 token/s；Galaxy S24 Ultra 20 轮里降了约 15%，稳定在约 10 token/s。同一个模型在 RTX 4050 笔记本显卡上以 34.1 W 稳定在 131.7 token/s。另一项测量里，用 MNN 在手机上解码时整机功耗达到 7.9–9.9 W。长时间运行时，发热不能超过散热：

\[ \htmlClass{sym-v}{v_{\text{持续}}} \approx \frac{\htmlClass{sym-Pd}{P_{\text{散热}}}}{\htmlClass{sym-E}{E_{\text{token}}}},\qquad \htmlClass{sym-Pd}{P_{\text{散热}}} \approx \frac{\htmlClass{sym-T}{T_{\text{壳}} - T_{\text{环境}}}}{\htmlClass{sym-R}{R_{\text{th}}}} \]

结论：手机长时间运行的速度由“能散掉几瓦 ÷ 每个 token 多少焦耳”决定，而不是由带宽决定。减少每个 token 搬的字节（更低的位数、更少的激活参数）同时提高峰值和持续速度，是手机上最直接的办法。

推导：一部手机能持续散掉几瓦，多久开始降频

第 1 步，热阻。手机靠外壳对空气的自然对流和辐射散热。自然对流的换热系数约 5–10 W/(m²·K)；辐射在室温附近线性化为 \(4\varepsilon\sigma T^3\approx 4\times 0.9\times 5.67\times 10^{-8}\times 300^3\approx 5.5\) W/(m²·K)。合计 \(h\approx 10\)–15 W/(m²·K)。正反两面面积 \(S\approx 2\times 0.15\ \text{m}\times 0.07\ \text{m}\approx 0.02\ \text{m}^2\)，热阻 \(R_{\text{th}} = 1/(hS)\approx 3\)–5 K/W。

第 2 步，能持续的功率。温升 18 K：\(P_{\text{散热}}\approx 18/(3\sim 5)\approx 4\)–6 W。热量集中在芯片附近，外壳并不是均匀的温度，实际还要更低，量级是几瓦。满载的 8–10 W 只能维持一段时间，之后速度大约要降到六成左右，与 iPhone 的测量（40.5 → 23.7 token/s）一致。

第 3 步，时间尺度。整机热容 \(C_{\text{th}}\approx mc\approx 0.2\ \text{kg}\times 800\ \text{J/(kg·K)}\approx 160\) J/K，时间常数 \(\tau = R_{\text{th}}C_{\text{th}}\approx 8\)–13 分钟。外壳温度按 \(T(t) = T_{\text{环境}} + PR_{\text{th}}\big(1 - e^{-t/\tau}\big)\) 上升；\(P = 9\) W、\(R_{\text{th}} = 4\) K/W 时稳态温升 36 K，升到 18 K 需要 \(t = \tau\ln 2\approx 0.7\tau\)，约 7 分钟。但芯片本身只有几克，热量来不及散开，局部几秒到几十秒就会碰到芯片的温度上限，调速器先降频。所以手机降频有两个时间尺度：芯片级的秒级，外壳的分钟级。iPhone 三轮之内就掉速，对应的是前一个。

第 4 步，降频为什么让解码掉得多（模型预测）。动态调频调压（DVFS）同时降低频率 \(f\) 和电压 \(V\)。动态功耗 \(\propto C_{\text{sw}}V^2f\)（\(C_{\text{sw}}\) 是开关电容），在常用范围内 \(V\) 大致随 \(f\) 线性变化，所以功耗 \(\propto f^3\)：功耗砍半，频率只降到 \(0.5^{1/3}\approx 0.79\)。计算受限的预填充跟着频率走，只慢约 20%。解码的能量主要花在内存访问和接口上，随芯片频率变化不大，\(E_{\text{token}}\) 近似不变；当功耗被散热卡住（功率受限，而不是带宽受限）时，速度 \(\approx P/E_{\text{token}}\)，功耗砍半，速度也接近砍半。这是一个粗略的模型，没有按阶段拆分的实测支持；实际的调速器还会单独调内存频率。

这个推导告诉我们：手机能持续散掉的只有几瓦，外壳几分钟、芯片几秒就会碰到上限；之后速度由“几瓦 ÷ 每个 token 多少焦耳”决定。减少每个 token 搬的字节同时提高峰值和持续速度；NPU 每次运算的能耗低，主要省的是预填充。

嵌入式 NPU：TOPS 为什么不能直接比

嵌入式板子的宣传数字常常是 TOPS（每秒万亿次运算，通常指 INT8 的乘加）。但跑语言模型时，生成速度看的仍是第三笔账：带宽 ÷ 每个 token 读的字节，和 TOPS 几乎无关。Jetson Orin Nano Super 的内存带宽约 102 GB/s，4 位的 3B 模型约 1.7 GB，生成上限约 60 token/s；带 Hailo-10H 的树莓派 5 跑 1.5B 模型只有 6.9 token/s，但功耗不到 2 W、几乎没有波动，它受限于模块上的内存带宽（同一项 2026 年的测量）。TOPS 只在预填充和视觉模型这类计算受限的任务上起作用，而且要打折：很多厂商标的是 2:4 结构化稀疏下的峰值，稠密计算打对折；标的是 INT8，换成 INT16 或 FP16 再减半或更多；实际模型受访存和不支持的算子拖累，利用率常常只有三到六成。可用算力约为标称 TOPS × 0.5（若标的是稀疏）× 利用率。

本地模型与云端模型的差距在缩小吗

缩小
常被引用的两个数是两种不同的比较，不能并排读成“差距从 6–12 个月缩到了 4 个月”。一是本地的差距：Epoch AI（2025-08）测得，一张顶级游戏卡（RTX 5090 这一档）能运行的开源模型，落后前沿 6–12 个月（四项指标各自平均 6.3–12.4 个月）。二是开源的差距：Epoch AI（2026-05）测得，2026 年以来最强的开源模型与闭源前沿的差距平均约 4 个月，但这些开源旗舰多半放不进你的显卡。开源模型追赶得快，量化和 MoE 让大模型越来越容易放进本地设备；隐私、离线、零边际成本和低延迟，是本地部署的独特优势。
没有缩小
Epoch 自己也提醒，小型开源模型更可能针对基准做了优化，实际可用性的差距要比 6–12 个月更长。前沿能力本身在快速前进：一年前的前沿，到今天往往已不够用；智能体任务需要百万 token 的上下文和长时间推理，本地设备的预填充速度和内存都难以承受；最强的模型越来越大（万亿参数），本地只能运行它们的蒸馏版。
现在怎么看
“本地能跑一年前的前沿”大致成立，“本地能跑今天的前沿”不成立。实际的分工是：日常、隐私敏感、离线的任务在本地，复杂的长任务交给云端。本地小模型处理简单请求、必要时转给云端的端云协同，是手机厂商的主流方案。

常见误解

  • 能装进显存就能跑得快。装得下只是第一本账；生成速度看带宽，读长提示看算力，Mac、手机和只有 CPU 的机器在后者上差距很大。上下文拉长后，读 KV 还会把生成速度拖慢近一半。
  • TOPS 越高，越适合跑大模型。大模型的解码受内存带宽限制；TOPS 还常按稀疏、INT8 标注，需要打折。
  • 同样占 6 GB，小模型高精度比大模型低精度好。多数情况下相反：大模型的低位版本（尤其是 QAT 的）通常更强，训练后量化的甜点在 4 位左右，而两者生成速度几乎一样。例外是读提示多的场景：预填充的计算量只看参数量。
  • MoE 本地一定慢。MoE 每个 token 只读少量专家，在带宽受限的本地设备上反而有优势；放不进显存时，把专家放在 CPU 内存里由 CPU 计算仍然可用，只要别让专家落到硬盘上。

演进史

2023-03

llama.cpp：大模型第一次跑在笔记本上

卡在哪
大模型只能在数据中心的 GPU 上运行：7B 的 FP16 权重就要 13 GB，还要 CUDA。
怎么解决
LLaMA 权重流出后不久，llama.cpp 用纯 C/C++、32 个权重共用一个缩放因子的 4 位量化（Q4_0，最初缩放因子存 FP32，5 bpw；2023-05 改用 FP16 后为 4.5 bpw）和内存映射加载，让 7B 在 MacBook 的 CPU 上运行；随后加入 Metal、CUDA 后端。
代价
直接取整的 4 位损失明显；文件格式几次不兼容地改动。
引出
同样的位数怎样误差更小：K-quants（2023-06）、imatrix（2024-01），以及更早的 GPTQ（2022-10）、AWQ 进入本地生态，这段历史在第 章；文件怎样稳定下来：GGUF（见支线）。
被淘汰GGML 早期的模型文件格式
最早的 GGML 文件只存张量，超参数和分词器靠代码约定，格式改了几版，每次升级都让旧文件失效。GGUF（2023-08）把这些信息都写进文件，按键值对扩展，之后再没有大的断代。它留下的教训是：本地生态里，“文件能不能打开”本身就是一个工程问题。
2023-05 → 2024

MLC、手机 NPU 与系统级端侧模型

卡在哪
每种设备（安卓 GPU、iPhone、浏览器）都要重写内核；手机内存和电池限制模型规模。
怎么解决
MLC-LLM（2023-05）用编译器为 Vulkan、Metal、OpenCL、WebGPU 生成内核；高通、联发科的旗舰 NPU 开始支持大模型；Phi-3 mini 等强力小模型；Apple Intelligence 发布端侧约 3B 的模型（2024-06）；Gemini Nano 进入 Pixel 手机。
代价
NPU 工具链封闭、算子支持滞后；解码仍受带宽限制；端侧模型只能做简单任务，复杂请求转给云端。
引出
手机上的路线后来走向 QAT 与极低位（Apple 的 2 位 QAT，2025）和逐层嵌入外置（Gemma 3n，2025-06，见下一节点的支线）。
持续发展嵌入式 NPU 上的大模型
瑞芯微的 RKLLM、各家边缘 AI 芯片开始支持 1–3B 的语言模型，但受内存带宽和封闭算子集合的限制，主要用于语音助手、简单问答等场景；视觉检测仍是嵌入式 NPU 的主战场。
2023-12 → 2025

统一内存：大容量放下大模型

卡在哪
消费级显卡 12–24 GB，放不下 30B 以上的模型；Mac 内存大，但框架按独立显卡设计，数据在 CPU 与 GPU 之间来回拷。
怎么解决
Apple 发布 MLX（2023-12），CPU、GPU 共用一份数据，大内存的 Mac 能放下大模型；2025 年起 AMD Ryzen AI Max+（2025-02）、NVIDIA DGX Spark（2025-10）把 128 GB 统一内存做进小主机。
代价
带宽和 GPU 算力低于同价位显卡，稠密大模型生成慢、读提示更慢。
引出
容量够了、带宽不够，正好适合每个 token 只读少量参数的 MoE（下一节点是同一时期的另一条线）。
分支从闪存按需读取：LLM in a flash 与逐层嵌入
Apple 的 LLM in a flash（2023-12）研究在内存不够时从闪存按需读取权重：只读预测会被激活的部分，并把要一起读的数据排在一起，跑起了两倍于内存的模型。Gemma 3n（2025-06）的逐层嵌入是同一思路的产品化：按 token 编号查表的那部分参数放在闪存里，常驻内存的只有有效参数。
2024 → 2025

MoE 成为本地主力：专家放进 CPU 内存

卡在哪
稠密大模型在 100–300 GB/s 的带宽上太慢，放不进显存时整块卸载到内存又慢一个数量级。
怎么解决
激活参数很少的 MoE：Qwen3-30B-A3B（2025-04）、gpt-oss-20b（2025-08，MXFP4，16 GB 设备可运行）。Fiddler（2024-02）提出让 CPU 就地算专家；llama.cpp 支持按名字把专家张量留在 CPU 内存（2025）。
代价
总参数仍要有地方放；专家一旦落到硬盘上，速度掉一个数量级；读提示时要把专家搬上显卡。
引出
同一时期，各家开始发布官方 QAT 版本（Gemma 3 QAT，2025-04；gpt-oss 的 MXFP4），把权重字节这一项继续往下压（下一节点）。
2024-02 → 2026-09

低比特与三值：让模型适应量化网格

卡在哪
训练后量化到 3 位以下会崩，崩在长推理上。
怎么解决
BitNet b1.58（2024-02）从头训练三值模型，bitnet.cpp（2024-10）在 CPU 上运行；PrismML 先发布二值的 1-bit Bonsai 8B（2026-03，1.125 bpw、1.15 GB），再发布 Ternary Bonsai 2 27B（2026-09，1.72 bpw）。这条线的细节在第 章。
代价
要专门训练和专门的运行时分支；在快的显卡上解码不再完全受带宽限制；成绩多为厂商自报。
引出
对本地部署的影响是同样的显存能放下大约三倍参数的模型（「同样的内存」一节）。
争论三值会成为主流吗
支持者看到的是：同样的内存放下大三倍的模型，矩阵乘法只剩加减。怀疑者指出：需要从头训练或大量 QAT，主流 GPU 没有三值运算单元，加速依赖专门内核，在 H100 和 Blackwell 上三值的密排格式反而更慢；常规基准可能低估长尾知识的损失。见第 章的争议框。
2025-10 → 2026-05

补上闲着的算力：矩阵单元与端侧草稿头

卡在哪
Mac 读提示太慢；单用户解码时大部分算力闲着。
怎么解决
两条独立的线。Apple M5（2025-10）在每个 GPU 核心里加入矩阵加速单元，首 token 时间快 3.3–4.1 倍。Gemma 4（2026-04）发布端侧版本，随后配套 MTP 草稿（2026-05），用闲着的算力一次验证多个 token。
代价
M5 的生成速度只随带宽涨；草稿在算力弱的设备上收益小，对 MoE 收益也打折。
引出
端侧模型的输入越来越不止文字：手机上的摄像头和屏幕截图（第 章）。

自测

1. 一台 24 GB 显存的显卡，想跑 Qwen3-32B 稠密模型，Q4_K_M（约 4.9 bpw），每 token 的 KV 缓存约 256 KB（FP16，64 层 × 8 个 KV 头）。权重多大？留 1 GB 给运行时，最多能用多长的上下文？KV 改存 Q8_0 呢？
权重 \(32\times 10^9\times 4.9/8\approx 19.6\) GB。剩余约 \(24 - 19.6 - 1 = 3.4\) GB，\(3.4\text{ GB}/256\text{ KB}\approx 1.3\) 万 token。Q8_0 是 8.5 位，KV 容量扩大 \(16/8.5\approx 1.9\) 倍，约 2.4 万 token（不是翻倍）。
2. 同一台 M3 Max（约 400 GB/s，GPU 约 14 TFLOPS），跑 4 位的 30B 稠密模型和 4 位的 30B 总参数、3B 激活的 MoE。这次生成和预填充都要算：生成速度上限各是多少？读一个 16K 的提示各要多久（利用率 50%）？
稠密：每 token 约 15 GB，上限约 27 token/s；预填充 \(2\times 3\times 10^{10}\times 16384/(7\times 10^{12})\approx 140\) 秒。MoE：每 token 约 1.5 GB，上限约 270 token/s（MoE 的实际利用率更低，见「解码的上限」）；预填充按激活参数计 \(2\times 3\times 10^9\times 16384/(7\times 10^{12})\approx 14\) 秒。
3. M3 上 7B 的 4 位模型读提示约 187 token/s、生成约 21 token/s。给它挂一个 MTP 草稿头，接受率 \(\alpha = 0.8\)，每个草稿 token 的成本 \(c = 0.05\)。\(\gamma = 3\) 和 \(\gamma = 15\) 时加速比各约多少？换到 RTX 4090（\(m^\ast\approx 78\)）呢？
M3 的 \(m^\ast\approx 187/21\approx 9\)。\(\gamma = 3\)：\(\mathbb E[X] = (1 - 0.8^4)/0.2\approx 2.95\)，验证 4 个位置算一步，\(S\approx 2.95/(1 + 0.15)\approx 2.6\)。\(\gamma = 15\)：\(\mathbb E[X] = (1 - 0.8^{16})/0.2\approx 4.86\)，验证 16 个位置约 \(16/9\approx 1.8\) 步，\(S\approx 4.86/(1.8 + 0.75)\approx 1.9\)，草稿越长反而越慢。RTX 4090 上 16 个位置仍在免费范围内：\(\gamma = 15\) 时 \(S\approx 4.86/1.75\approx 2.8\)，比 \(\gamma = 3\) 好。最优草稿长度取决于设备的 \(m^\ast\)。
