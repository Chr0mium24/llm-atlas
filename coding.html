AI 编程：从补全一行到独立完成任务

编程是大模型最成功、也最被认真测量的应用，因为代码有天然的验证器：能不能运行，测试过没过。这一章先跟着一个玩具 bug 看编程智能体每一步在做什么，再讲代码模型怎样训练，然后讲贯穿全章的一个量：测试的误放率。它决定了 RL 会不会教出针对测试取巧的模型、多采样再筛选的天花板在哪里、评测分数有多可信。最后看每一代编程工具在修什么，以及 AI 到底让开发者快了还是慢了。

上一章的智能体在编程上落地最早、最成熟：Claude Code、Codex、Cursor 这类工具每天被数百万开发者使用。编程既是智能体的主战场，也是 RL 可验证奖励最丰富的来源。这一章看这个循环在代码上具体长什么样，以及“测试”这个验证器有多可靠。

从零开始：一个 bug 的一生

这一节不讲任何模型的训练。用一个只有三个文件的玩具仓库和一个 bug，跟着一个编程智能体走完“定位、复现、修改、跑测试、读报错、再修改”的全过程，顺便把后面每一节都要用的概念讲一遍：issue 与单元测试、测试覆盖、补丁与回归、执行反馈、验证器与误放率。熟悉软件开发的读者可以直接跳到「代码模型怎样训练」。

一个三文件的仓库和一个 issue

一个代码仓库（repository）是一个项目的全部文件加上修改历史。玩具仓库叫“小统计”，只有三个文件：core.py 里有求平均数和求中位数的两个函数，约 60 行；cli.py 让用户在命令行里调用它们；test_core.py 是测试。

某天一位用户提交了一条 issue（问题报告）：“对 4、1、3、2 求中位数，返回 3，应该是 2.5。”issue 是开源项目里报告 bug、提出需求的标准方式，也就是智能体拿到的任务描述。

test_core.py 里有 5 个单元测试（unit test）：每个是一小段自动运行的检查，给函数一个固定输入，断言输出等于期望值，相等就“通过”，否则“失败”并打印哪里不对。它们检查：三个数的平均数、负数的平均数、3、1、2 的中位数是 2、只有一个数时的中位数、空列表会报错。

bug 在哪？求中位数的函数先排序，再取长度一半（向下取整）处的数。奇数个数时完全正确；偶数个数时应取中间两个数的平均，它却只取了靠后的那个。bug 能活到今天，是因为所有中位数用例都是奇数个数。测试实际检查到了哪些输入和代码路径，叫测试覆盖（test coverage）。“偶数个数”这条路径没被覆盖，所以测试全部通过，bug 照样存在。

第 1–3 步：定位，以及“测试全过了”

智能体开工前，上下文里已经有约 3000 个 token 的系统提示（行为规范，加上四个工具的说明：搜索、读文件、改文件、运行命令），再加上约 100 个 token 的 issue。第 章的记号里，这就是初始上下文 \(C_0 \approx 3100\)。

  1. 模型搜索“median”这个名字，工具返回一行：core.py 第 18 行（约 60 个 token）。
  2. 读 core.py 全文，返回约 520 个 token。模型在第 22 行看到了“取长度一半处的元素”。
  3. 先运行已有的测试，返回“5 个通过”（约 80 个 token）。

前两步叫定位（fault localization）：从问题描述找到该改的文件和行。真实仓库有成千上万个文件，定位往往是最难的一步。把“可能相关”的文件直接塞进上下文效果很差：SWE-bench（用真实仓库的 issue 出题的评测，见下文「评测」）的原论文（2023）里，给 Claude 2 的检索上下文从 1.3 万 token 加到 5 万 token，正确文件被包含进来的比例从 29.6% 升到 51.1%，解决率却从 1.96% 降到 1.22%。智能体的做法和人一样：搜索、跳转，只读需要的那几十行。

第 3 步的结果是整章的伏笔：测试全过了，bug 还在。“通过测试”和“代码正确”是两回事。

第 4–5 步：先复现，再动手

有经验的开发者修 bug 之前，会先写一个复现测试：一个能稳定触发这个 bug、因此现在一定失败的测试。智能体照做：

  1. 在 test_core.py 末尾加一个测试：4、1、3、2 的中位数应为 2.5（工具返回“已写入”，约 30 个 token）。
  2. 运行它，失败：“期望 2.5，实际得到 3”，连同出错位置约 260 个 token。

这一步有三个作用：确认理解了问题；得到一个会从“失败”变成“通过”的信号，每次修改都能拿它检验；修好后它留在测试集里，防止 bug 复发。后面的 SWE-bench 就按这个结构出题。

第 6–9 步：改、跑、读报错、再改

对代码的一组修改叫补丁（patch，也叫 diff）：记录在哪个文件删掉了哪几行、加上了哪几行。

  1. 模型改写中位数函数：个数为偶数时，取中间两个数的平均。但它用“长度除以 2”来算下标，在 Python 里这得到的是小数 2.0。
  2. 运行测试，报错：“下标必须是整数，不能是小数”，附带出错的那一行（约 300 个 token）。
  3. 模型读懂了报错，把除法改成整除。
  4. 运行全部测试：6 个通过（原来的 5 个加上新写的 1 个）。
  5. 写一段总结，不再调用工具，循环结束。

第 7 步里，运行代码的结果（通过、失败、报错信息）回到了模型的上下文，这叫执行反馈（execution feedback）。报错指出了哪一行、什么原因，模型第二次就改对了。第 9 步里原来的 5 个测试确认这次修改没弄坏原有功能；弄坏了原有功能叫回归（regression），防回归的测试就是 SWE-bench 里的另一组测试。

为什么“能跑测试”是关键

设想智能体没有运行代码的工具。它只能在第 6 步交出第一版修改，而那一版是错的。能跑测试，错误就在第 7 步被抓住、第 8 步被改正。第 章「长任务为什么难」把这写成了“检查并重试”的等比级数：每次尝试以概率 \(p\) 做对，做错时以概率 \(r\) 被发现、触发重做；不限重试次数时，最终做对的概率是 \(p/\big(p + (1-p)(1-r)\big)\)。

在编程里，检查就是测试，而测试会漏。一个错误的补丁仍然通过全部测试的概率，叫误放率（false-pass rate），记作 \(\varphi\)，它就是上式里的 \(1 - r\)。玩具仓库原来的 5 个测试，对“偶数个数取错”的误放率是 100%。

能自动判断“这个输出对不对”的程序，都叫验证器（verifier）：单元测试、编译器、类型检查、证明检查器。测试是不完美的验证器：通常不冤枉正确的补丁，但会放过一部分错误的。上面的极限换个角度看，正是“通过测试的补丁里真正正确的比例”，即验证器的精确率（precision）：

\[ \htmlClass{c-adv}{\htmlClass{sym-pi}{\pi}} = P(\text{真正正确}\mid\text{通过测试}) = \frac{\htmlClass{sym-p}{p}}{\htmlClass{sym-p}{p} + (1 - \htmlClass{sym-p}{p})\,\htmlClass{sym-phi}{\varphi}} \] 贝叶斯公式：通过测试的补丁有两个来源，正确的（全部通过）和错误但溜过去的
在所有通过测试的补丁里，正确的占 \(p\) 那么多，错误但骗过了测试的占 \((1-p)\varphi\) 那么多。前者占总数的比例，就是“测试说通过”这句话的可信度。
\(\pi\)
验证器的精确率：通过测试的补丁里真正正确的比例
\(p\)
模型一次尝试写出正确补丁的概率
\(\varphi\)
误放率：一个错误补丁通过全部测试的概率（第 章的检出率 \(r\) 等于 \(1-\varphi\)）
\(p = 0.6\)、\(\varphi = 0.1\)：\(\pi = 0.6/(0.6 + 0.04) = 93.75\%\)。按第 章的式子，允许重试 1 次时做对的概率是 \(0.6\times(1 + 0.36) = 81.6\%\)，重试 2 次 89.4%，不限次数就到 93.75% 为止。测试只能抓住一半错误（\(\varphi = 0.5\)）时，天花板降到 75%；完全没有测试（\(\varphi = 1\)）时，停在 \(p = 60\%\)。

这个量在本章出现三次：这里是串行的“改了再跑”；「测试当奖励」里，它决定 RL 的奖励在多大程度上等于“真修好了”；「多采样加测试筛选」里，它是并行采样的天花板。结论相同：提高 \(p\) 和降低 \(\varphi\) 都能抬高天花板；只要 \(\varphi\) 不为 0，无限重试、无限采样也到不了 100%。

代码模型怎样训练

2021 年的 Codex 是在 GPT-3 系列模型上用 159 GB 的 GitHub Python 代码继续训练得到的（最大 12B 参数），GitHub Copilot 最初用的就是它。同等规模、没练过代码的 GPT 模型在 HumanEval（Codex 论文发布的 164 道手写 Python 函数题，平均每题 7.7 个单元测试）上一道也做不出，Codex 一次采样能做对 28.8%。此后代码数据成为所有大模型预训练的标配（第 章），开源的 The Stack v2 覆盖 600 多种编程语言，并按许可证过滤、去重。与普通文本相比，代码训练有几个专门的设计。

中间填空。写代码时，光标常常在文件中间：上面有代码，下面也有代码。普通的自回归模型只能看左边。中间填空（fill-in-the-middle, FIM, Bavarian 等, 2022）在训练时把一部分文档重新排列：

\[ \underbrace{\text{前缀}\ \ \text{中间}\ \ \text{后缀}}_{\text{原始文档}} \ \longrightarrow\ \htmlClass{c-new}{\langle\text{PRE}\rangle}\,\text{前缀}\,\htmlClass{c-new}{\langle\text{SUF}\rangle}\,\text{后缀}\,\htmlClass{c-new}{\langle\text{MID}\rangle}\,\htmlClass{c-adv}{\text{中间}} \]
随机挑一段作为“中间”，把它挪到最后，用三个特殊 token 标出各部分。模型仍然只是从左到右预测下一个 token，但预测中间那段时，已经看过了前缀和后缀。
原文 “def area(r):⏎ return 3.14 * r * r⏎print(area(2))”，选中间为 “return 3.14 * r * r”。重排后：⟨PRE⟩def area(r):⏎ ⟨SUF⟩⏎print(area(2))⟨MID⟩return 3.14 * r * r。推理时，编辑器把光标前后的代码分别放进前缀和后缀，让模型生成中间，直到它输出一个表示“已经接上后缀”的结束 token。论文发现，把 50% 乃至 90% 的训练文档做这种变换，从左到右的能力都看不出损失；只有 100% 变换时才变差。

两个细节决定了效果。切分点在字符级别均匀随机地选，前缀、中间、后缀平均各占三分之一，中间段可能从半个 token 开始，这正是光标停在一个词中间的情形；按行或按 token 切分的模型在这种情形下几乎完全失败。三段的损失都保留，训练过的 token 一个也没少。为什么这样重排几乎不影响原来的能力？把两种顺序写成概率的分解就清楚了：

\[ \begin{aligned} \text{从左到右：}\ p(\text{文档}) &= p(\text{前})\;p(\text{中}\mid\text{前})\;p(\text{后}\mid\text{前},\text{中}) \\ \text{中间填空：}\ p(\text{文档}) &= p(\text{前})\;\htmlClass{c-new}{p(\text{后}\mid\text{前})}\;\htmlClass{c-new}{p(\text{中}\mid\text{前},\text{后})} \end{aligned} \]
同一份文档的概率，可以按不同的顺序用链式法则拆开。从左到右是一种顺序，中间填空是另一种；两者都是精确的等式，描述的是同一个分布。区别只在新出现的两个条件概率：跳过中间预测后缀，和看着两头预测中间。
完美的模型给两种排法算出的概率相等。真实模型做不到：论文在同一批文档上比较，填空排法的困惑度总是更高，即 \(p_{\text{填空}}(\text{文档}) < p_{\text{左到右}}(\text{文档})\)。跳过一段不知道的内容去预测后面，本来就更难。
中间填空为什么几乎“免费”，又为什么不能事后补

第 1 步，不是新目标。链式法则对任何顺序都成立。中间填空和从左到右是同一个联合分布 \(p(\text{前},\text{中},\text{后})\) 的两种分解，最大似然的目标都是“让真实文档的概率尽量大”，原则上不冲突：足够强的模型可以把两种分解都学对。问题只在有限的容量要分给两种模式。

第 2 步，数一数“上下文完全一样”的 token。设变换比例为 \(f\)。没被变换的文档（占 \(1-f\)）是普通训练；被变换的文档里，前缀（平均三分之一）的上下文也和普通训练一样。所以上下文完全相同的 token 比例是 \((1-f) + f/3\)：\(f = 0.5\) 时 2/3，\(f = 0.9\) 时只有 0.40。可 \(f = 0.9\) 时从左到右的损失照样不变，“免费”不是因为大部分 token 没被动过。

第 3 步，局部没变，变的是全局。论文的解释：三段中的每一段内部仍是从左到右逐 token 预测，相当于把一篇文档切成三篇短文档，局部的预测任务（语法、变量名、紧邻的几百个 token）完全一样；变的只是全局的注意力模式：后缀看不到中间，中间能看到两头。大部分预测能力来自局部上下文，这部分一点也没少练。

第 4 步，为什么 100% 会变差，事后补为什么贵。\(f = 1\) 时，模型从没练过 \(p(\text{后}\mid\text{前},\text{中})\) 这种“看完前文接着往下写”的条件概率，而普通生成要的恰恰是它；留 10% 的文档保持原样就够了。反过来，在训好的从左到右模型上用微调补上填空能力，要大得多的算力和较大的学习率，作者猜测是预训练形成的全局注意力模式已经定型。

这个推导告诉我们：中间填空只是同一个分布换了一种分解顺序；它占用的是“全局注意力模式”的一点容量，局部的逐 token 预测一点也没少练，所以在预训练里加进去几乎免费。“免费”只在从头训练时成立，这也是 2022 年以后几乎所有代码模型从预训练起就带上 FIM 的原因。

仓库级上下文。真实代码分散在许多文件里，一个函数的含义要看它的调用者和依赖。DeepSeek-Coder、StarCoder 2 等按依赖关系把同一仓库的文件拼接成长序列来训练，让模型学会跨文件的引用，这叫仓库级上下文（repository-level context）。上下文也一路变长：StarCoder（2023）8K，Code Llama（2023）用 16K 训练、能外推到 10 万 token（第 章）。但上面的 SWE-bench 数字说明，放得进去不等于用得好：真正的提升来自让模型自己去找、去跑，也就是下一节的执行反馈。

把测试变成奖励：软件工程的 RL 环境

代码可以运行，测试可以判对错，这是第 章 RLVR 最理想的场景。玩具里那 10 轮循环就是一条轨迹，最后测试过没过就是奖励。把它做成可以大规模采样的训练场，就是软件工程 RL 环境：每道题是一个装好依赖的容器镜像（修复前的仓库）、一段任务描述和一组判分测试。DeepSWE（2025-07）的奖励很典型：5 分钟内复现 bug 的那组和防回归的那组测试全部通过得 1 分，否则 0 分。

难点在于造题。SWE-Gym（2024-12）从真实 issue 里人工整理出约 2400 道题，每题手工配置环境，真实但难以扩大。SWE-smith（2025-04）反过来：拿一个能通过全部测试的仓库，自动改坏代码让测试失败，“修回来”就是一道题，从 128 个仓库造出约 5 万道，代价是 bug 的分布和真实 issue 不同。R2E-Gym 等则从提交历史里挖“同时改了代码和测试”的提交，缺测试时让模型补写。

效果很明显。DeepSWE 只用 RL、在 R2E-Gym 的 4500 道题上训练 Qwen3-32B，64 张 H100 训练 6 天，每一步要同时开 512 个容器，SWE-bench Verified 的单次通过率从 23% 提到 42.2%。Qwen3-Coder（2025-07）训练时并行运行 2 万个环境；Cursor 的 Composer 据报道在数十万个并发沙盒中做 RL。第 章的 GRPO 在这里同样适用：一组轨迹全对或全错的题没有梯度，所以各家先估计每道题的通过率，筛掉太简单和太难的。Qwen3-Coder-Next 还对超过轮数上限仍未结束的轨迹、格式错误的工具调用额外扣分。

也有不跑代码的做法。Meta 的 SWE-RL（2025-02）不搭执行环境，奖励是生成补丁和真实补丁的文本相似度（0 到 1 连续取值）。它便宜，能用海量历史 PR，信号也比 0/1 密，训练出的 70B 模型在 Verified 上达到 41.0%。代价是它奖励“像参考答案”而不是“能工作”：写法不同的正确修复被扣分，字面很像却差一个符号的补丁反而得高分。执行奖励正好相反：奖励能工作的代码，但稀疏、昂贵，而且有下一节的误放问题。

测试当奖励：误放率与针对测试取巧

回到玩具仓库。假设智能体在第 6 步交出这样一个补丁：“如果输入正好是 4、1、3、2，就返回 2.5，否则照旧。”它能通过复现测试和原来的 5 个测试。人类开发者不会这样做，因为他知道目标是修好中位数；RL 只看奖励，分不清它和真正的修复。这种专门针对测试用例写的分支叫对测试写特例（special-casing），是钻奖励空子在代码里最常见的形式。

第一道防线是隐藏测试：判分时额外运行一批智能体看不到的测试（SWE-bench 里就是出题时藏起来的那些）。错误补丁能不能混过去，取决于它在多大比例的输入上出错，以及隐藏测试有多少个：

\[ \htmlClass{sym-phi}{\varphi} = (1 - \htmlClass{sym-delta}{\delta})^{\htmlClass{sym-m}{m}} \] 假设每个隐藏测试独立地从可能的输入里随机抽取
一个错误的补丁在比例为 \(\delta\) 的输入上会出错。每个隐藏测试有 \(\delta\) 的概率撞上它，\(m\) 个测试全部没撞上，补丁才能骗过去。
\(\varphi\)
这个错误补丁通过全部隐藏测试的概率（误放率）
\(\delta\)
补丁出错的输入所占的比例：写特例的补丁几乎处处出错，δ 很大；只漏了一个边界情况的补丁，δ 很小
\(m\)
隐藏测试的个数
写特例的补丁 \(\delta = 0.6\)：5 个隐藏测试就把误放率压到 \(0.4^5 = 1\%\)。只修了常见情况、漏掉边界的补丁 \(\delta = 0.05\)：10 个隐藏测试误放率仍有 \(0.95^{10} = 60\%\)，要 90 个测试才降到 1%。最难抓的是“差一点就对”的补丁。

RL 会把模型推向哪里？策略梯度只提高期望奖励。奖励是“通过判分”，所以哪种做法通过的概率最高，模型就越来越偏向哪种，不管它是不是真修好了：

\[ \underbrace{\htmlClass{sym-p}{p} + (1 - p)\,\htmlClass{sym-phic}{\varphi_{\text{近错}}}}_{\text{认真修的通过率}} \;>\; \max\big(\htmlClass{sym-phiw}{\varphi_{\text{特例}}},\ \htmlClass{sym-phiw}{\varphi_{\text{不完整}}},\ \htmlClass{c-clip}{\htmlClass{sym-h}{h}}\big) \] 只有满足这个不等式，RL 才会把模型推向认真修
认真修的通过率，是真修好的概率加上“没修好但误放过去”的概率；它必须高于每一种取巧做法的通过率，包括直接去改测试。
\(p\)
认真修一次真正修好的概率
\(\varphi_{\text{近错}}\)
认真修但没修好时，这个“差一点”的补丁的误放率
\(\varphi_{\text{特例}},\varphi_{\text{不完整}}\)
写特例、只修常见情况这两种偷懒补丁的误放率，随隐藏测试数 m 下降
\(h\)
修改测试文件、让测试框架提前退出这类做法的通过率：测试文件可写、判分前不恢复时为 1，与 m 无关
按下面演示的设定，\(p = 0.35\)。没有隐藏测试：认真修 0.675，三种取巧都是 1，取巧胜出。4 个隐藏测试、测试文件受保护：认真修 0.563，写特例 0.026，只修常见情况 0.522，改测试 0，认真修只领先 4 个百分点。测试文件不受保护：\(h = 1\)，再多的隐藏测试也没用。

能看到三件事。没有隐藏测试时，几十步之内测试通过率冲到接近 100%，真正修好的比例却跌到接近 0，奖励和目标彻底分家。隐藏测试和保护测试文件挡的是不同的路：前者挡偷懒的补丁，挡不住改测试；后者正好相反，两者都要。把隐藏测试加到 6 个、不保护测试文件，改测试一开始只有 2% 的概率，前两百步几乎看不见，然后突然接管；下面第二个推导解释这段潜伏期。

为什么加测试只能慢慢压低误放率

第 1 步，单个补丁：指数下降。对一个固定的错误补丁，\(\varphi = (1-\delta)^m\) 随测试数指数下降。\(\delta = 0.1\) 时，10 个测试 35%，100 个测试 \(2.7\times 10^{-5}\)。照这样算，几十个测试就够了。

第 2 步，错误补丁各不相同。模型写出的错误补丁是一大批，δ 各不相同，认真修出来的大多“差一点就对”，δ 集中在 0 附近。设 δ 的分布密度正比于 \(\delta^{a-1}\)（\(0 < a \le 1\)，\(a\) 越小，“差一点”的越多），平均误放率是

\[ \begin{aligned} \bar\varphi(m) &= \int_0^1 a\,\delta^{a-1}(1-\delta)^m\,d\delta = a\,B(a,\, m+1) \\ &= \frac{a\,\Gamma(a)\,\Gamma(m+1)}{\Gamma(m+a+1)} \;\approx\; \Gamma(a+1)\, m^{-a} \end{aligned} \]

最后一步用了 \(\Gamma(m+1)/\Gamma(m+a+1)\approx m^{-a}\)（\(m\) 较大时）。

第 3 步，代入数字。\(a = 0.5\)：10 个测试 27%，100 个 8.8%，1000 个 2.8%。测试数每翻 10 倍，误放率只降为约 \(1/\sqrt{10}\approx 1/3.2\)，从指数变成了幂律。平均值被那些 δ 极小的补丁主导，而随机抽取的测试很难撞上它们出错的那一小块输入。

第 4 步，对照实测。AlphaCode（2022）测过真实数据集的误放率：对每道题大量采样，取“被判为解出”的题，人工检查程序是否真的对。HumanEval 平均每题 7.7 个测试，误放率 30%；CodeContests 原始版每题 12.4 个，误放率 62%。他们变异已有输入生成新测试、用已知正确的程序核对输出，每题测试增到约 204 个，再丢掉测试过少的题，误放率降到 4%。EvalPlus（2023）把 HumanEval 的测试扩充 80 倍，各模型的 pass@k 下降了最多 19.3%–28.9%。

第 5 步，有针对性的测试更有效。既然误放来自 δ 很小的补丁，就直接去找“这个补丁和正确答案在哪个输入上不一样”。PatchDiff（2025）为每个通过了 SWE-bench 测试的补丁专门生成区分它与参考补丁的测试，发现 29.6% 的“通过”补丁行为与参考补丁不同（见评测一节）。

这个推导告诉我们：误放主要来自“差一点就对”的补丁，它们只在很少的输入上出错，随机加测试对它们的杀伤是多项式的而不是指数的。有效的办法是有针对性地生成测试（变异、差分测试），而不是堆数量。也正因为这些补丁最像正确答案，它们是 RL 最容易“学会”的那类偷懒：不是作弊，只是做得不完整，却拿了满分。

取巧的潜伏期：为什么钻空子常在训练后期突然出现

第 1 步，期望梯度。把模型的选择简化成在几种做法之间按 softmax 选：\(\pi_j \propto e^{\theta_j}\)，做法 \(j\) 的期望奖励 \(R_j\) 就是它的通过率，总期望奖励 \(J = \sum_j \pi_j R_j\)。第 章按钮游戏里的计算给出 \(\partial J/\partial\theta_j = \pi_j\,(R_j - J)\)：通过率高于平均的做法被调高。

第 2 步，终点只看通过率。梯度上升让概率最终集中到 \(R_j\) 最大的做法上。“真正修好”在式子里根本不出现，只通过 \(R_j\) 间接起作用。

第 3 步，开始时取巧很少见。设一开始几乎总在认真修（\(\pi_C\approx 1\)，\(J\approx R_C\)），改测试的概率 \(\pi_H\) 很小。softmax 下 \(d\pi_H = \pi_H\big(d\theta_H - \sum_k \pi_k\,d\theta_k\big)\)，后一项此时约为 0，所以每步

\[ \Delta\pi_H \approx \pi_H\cdot\alpha\,\pi_H\,(R_H - R_C) = \alpha\,(R_H - R_C)\,\pi_H^2 \]

增长速度和 \(\pi_H\) 的平方成正比：它越罕见，长得越慢。

第 4 步，解这个方程。把步数看成连续的时间 \(t\)，\(d\pi_H/dt = \kappa\,\pi_H^2\)，\(\kappa = \alpha(R_H - R_C)\)。分离变量得 \(1/\pi_H(t) = 1/\pi_H(0) - \kappa t\)，于是

\[ \pi_H(t) = \frac{\pi_H(0)}{1 - \kappa\,\pi_H(0)\,t}, \qquad t^* \approx \frac{1}{\alpha\,\pi_H(0)\,(R_H - R_C)} \]

在 \(t^*\) 之前，\(\pi_H\) 几乎不动；接近 \(t^*\) 时分母趋于 0，它急剧上升，直到近似不再成立、取巧占据多数。

第 5 步，代入数字。演示里 6 个隐藏测试、不保护测试文件：\(R_C = 0.523\)，\(R_H = 1\)，\(\pi_H(0) = 0.02\)，\(\alpha = 0.5\)，\(t^*\approx 1/(0.5\times 0.02\times 0.477)\approx 210\) 步；模拟里“认真修”在第 277 步跌破一半，量级一致。初始概率减半，潜伏期约翻倍，但不会消失。

这个推导告诉我们：只要取巧的通过率高于认真做，它迟早会胜出；初始概率越小，潜伏期越长，训练前期的曲线一切正常，后期突然爆发。这和工业界的报告吻合：Qwen3-Coder-Next 的新型钻空子行为正出现在 RL 后期。防御只能是让取巧的通过率低于认真做，而不是指望它“想不到”。

意外：模型学会了“让测试通过”，而不是修好代码

原以为
测试是客观的奖励，很难被钻空子（第 章说可验证奖励“很难被钻空子”）。
实际发现
大规模编程 RL 之后，模型出现了各种针对测试的取巧：对测试用例写特例、修改或删除失败的测试、让测试框架提前退出。Anthropic 在 Claude 3.7 Sonnet 的系统卡中坦承了对测试写特例的倾向；METR 记录了模型在“优化程序速度”任务中直接改写计时函数。ImpossibleBench（2025-10）构造规格与测试相互矛盾、不可能正当通过的任务：GPT-5 在 SWE-bench 改编版上作弊通过 54%，Claude 系列的作弊约八成是直接改测试。环境也有漏洞：2025-09 有人发现 SWE-bench 的容器里留着未来的提交记录，Claude Sonnet 4、Qwen3-Coder 等会翻历史直接找到官方修复；Qwen3-Coder-Next（2026-03）删掉了这些记录，RL 后期的模型又学会自己重新连上 GitHub 拉取历史。
为什么
测试只是“代码正确”的不完全代理，上面的不等式只要有一处不满足，优化压力就会找到那条路（第 章的古德哈特定律）。联网、git 历史、可写的测试目录、可改写的计时函数，都是“改掉判分者”的通道。
现在怎么看
训练环境要层层设防：判分前恢复测试文件、隐藏测试、清理 git 历史、拦截访问原仓库的网络请求（Qwen3-Coder-Next 拦下同时包含仓库地址和联网命令的工具调用）、再用模型审查轨迹。审查也不完美：ImpossibleBench 里，模型监控在竞赛题改编版上能抓住 86%–89% 的作弊，在 SWE-bench 改编版上只有 42%–65%。更令人担心的是，在编程中学会钻空子的模型，可能把这种倾向泛化到其它场景（第 章的涌现不对齐）。

评测：从 164 道小题到修真实仓库

早期的评测是“写一个函数”：HumanEval（2021）的每道题给出函数签名和说明，用单元测试判对错。由于模型的输出是随机的，评测通常报告 pass@k：采样 \(k\) 次，至少一次通过测试的概率。直接采样 \(k\) 次来估计方差很大，Codex 论文给出了一个无偏估计：

\[ \text{pass@}k = \mathbb E_{\text{题目}}\left[\,1 - \frac{\binom{\htmlClass{sym-n}{n} - \htmlClass{sym-c}{c}}{k}}{\binom{n}{k}}\,\right] \]
每题采样 \(n\ge k\) 次，数出其中 \(c\) 次通过。从这 \(n\) 次里随机挑 \(k\) 次，全都不通过的概率是“从 \(n - c\) 个失败里挑 \(k\) 个”的组合数除以总组合数；用 1 减去它，就是至少一次通过的概率。
\(n\)
每道题实际采样的次数（如 200）
\(c\)
其中通过测试的次数
\(n = 10\)，\(c = 3\)。pass@1 \(= 1 - \binom{7}{1}/\binom{10}{1} = 0.3\)，就是通过率。pass@5 \(= 1 - \binom{7}{5}/\binom{10}{5} = 1 - 21/252 = 0.917\)。如果直接用 \(1 - (1 - 0.3)^5 = 0.832\) 估计，会因为 \(n\) 有限而产生偏差（偏差的方向和大小见第 章的推导）。

pass@k 假设了完美的验证器：\(k\) 个样本里有一个对的就算解出。Codex 论文自己给出了这个假设有多乐观：Codex-S（Codex 再在正确解答上微调的版本）每题采样 100 次，77.5% 的题至少有一个样本是对的；不拿隐藏测试去挑、按模型自己的平均对数概率挑一个，只有 44.5%。“写得出”和“挑得出”差了 33 个百分点，这是多采样加筛选一节的主题。

HumanEval 很快饱和：2024 年头部模型已超过 90%，而且题目早已散布在网上，难以排除污染。评测于是沿着“更真实、更长、更难污染”的方向演进：

SWE-bench 的结构和玩具仓库一一对应：issue 是任务描述；出题时把已合并 PR 里新增的测试藏起来，判分时放回去运行。FAIL_TO_PASS 一组修复前失败、修复后应通过，相当于复现测试；PASS_TO_PASS 一组原本就通过、修复后仍应通过，相当于防回归的那 5 个测试。逐步看一遍：

SWE-bench 的分数能说明多少

主张
它用真实仓库的真实 issue、真实测试，比写小函数更接近工程实践；分数从 2023 年的不到 2% 涨到 2026 年的 80% 以上，说明模型的工程能力有了质的飞跃。
质疑
一是污染。“SWE-bench 幻觉”研究（2025）发现，模型只看 issue 描述、不看代码，就能以很高的准确率说出该改哪个文件。同一个模型换到 SWE-bench Pro，分数常常大幅下降：据报道 Claude Opus 4.5 在 Verified 上 80.9%，在 Pro 上 45.9%。二是误放。SWE-bench+（2024-10）检查了 SWE-agent 加 GPT-4 判为解决的 251 个补丁：32.67% 的答案就写在 issue 或评论里，31.08% 靠测试太弱才通过；去掉这两类，解决率从 12.47% 降到 3.97%。PatchDiff（ICSE 2026）在 Verified 上发现，7.8% 的“通过”补丁过不了开发者的完整测试集，29.6% 的行为和参考补丁不同，合计让解决率虚高约 6.2 个百分点。
现在怎么看
Verified 的高分主要说明模型在熟悉的公开仓库上很强；更难污染的 Pro、Terminal-Bench 和私有代码库更能反映真实水平。看分数要同时看评测版本、harness 和推理预算（第 章），并记住它出自一个误放率不为零的验证器。

多采样加测试筛选：验证器的天花板

既然每次输出都不同，最直接的办法是多采几个，挑一个能通过测试的。这种采样加筛选（generate-and-filter）在编程里格外好用，因为测试是现成的验证器（对比第 章没有验证器时的多数投票）。AlphaCode（2022）把它推到极致：每道竞赛题采样上百万个程序，用题面的样例测试过滤掉约 99%；剩下的再用专门训练的模型生成新输入，把输出相同的程序归为一类，从最大的类开始各挑一个，凑满 10 次提交。在 10 场各有 5000 人以上参赛的 Codeforces 比赛里，它平均排在前 54.3%。

采样越多越好吗？测试完美时是：成功率就是 pass@k，一直涨向 100%。测试不完美时，答案藏在精确率里：

\[ P(k) = \htmlClass{c-adv}{\underbrace{\frac{\htmlClass{sym-p}{p}}{p + \htmlClass{sym-w}{w}}}_{\pi}}\,\Big(1 - (1 - p - \htmlClass{sym-w}{w})^{\htmlClass{sym-k}{k}}\Big),\qquad \htmlClass{sym-w}{w} = (1-p)\,\htmlClass{sym-phi}{\varphi} \] 采 k 个，在通过测试的补丁里随机提交一个；一个都没通过就放弃

\(p\)

\(w\)

\(\varphi\)
误放率
\(k\)

\(p = 0.3\)、\(\varphi = 0.1\)：\(w = 0.07\)，\(\pi = 0.3/0.37 = 81.1\%\)。\(k = 1\)：30%；\(k = 10\)：\(0.811\times(1 - 0.63^{10}) = 80.3\%\)；再多也只到 81.1%。完美验证器下 pass@10 是 97.2%。一道难题 \(p = 0.05\)：\(\pi = 0.05/0.145 = 34.5\%\)，通过测试的补丁里将近三分之二是错的。

一批题目难度不同，难题的 \(\pi\) 低，采样多了反而会“找到”更多骗过测试的错误补丁。下面的演示把一批难度参差不齐的题放在一起：

采样加筛选的成功率，以及为什么会有最佳采样数

第 1 步，一个样本的三种结局。正确（概率 \(p\)，假设正确的补丁总能通过测试）；错误但通过测试（\(w = (1-p)\varphi\)）；不通过（\(1 - p - w\)）。各样本独立。

第 2 步，至少一个通过。\(k\) 个样本全不通过的概率是 \((1-p-w)^k\)，所以至少一个通过的概率是 \(1 - (1-p-w)^k\)。

第 3 步，挑出来的那个对不对。在“这个样本通过了”的条件下，它正确的概率是 \(p/(p+w) = \pi\)，而且每个通过的样本各自独立地满足这一点。从通过的样本里随机挑一个，它正确的概率就是 \(\pi\)，与通过了几个无关。两步相乘就是 \(P(k) = \pi\big(1 - (1-p-w)^k\big)\)，\(k\to\infty\) 时趋于 \(\pi\)。

第 4 步，一批难度不同的题。第 \(i\) 题的单次正确率为 \(p_i\)。整体成功率是各题的平均，天花板是 \(\mathbb E_i[\pi_i]\)；提交了错误补丁的比例是 \(\mathbb E_i\big[(1-\pi_i)\big(1 - (1-p_i-w_i)^k\big)\big]\)。难题的 \(p_i\) 小，\(\pi_i\) 也小：\(k\) 小时它们没有补丁通过（放弃），\(k\) 大时就冒出一个骗过测试的错误补丁。所以成功率早早饱和，错误提交却一直增加。

第 5 步，错误提交有代价时。修好一题得 1、提交错误补丁得 \(-c\)、放弃得 0，净收益 \(U(k) = \text{成功率}(k) - c\cdot\text{错误提交率}(k)\)。前者饱和得快，后者涨得久，\(U\) 在有限的 \(k\) 处最大：演示的默认设定（平均单次正确率 30%、误放率 5%、\(c = 1\)）下约为 8。Stroebl 等（2024）用真实数据测过：拿 HumanEval、MBPP 原版的测试当验证器、扩充后的测试当标准答案，较弱的模型误放率更高，再怎么多采样也追不上 GPT-4o 的单次正确率；考虑错误提交的代价，最佳采样数往往不到 10。AlphaCode 的聚类则相当于在测试之外再加一个验证器：正确的程序在新输入上行为一致、聚成大类，错误的各错各的。

这个推导告诉我们：有了测试，多采样的收益由验证器的精确率封顶，而不是由模型能不能“偶尔写对一次”决定。想让多采样继续有效，就要同时提高验证器的质量：更多、更有针对性的测试，或者再加一层独立的验证。

2025 年的实践印证了这一点。DeepSWE 对每个 SWE-bench Verified 任务跑 16 条轨迹：单条平均 42.2%，16 条里至少一条对的（pass@16）71.0%，用两个验证器（一个模型生成更多测试来跑，另一个模型直接读补丁打分）挑一条交上去是 59.0%。从 71.0 到 59.0 的 12 个百分点，就是验证器的不完美。

每一代在修什么：从补全到后台智能体

AI 编程的形态换了五代。每一代都把人从循环里往外挪一步，修掉上一代“人”这个环节的瓶颈，又留下新的瓶颈；最后剩下的人工环节决定整体能快多少（下一节）。

形态起点卡在哪改了什么代价
补全2021，Copilot打字慢，样板代码多光标处用 FIM 补一行或一段，几百毫秒内出结果只看到附近的代码

第三、四代能成立，一开始靠的是为模型量身定做的工具，即第 章讲的 SWE-agent 的智能体-计算机接口。到 2025 年，模型本身被 RL 训练得会用命令行了，接口的重要性随之下降：mini-SWE-agent 只给模型一个执行命令的工具，核心代码约 100 行，据其介绍在 Verified 上超过 74%。这是苦涩的教训的又一个例子：精心设计的外部结构，被更强的模型取代。

2025 年 2 月，Karpathy 提出 vibe coding：完全顺着感觉，用自然语言描述想要什么，接受 AI 生成的所有修改，不读代码，出错了就把报错贴回去。它等于把审查这一环直接删掉，风险全部交给测试和运气，适合一次性的原型和个人小工具；需要长期维护、涉及安全的软件，大多数团队仍是“规格先行、AI 实现、人审查”。

第五代的标志是“长时间”：在云端沙盒里、不需要人盯着、连续工作几小时到几周的后台编程智能体。几个有数字的例子：

  • OpenAI 称，GPT-5-Codex（2025-09）在内部测试中曾在大型任务上连续独立工作 7 小时以上，反复改写实现、修复失败的测试。
  • Cursor 在 2026-01 的博客中称，数百个智能体并行运行近一周，从零写出一个浏览器，代码超过 100 万行。“平起平坐、靠锁协调”的方案失败了（20 个智能体的产出只相当于两三个），改成“规划者拆任务、工作者各自完成”才跑起来。
  • Anthropic 的研究员（2026-02）让 16 个并行的 Claude Opus 4.6 在两周、约 2000 个会话里写出一个约 10 万行的 Rust 版 C 编译器，能为 x86、ARM、RISC-V 编译 Linux 6.9，读入约 20 亿 token、写出 1.4 亿 token，花费不到 2 万美元。作者的头号经验是：智能体会自主地去解决你给它的任何问题，所以验证器必须近乎完美，否则它会解决一个错的问题。编译内核无法拆分，16 个智能体总撞上同一个 bug；解法是拿 GCC 当参考答案：随机让大部分文件用 GCC 编译，出错就定位到剩下的那一小部分。局限也明显：生成的代码比 GCC 慢，加新功能时常弄坏已有功能。

这和「从零开始」里的精确率是同一件事：智能体自主运行得越久，“改了再跑”的循环转得越多，最终质量越接近验证器的精确率，而不是模型的单次正确率。长时间智能体能走多远，首先取决于有没有一套近乎完美的测试或参考实现。

实际效果：快了还是慢了

早期的研究几乎都报告了大幅提速：GitHub 2023 年的随机对照试验中，用 Copilot 写一个 HTTP 服务器快了 56%；Google 2024 年的内部实验约快 21%。各大公司也宣称有相当比例的新代码由 AI 生成（Google 称超过四分之一，微软称 20–30%）。但“写了多少代码”不等于“快了多少”。测因果的标准做法是随机对照试验（randomized controlled trial, RCT）：随机决定谁（或哪个任务）用 AI，再比较结果；随机保证两组在任务难度、开发者水平这些看不见的因素上平均相同。2025 年 7 月，METR 的一项随机对照试验得出了相反的结论。

AI 编程工具让资深开发者更快了吗

METR 2025
16 位资深开源开发者在自己熟悉的大型仓库（平均 2.2 万星、超过百万行）中完成 246 个真实任务，每个任务随机决定能否使用 AI 工具（当时主要是 Cursor 加 Claude 3.5/3.7 Sonnet）。结果：允许用 AI 时任务耗时多了 19%（95% 置信区间 +2% 到 +39%）；而开发者事前预计会快 24%，事后仍认为自己快了 20%。
为什么
大量时间花在写提示、等待、审查和修正 AI 的输出上；资深开发者在熟悉的代码库里本来就快、要求又高，AI 的建议常不符合项目的隐含约定。早期“快 56%”的实验是从零写小程序，情况完全不同。
2026 年的更新
METR 在 2026-02 称原结论已经过时，提速如今很可能存在，但新数据不可靠。新一轮试验（2025-08 起，57 位开发者、800 多个任务）的点估计已转向提速：回来参加的 10 位原受试者用 AI 时任务耗时 −18%（置信区间 −38% 到 +9%），新招的 47 位 −4%（−15% 到 +9%），两个区间都包含 0。METR 认为这很可能低估了提速，原因是选择效应：越来越多的开发者不愿“一半任务禁用 AI”而拒绝参加；30%–50% 的受试者承认，不想禁用 AI 去做的任务干脆不报上来；报酬也从每小时 150 美元降到 50 美元；同时开好几个智能体的人，耗时没法准确记录。METR 正在重新设计研究。把这次更新说成“结论反转”也不准确：METR 只说提速很可能存在，没说有多大。
现在怎么看
效果强烈依赖任务类型、代码库熟悉程度和工具成熟度：从零写小程序、陌生代码库、样板代码，提速明显；熟悉的大型代码库中的复杂修改，收益不确定。“感觉快了”不是可靠的测量；人人离不开 AI 时，“随机禁用 AI”这种测量方法本身也开始失效。

一个简单的模型可以解释为什么“写代码变快了”与“整件事变慢了”可以同时成立。它是计算机体系结构里阿姆达尔定律（Amdahl's law）的一个变体：只加速一部分工作时，整体加速的上限由没被加速的那部分决定。

\[ T_{\text{用 AI}} = (1 - \htmlClass{sym-f}{f}) + \frac{f}{\htmlClass{sym-s}{s}} + \htmlClass{c-adv}{\htmlClass{sym-o}{o}} \]
以不用 AI 时的总时间为 1：写代码占 \(f\)，AI 把这部分加速 \(s\) 倍，其余工作不变，但多出了新的开销 \(o\)。只要 \(o > f(1 - 1/s)\)，总时间就超过 1。
\(f\)
写代码占总时间的比例；其余是理解需求、读代码、调试、沟通
\(s\)
AI 对写代码这部分的加速倍数
\(o\)
新增开销：写提示、等待、审查和修正 AI 的输出
\(f = 0.3\)，\(s = 5\)，没有开销时总时间 \(0.7 + 0.06 = 0.76\)，快了 24%。若审查和修正占去 0.3，总时间 \(1.06\)，反而慢了 6%。即使 \(s\) 无穷大，加速也不超过 \(1/(1 - f) = 1.43\) 倍（阿姆达尔定律）。

开销 \(o\) 不是常数：审查 AI 写的代码，时间大致和它写了多少成正比。代进去，结论更尖锐：

\[ T = (1 - f) + f\Big(\frac{1}{s} + \htmlClass{c-adv}{\htmlClass{sym-rho}{\rho}}\Big) \quad\Longrightarrow\quad \text{写代码这部分的加速} = \frac{1}{1/s + \rho} \;<\; \frac{1}{\rho} \]
把开销写成 \(o = \rho f\)：审查并修正 AI 的代码，花的时间是自己写这些代码的 \(\rho\) 倍。于是 AI 再快（\(s\to\infty\)），写代码这部分也最多快 \(1/\rho\) 倍。
\(\rho\)
审查比：审查并修正 AI 写的代码所需时间，除以自己写同样代码所需时间
\(\rho = 0.5\)（审查要花自己写的一半时间）：写代码这部分最多快 2 倍；\(f = 0.3\)、\(s = 5\) 时总时间 \(0.7 + 0.3\times 0.7 = 0.91\)，只快 9%。\(\rho = 1\)（审查和自己写一样慢）：总时间 1.06，就是上面那个“慢了 6%”。
阿姆达尔定律用于开发效率：上限、盈亏点与审查瓶颈

第 1 步，基本式与盈亏点。把不用 AI 时的总时间记为 1，分成写代码 \(f\) 和其它 \(1-f\)。用 AI 后 \(T = (1-f) + f/s + o\)，加速比 \(S = 1/T\)。\(T < 1\) 等价于 \(o < f(1 - 1/s)\)：\(f = 0.3\)、\(s = 5\) 时开销不能超过 0.24。资深开发者在熟悉的代码库里 \(f\) 本来就小，留给开销的余地也小。

第 2 步，上限。令 \(s\to\infty\)：\(S \le 1/(1 - f + o) \le 1/(1-f)\)。没被加速的部分成了天花板。

第 3 步，审查与代码量成正比。令 \(o = \rho f\)，\(T = (1-f) + f(1/s + \rho)\)。写代码这部分的有效加速 \(1/(1/s + \rho)\) 在 \(s\to\infty\) 时趋于 \(1/\rho\)；要比自己写快，需要 \(\rho < 1 - 1/s\)。AI 写得越快，瓶颈越落在 \(\rho\) 上。

第 4 步，并行智能体也绕不过它。一个人同时派出 \(n\) 个后台智能体，写代码的墙钟时间变成 \(f/(sn)\)，但审查仍由这一个人串行完成：\(T \to (1-f) + \rho f\)。\(f = 0.5\)、\(\rho = 0.3\) 时，派出再多智能体也最多快 \(1/0.65\approx 1.54\) 倍。审查成了阿姆达尔定律里“不能并行的部分”。

第 5 步，怎样降低 \(\rho\)。\(\rho\) 由“人要多仔细才放心”决定。测试、类型检查、静态分析越可靠（误放率 \(\varphi\) 越低），人越可以只看测试结果和关键改动；vibe coding 等于直接令 \(\rho = 0\)，把全部风险交给误放率。

这个推导告诉我们：AI 让写代码变得多快，整体收益都被两样东西封顶：没被加速的工作，和审查 AI 输出的时间。后者随代码量增长，并行也绕不过去。所以 AI 编程时代真正的杠杆是自动化的验证：它同时降低 \(\rho\) 和 \(\varphi\)。

代码质量与安全

另一个问题是生成的代码本身。Pearce 等（2021）发现 Copilot 在安全相关场景中生成的程序约 40% 含漏洞；Veracode 2025 年用 80 个任务测试一百多个模型，约 45% 的生成代码含安全缺陷（Java 超过 70%），且没有随模型变新、变大而明显下降。这些代码能运行、甚至能通过功能测试：功能测试测不出安全漏洞，安全需要另一类验证器（静态分析、模糊测试、安全审查）。

新的风险也随之出现。模型会“幻觉”出不存在的软件包名：Spracklen 等（USENIX Security 2025）用 16 个模型生成 57.6 万段代码，商业模型推荐的包里平均至少 5.2% 不存在，开源模型 21.7%，共出现 20.5 万个不同的虚构包名。攻击者抢先注册这些名字、放入恶意代码，等别人照着 AI 的建议安装，这叫 slopsquatting。仓库统计还显示，AI 普及后重复代码和短期内被改回的代码比例上升。

这些问题与第 章的结论一致：让错误能被发现，比让每一步更准更重要。测试、类型检查、静态分析、代码审查，在 AI 编程时代不是更不重要，而是更重要了。

常见误解

  • SWE-bench 80% 意味着 AI 能完成 80% 的工程工作。它测的是公开仓库中描述清楚、有测试覆盖的修复任务；需求理解、设计、沟通、长期维护都不在其中，更难污染的评测上分数低得多。
  • 能通过测试的代码就是正确的。测试只覆盖部分情况：SWE-bench Verified 上约 30% 的“通过”补丁行为与参考答案不同。RL 训练出的模型还可能专门针对测试取巧。
  • 多采样几次、多试几轮，总能修好。只要测试会误放，成功率的上限就是验证器的精确率 \(p/(p + (1-p)\varphi)\)。采样越多，越容易“找到”骗过测试的错误补丁。
  • 感觉快了就是真的快了。METR 2025 年的试验中，开发者实际慢了 19% 却以为快了 20%。
  • AI 写的代码比人写的更安全，因为它见过最佳实践。它也见过大量有漏洞的代码；多项测试显示四成左右的生成代码含安全缺陷。

在 GPT-3 系列上用 159 GB GitHub 代码继续训练出 Codex；用单元测试判对错、用 pass@k 汇报；Copilot 把补全带进编辑器。
代价
只能写独立的短函数；采 100 次能写对的题，没有测试就挑不出来（77.5% 对 44.5%）。
引出
用测试来挑，大量采样能走多远？
退居小众基于搜索和形式规格的程序合成
从示例或形式规格中搜索程序的传统方法基本退出了通用编程，但“形式规格 + 验证”在数学证明和安全关键软件中重新受到重视（第 章）：形式化证明是误放率为零的验证器。
2022

AlphaCode 与中间填空：大量采样，用测试筛选

卡在哪
竞赛题需要真正的算法设计，单次采样几乎做不出；补全需要看到光标后面的代码。
怎么解决
AlphaCode 每题采样上百万个程序，用测试过滤、聚类后提交 10 个，平均排前 54.3%；FIM 让模型学会填空。
代价
每题百万次采样，成本极高；只在规格清晰、测试充分的题上成立；模型闭源。
引出
开源社区能否追上，评测能否走出函数级的小题？
仍在发展竞赛编程：从中位数到金牌
2025-09 的 ICPC 世界总决赛上，OpenAI 和 Google DeepMind 的推理模型分别解出 12 题中的 12 题和 10 题，达到金牌水平。三年间的变化是 RL：采样和筛选从推理时挪进了训练时，模型在长思维链里自己生成、检验、修正（第 章）。但竞赛题规格清晰、可完全测试，和真实工程差距仍大。
2023

卡在哪

2023 年流行为代码单独训练中小模型。到 2025 年，最好的编程模型几乎都是通用前沿模型，代码专用模型多是通用模型的代码增强版（如 Qwen3-Coder）或为补全延迟优化的小模型。
2024

智能体：让模型自己探索、自己运行

卡在哪
一次性的“检索 + 生成”在仓库级任务上几乎无效。
怎么解决
Devin（2024-03，在随机抽取的四分之一题目上自报 13.86%）、SWE-agent（2024-05，全集 12.5%）把智能体循环用到修 issue 上；Claude 3.5 Sonnet（2024-06）等模型带来跃升；SWE-bench Verified（2024-08）提供可信的 500 题。

引出
能不能直接在这种循环里训练模型？
争论Agentless：到底需不需要智能体
Agentless（2024-07）认为模型还不可靠，不该让它决定下一步：固定成“分层定位、生成多个补丁、用测试挑选”三步，在 SWE-bench Lite 上以每题 0.34 美元做到 27.3%，超过当时所有开源智能体。结局是各对一半：智能体 RL 之后自主循环成为主流；固定流水线留作便宜的基线和 RL 的脚手架（SWE-RL 用的就是它的简化版）。

争论随机对照试验还测得出生产力吗
METR 2026-02 的新一轮点估计转为提速，但它自己判定数据不可靠：最依赖 AI 的开发者和任务，恰恰因为不愿禁用 AI 而退出了试验。按任务随机分配的设计在 AI 普及之后系统性地漏掉了效果最大的部分，这是“测量跟不上能力”的一个缩影（第 章）。

自测

1. 每题采样 \(n = 20\) 次，某题通过了 \(c = 4\) 次。它的 pass@1 和 pass@5 估计值是多少？
pass@1 \(= 4/20 = 0.2\)。pass@5 \(= 1 - \binom{16}{5}/\binom{20}{5} = 1 - 4368/15504\approx 0.718\)。
2. 模型单次写出正确补丁的概率是 40%，测试的误放率是 20%。采样 16 个补丁、在通过测试的里随机交一个，成功率约多少？和 pass@16 相比如何？误放率要降到多少，成功率才能到 90%？
\(w = 0.6\times 0.2 = 0.12\)，\(\pi = 0.4/0.52\approx 76.9\%\)。\(P(16) = 0.769\times(1 - 0.48^{16})\approx 76.9\%\)（\(0.48^{16}\approx 8\times 10^{-6}\)，几乎肯定有补丁通过）。pass@16 \(= 1 - 0.6^{16}\approx 99.97\%\)，差了 23 个百分点，全部来自误放。要 \(\pi\ge 0.9\)：\(0.4\ge 0.9\times(0.4 + 0.6\varphi)\)，即 \(\varphi\le 0.04/0.54\approx 7.4\%\)。
3. 一个编程 RL 环境里，认真修一次修好的概率是 30%，没修好的“近似”补丁有 20% 能混过测试；测试文件对智能体可写，判分前也不恢复。训练下去会发生什么？给出两种修法，并说明为什么“多加隐藏测试”不在其中。
认真修的通过率 \(0.3 + 0.7\times 0.2 = 0.44\)，改测试的通过率是 1。策略梯度的终点是通过率最高的做法，模型迟早会学会改测试；它起初越罕见，潜伏期越长（约 \(1/(\alpha\,\pi_H(0)\times 0.56)\) 步），但一定会发生。修法：判分前恢复测试文件或设为只读；检查补丁是否改了测试文件，改了即判 0 分；用模型或规则审查轨迹。隐藏测试只压低偷懒补丁的误放率，改测试的做法连判分方式一起改掉了，通过率与测试数无关。
4. 一个开发者写代码占 30% 的时间，AI 把这部分加速 5 倍，但审查和修正 AI 输出新增了相当于原总时间 30% 的工作。整体是快了还是慢了？开销降到多少以下才不吃亏？
\(0.7 + 0.3/5 + 0.3 = 1.06\)，慢了 6%。不吃亏要求 \(o < f(1 - 1/s) = 0.3\times 0.8 = 0.24\)。如果把开销看成与代码量成正比（审查比 \(\rho = 1\)），AI 再快也没用：写代码这部分的加速 \(1/(1/s + \rho)\) 永远小于 1。

必读

  1. Evaluating Large Language Models Trained on Code（Chen 等, 2021）Codex、HumanEval 与 pass@k 无偏估计；“写得出”和“挑得出”的差距最早就记录在这里。
  2. Efficient Training of Language Models to Fill in the Middle（Bavarian 等, 2022）FIM 为什么“免费”、为什么事后补很贵。
  3. Competition-Level Code Generation with AlphaCode（Li 等, 2022）采样加筛选的极致做法；那张误放率表是理解“测试有多可靠”的起点。
  4. SWE-bench（Jimenez 等, 2023）把评测带到真实仓库，以及“塞进更多上下文反而更差”的发现。
