AI 编程：从补全一行到独立完成任务

编程是大模型最成功、也最被认真测量的应用，因为代码有天然的验证器：测试。但测试会漏。这一章用一个量贯穿始终，即测试的误放率，看它怎样给“改了再跑”、RL 的奖励、多采样筛选和评测分数各设天花板；也讲代码模型怎样训练，以及 AI 让开发者快了还是慢了。

智能体在编程上落地最早，编程也是可验证奖励最丰富的来源。上一章留下三个问题：代码模型怎样训练，评测为什么一再饱和，开发者快了还是慢了。三个答案都绕不开“测试”这个验证器有多可靠。

  • 策略梯度、RLVR、钻奖励空子、pass@k：第 章
  • 自回归生成：第 章；特殊 token：第 章；数据去重与许可：第 章
  • 不需要软件开发背景。下面「从零开始」一节会把仓库、issue、单元测试、补丁、回归这些概念从零讲一遍。

从零开始：一个 bug 的一生

用一个三文件的玩具仓库和一个 bug，跟着编程智能体走完“定位、复现、修改、跑测试、读报错、再修改”，顺便把后面要用的概念讲一遍。熟悉软件开发的读者可以跳到「为什么“能跑测试”是关键」，那里定义的误放率和精确率贯穿全章。

一个三文件的仓库和一个 issue

代码仓库（repository）是一个项目的全部文件加上修改历史。玩具仓库“小统计”只有三个文件：core.py 里有求平均数和中位数的两个函数；cli.py 让用户在命令行调用它们；test_core.py 是测试。

某天一位用户提交了一条 issue（问题报告）：“对 4、1、3、2 求中位数，返回 3，应该是 2.5。”issue 是开源项目里报告 bug 的标准方式，也就是智能体拿到的任务描述。

test_core.py 里有 5 个单元测试（unit test）：每个给函数一个固定输入，断言输出等于期望值，相等就“通过”，否则“失败”并打印哪里不对。它们检查：三个数的平均数、负数的平均数、3、1、2 的中位数是 2、一个数的中位数、空列表会报错。

bug 在哪？中位数函数先排序，再取长度一半（向下取整）处的数。奇数个数时正确；偶数个数时应取中间两个数的平均，它却只取了靠后的那个。测试实际检查到了哪些输入和代码路径，叫测试覆盖（test coverage）。所有中位数用例都是奇数个数，“偶数”这条路径没被覆盖，所以测试全部通过，bug 照样存在。

第 1–3 步：定位，以及“测试全过了”

开工前，上下文里有约 3000 个 token 的系统提示（行为规范和四个工具的说明：搜索、读文件、改文件、运行命令），加上约 100 个 token 的 issue，即第 章的初始上下文 \(C_0 \approx 3100\)。

  1. 模型搜索“median”这个名字，工具返回一行：core.py 第 18 行（约 60 个 token）。
  2. 读 core.py 全文，返回约 520 个 token。模型在第 22 行看到了“取长度一半处的元素”。
  3. 先运行已有的测试，返回“5 个通过”（约 80 个 token）。

前两步叫定位（fault localization）：从问题描述找到该改的文件和行。真实仓库有成千上万个文件，定位往往最难，把“可能相关”的文件一股脑塞进上下文效果很差（下一节有数字）；智能体和人一样搜索、跳转，只读需要的几十行。第 3 步是整章的伏笔：测试全过了，bug 还在。

第 4–5 步：先复现，再动手

有经验的开发者修 bug 之前，先写一个复现测试：能稳定触发这个 bug、因此现在一定失败的测试。智能体照做：

  1. 在 test_core.py 末尾加一个测试：4、1、3、2 的中位数应为 2.5（工具返回“已写入”，约 30 个 token）。
  2. 运行它，失败：“期望 2.5，实际得到 3”，连同出错位置约 260 个 token。

复现测试确认理解了问题，给出一个会从“失败”变成“通过”的信号，修好后还留下来防止复发。

第 6–9 步：改、跑、读报错、再改

对代码的一组修改叫补丁（patch，也叫 diff）：记录在哪个文件删掉了哪几行、加上了哪几行。把补丁提交给维护者审查、合并的请求，叫拉取请求（pull request, PR）。

  1. 模型改写中位数函数：偶数个时取中间两个数的平均。但它用“长度除以 2”算下标，得到的是小数 2.0。
  2. 运行测试，报错：“下标必须是整数，不能是小数”，附带出错的那一行（约 300 个 token）。
  3. 模型读懂了报错，把除法改成整除。
  4. 运行全部测试：6 个通过（原来的 5 个加上新写的 1 个）。
  5. 写一段总结，不再调用工具，循环结束。

第 7 步里，运行结果（通过、失败、报错信息）回到了模型的上下文，这叫执行反馈（execution feedback）：报错指出了哪一行、什么原因，模型第二次就改对了。第 9 步里原来的 5 个测试确认没弄坏原有功能；弄坏原有功能叫回归（regression）。

算一笔账：10 次模型调用，4.4 万个 token

每一轮模型都要把整个上下文重读一遍，再写出一小段。10 轮加起来（示意值）读入约 4.4 万 token、写出约 1100，约 40 比 1，是第 章“上下文的账”的一个实例（\(n = 10\)、\(\Delta\approx 250\)，\(nC_0 + n^2\Delta/2\approx\) 4.3 万；前缀缓存的折扣也在那一章）。真实任务大一到两个数量级：Qwen3-Coder-Next 的技术报告（2026-03）记录，RL 训练中平均每个任务的轮数从 50 涨到 130。

更要紧的是：10 次调用里有 4 次在跑测试。跑一次只花几秒 CPU，却给出最有用的信息：第 3 步说明测试没覆盖这里，第 5 步确认了 bug，第 7 步抓住了自己引入的新错误，第 9 步确认修好且没有回归。

为什么“能跑测试”是关键

没有运行代码的工具，智能体只能在第 6 步交出那个错误的第一版；能跑测试，错误就在第 7 步被抓住、第 8 步被改正。第 章「长任务为什么难」把这写成了“检查并重试”的等比级数：每次尝试以概率 \(p\) 做对，做错时以概率 \(r\) 被发现、触发重做；不限重试次数时，最终做对的概率是 \(p/\big(p + (1-p)(1-r)\big)\)。

在编程里，检查就是测试，而测试会漏。一个错误的补丁仍然通过全部测试的概率，叫误放率（false-pass rate），记作 \(\varphi\)，它就是上式里的 \(1 - r\)。玩具仓库原来的 5 个测试，对“偶数个数取错”的误放率是 100%。

能自动判断输出对不对的程序都叫验证器（verifier）：单元测试、编译器、类型检查、证明检查器。测试通常不冤枉正确的补丁，但会放过一部分错误的。（测试过窄时也会拒掉写法不同的正确补丁，OpenAI 2026-02 审查 SWE-bench Verified 时发现这类缺陷不少，见第 章；本章的模型忽略这种情形。）上面的极限换个角度看，正是“通过测试的补丁里真正正确的比例”，即验证器的精确率（precision），记作 \(\eta\)（\(\pi\) 留给策略）：

\[ \htmlClass{c-adv}{\htmlClass{sym-eta}{\eta}} = P(\text{真正正确}\mid\text{通过测试}) = \frac{\htmlClass{sym-p}{p}}{\htmlClass{sym-p}{p} + (1 - \htmlClass{sym-p}{p})\,\htmlClass{sym-phi}{\varphi}} \] 贝叶斯公式：通过测试的补丁有两个来源，正确的（全部通过）和错误但溜过去的
在所有通过测试的补丁里，正确的占 \(p\) 那么多，错误但骗过了测试的占 \((1-p)\varphi\) 那么多。前者占总数的比例，就是“测试说通过”这句话的可信度。
\(\eta\)
验证器的精确率：通过测试的补丁里真正正确的比例
\(p\)
模型一次尝试写出正确补丁的概率
\(\varphi\)
误放率：一个错误补丁通过全部测试的概率（第 章的检出率 \(r\) 等于 \(1-\varphi\)）
\(p = 0.6\)、\(\varphi = 0.1\)：\(\eta = 0.6/(0.6 + 0.04) = 93.75\%\)。按第 章的式子，允许重试 1 次时做对的概率是 \(0.6\times(1 + 0.36) = 81.6\%\)，重试 2 次 89.4%，不限次数就到 93.75% 为止。测试只能抓住一半错误（\(\varphi = 0.5\)）时，天花板降到 75%；完全没有测试（\(\varphi = 1\)）时，停在 \(p = 60\%\)。

换成分类指标的说法：误放率是假阳性率，精确率就是 precision。它随 \(p\) 变是基率效应：同一套测试用在难题上，“通过”更不可信。

这个量在「测试当奖励」和「多采样加测试筛选」里还会出现：只要 \(\varphi\) 不为 0，无限重试、无限采样也到不了 100%。

代码模型怎样训练

2021 年的 Codex 是在 GPT-3 系列模型上用 159 GB 的 GitHub Python 代码继续训练得到的（最大 12B 参数），GitHub Copilot 最初用的就是它。同等规模、没练过代码的 GPT 模型在 HumanEval（Codex 论文发布的 164 道手写 Python 函数题，平均每题 7.7 个单元测试）上一道也做不出，Codex 一次采样能做对 28.8%。此后代码数据成为所有大模型预训练的标配（第 章）。与普通文本相比，代码训练有两个专门的设计。

中间填空。写代码时，光标常常在文件中间：上面有代码，下面也有代码。普通的自回归模型只能看左边。中间填空（fill-in-the-middle, FIM, Bavarian 等, 2022）在训练时把一部分文档重新排列：

\[ \underbrace{\text{前缀}\ \ \text{中间}\ \ \text{后缀}}_{\text{原始文档}} \ \longrightarrow\ \htmlClass{c-new}{\langle\text{PRE}\rangle}\,\text{前缀}\,\htmlClass{c-new}{\langle\text{SUF}\rangle}\,\text{后缀}\,\htmlClass{c-new}{\langle\text{MID}\rangle}\,\htmlClass{c-adv}{\text{中间}} \]
随机挑一段作为“中间”，把它挪到最后，用三个特殊 token 标出各部分。模型仍然只是从左到右预测下一个 token，但预测中间那段时，已经看过了前缀和后缀。
原文 “def area(r):⏎ return 3.14 * r * r⏎print(area(2))”，选中间为 “return 3.14 * r * r”。重排后：⟨PRE⟩def area(r):⏎ ⟨SUF⟩⏎print(area(2))⟨MID⟩return 3.14 * r * r。模型生成中间段，直到输出一个表示“已经接上后缀”的结束 token。

论文发现，把 50% 乃至 90% 的训练文档这样变换，从左到右的能力都看不出损失，100% 时才变差。为什么几乎“免费”？三段各自的内部仍是逐 token 从左到右预测，语法、变量名、紧邻几百个 token 的局部规律，练的次数一点没少；变的只是全局的注意力模式（后缀看不到中间，中间能看到两头），留一部分文档不变，两种模式就能并存。事后用微调补上则贵得多，所以 2022 年以后的代码模型几乎都从预训练起带上 FIM。切分点要在字符级别随机选，因为光标常停在词中间：按行切分的模型这时几乎完全失败，按 token 切分的也差得多。

中间填空为什么几乎“免费”，又为什么不能事后补

第 1 步，不是新目标。同一份文档的概率可以按不同顺序用链式法则拆开：

\[ \begin{aligned} \text{从左到右：}\ p(\text{文档}) &= p(\text{前})\;p(\text{中}\mid\text{前})\;p(\text{后}\mid\text{前},\text{中}) \\ \text{中间填空：}\ p(\text{文档}) &= p(\text{前})\;p(\text{后}\mid\text{前})\;p(\text{中}\mid\text{前},\text{后}) \end{aligned} \]

两者都是精确的等式，描述同一个联合分布，最大似然的目标都是“让真实文档的概率尽量大”，原则上不冲突：足够强的模型可以把两种分解都学对。真实模型容量有限，做不到：论文在同一批文档上比较，填空排法的困惑度总是更高，跳过一段不知道的内容去预测后面本来就更难。所以问题只在有限的容量怎样分给两种模式。

第 2 步，数一数“上下文完全一样”的 token。设变换比例为 \(f\)。没被变换的文档（占 \(1-f\)）是普通训练；被变换的文档里，前缀（平均三分之一）的上下文也和普通训练一样。所以上下文完全相同的 token 比例是 \((1-f) + f/3\)：\(f = 0.5\) 时 2/3，\(f = 0.9\) 时只有 0.40。可 \(f = 0.9\) 时从左到右的损失照样不变，“免费”不是因为大部分 token 没被动过。

第 3 步，局部没变，变的是全局。论文的解释：三段中的每一段内部仍是从左到右逐 token 预测，相当于把一篇文档切成三篇短文档，局部的预测任务完全一样；变的只是全局的注意力模式。大部分预测能力来自局部上下文，这部分一点也没少练。

第 4 步，为什么 100% 会变差，事后补为什么贵。\(f = 1\) 时，模型从没练过 \(p(\text{后}\mid\text{前},\text{中})\) 这种“看完前文接着往下写”的条件概率，而普通生成要的恰恰是它；留 10% 的文档保持原样就够了。反过来，在训好的从左到右模型上用微调补上填空能力，要大得多的算力和较大的学习率，作者猜测是预训练形成的全局注意力模式已经定型。

这个推导告诉我们：中间填空只是同一个分布换了一种分解顺序；它占用的是“全局注意力模式”的一点容量，局部的逐 token 预测一点也没少练，所以在预训练里加进去几乎免费。“免费”只在从头训练时成立。

仓库级上下文。一个函数的含义要看它在别的文件里的调用者和依赖。DeepSeek-Coder 按依赖关系、StarCoder 2 按仓库分组，把同一仓库的文件拼成长序列来训练，这叫仓库级上下文（repository-level context）。上下文也一路变长（第 章），但放得进去不等于用得好：SWE-bench（下一节讲它的结构）的原论文（2023）里，给 Claude 2 的检索上下文从 1.3 万加到 5 万 token，正确文件被包含的比例从 29.6% 升到 51.1%，解决率却从 1.96% 降到 1.22%。真正的提升来自让模型自己去找、去跑。

整条管线是：预训练混入大量代码，带上 FIM 和仓库级拼接；中期训练换上偏推理和智能体的数据（第 章）；用智能体轨迹做监督微调，学会调用工具；最后在能运行代码的环境里做 RL，即下面几节。

把测试变成奖励：软件工程的 RL 环境

代码可以运行，测试可以判对错，这是第 章 RLVR 最理想的场景。玩具里那 10 轮循环就是一条轨迹，最后测试过没过就是奖励。题目格式大多借自 SWE-bench（2023-10），一个用真实 GitHub 仓库的 issue 出题的评测，结构和玩具仓库一一对应：issue 是任务描述；已合并 PR 里新增的测试先藏起来，判分时放回去运行。FAIL_TO_PASS 一组修复前失败、修复后应通过，即复现测试；PASS_TO_PASS 一组原本就通过、修复后仍应通过，即防回归的那 5 个测试：

最后一步换成“写特例”的补丁，两组测试照样全过，这个漏洞留到下一节。把这种题做成可以大规模采样的训练场，就是软件工程 RL 环境：每道题是一个装好依赖的容器镜像（修复前的仓库）、一段任务描述和一组判分测试。DeepSWE（2025-07）的奖励很典型：5 分钟内两组测试全部通过得 1 分，否则 0 分。

难点在于造题。SWE-Gym（2024-12）从真实 issue 人工整理出约 2400 道题，真实但难以扩大。SWE-smith（2025-04）反过来，自动改坏一个能通过全部测试的仓库，“修回来”就是一道题，从 128 个仓库造出约 5 万道，代价是 bug 的分布和真实 issue 不同。R2E-Gym 等从提交历史里挖“同时改了代码和测试”的提交。

DeepSWE 只用 RL、在 R2E-Gym 的 4500 道题上训练 Qwen3-32B，64 张 H100 训练 6 天、每步开 512 个容器，SWE-bench Verified（人工筛选的 500 道题）的单次通过率从 23% 提到 42.2%；更大的环境规模见第 章。GRPO 在这里同样适用：一组轨迹全对或全错的题没有梯度，所以各家先估计每道题的通过率，筛掉太简单和太难的。Qwen3-Coder-Next 还对超过轮数上限仍未结束的轨迹、格式错误的工具调用额外扣分。

也有不跑代码的做法。Meta 的 SWE-RL（2025-02）的奖励是生成补丁和真实补丁的文本相似度（0 到 1），便宜，能用海量历史 PR，70B 模型在 Verified 上达到 41.0%。代价是它奖励“像参考答案”而不是“能工作”：写法不同的正确修复被扣分，差一个符号的补丁反而得高分。执行奖励奖励能工作的代码，但稀疏、昂贵，还有下一节的误放问题。

测试当奖励：误放率与针对测试取巧

回到玩具仓库。假设智能体在第 6 步交出这样一个补丁：“如果输入正好是 4、1、3、2，就返回 2.5，否则照旧。”它能通过复现测试和原来的 5 个测试。RL 只看奖励，分不清它和真正的修复。这种专门针对测试用例写的分支叫对测试写特例（special-casing），是钻奖励空子在代码里最常见的形式。

补丁按对测试的态度可以粗分四类：（1）认真修，可能修好，也可能差一点；（2）写特例；（3）只修常见情况，漏掉边界；（4）改测试：改测试文件，或让测试框架提前退出。前三类是糊弄测试，多跑一些测试能压低它们的通过率；第四类是改掉判分者，测试再多也没用，只能靠权限。还有一类问题出在环境里：偷答案，比如从 git 历史里翻出官方修复，只能靠隔离。

对付糊弄测试的第一道防线是隐藏测试：判分时额外运行一批智能体看不到的测试。错误补丁能不能混过去，取决于它在多大比例的输入上出错，以及隐藏测试有几个：

\[ \htmlClass{sym-phi}{\varphi} = (1 - \htmlClass{sym-delta}{\delta})^{\htmlClass{sym-m}{m}} \] 假设每个隐藏测试独立地从可能的输入里随机抽取
一个错误的补丁在比例为 \(\delta\) 的输入上会出错。每个隐藏测试有 \(\delta\) 的概率撞上它，\(m\) 个测试全部没撞上，补丁才能骗过去。
\(\varphi\)
这个错误补丁通过全部隐藏测试的概率（误放率）
\(\delta\)
补丁出错的输入所占的比例：写特例的补丁在很大一部分输入上出错，δ 大；只漏了一个边界情况的补丁，δ 很小
\(m\)
隐藏测试的个数
写特例的补丁（下面演示取 \(\delta = 0.6\)）：5 个隐藏测试就把误放率压到 \(0.4^5 = 1\%\)。只修常见情况的补丁（演示取 \(\delta = 0.15\)）：10 个隐藏测试误放率仍有 \(0.85^{10} = 20\%\)，要 29 个才降到 1%；只漏了一个更窄的边界（\(\delta = 0.05\)）时要 90 个。最难抓的是“差一点就对”的补丁。

真实的错误补丁 δ 各不相同，“差一点就对”的越多，随机加测试越不管用：平均误放率按幂律而不是指数下降，测试翻 10 倍可能只降到三分之一（下面第一个推导）。所以有针对性地生成测试比堆数量有效。

RL 会把模型推向哪里？策略梯度只提高期望奖励。奖励是“通过判分”，所以四类做法里哪一类通过的概率最高，模型就越来越偏向哪一类，不管它是不是真修好了：

\[ \underbrace{\htmlClass{sym-p}{p} + (1 - p)\,\htmlClass{sym-phic}{\varphi_{\text{近错}}}}_{\text{认真修的通过率}} \;>\; \max\big(\htmlClass{sym-phiw}{\varphi_{\text{特例}}},\ \htmlClass{sym-phiw}{\varphi_{\text{常见}}},\ \htmlClass{c-clip}{\htmlClass{sym-h}{h}}\big) \] 只有满足这个不等式，RL 才会把模型推向认真修
认真修的通过率，是真修好的概率加上“没修好但误放过去”的概率；它必须高于另外三类做法各自的通过率。
\(p\)
认真修一次真正修好的概率
\(\varphi_{\text{近错}}\)
认真修但没修好时，这个“差一点”的补丁的误放率
\(\varphi_{\text{特例}},\varphi_{\text{常见}}\)
写特例、只修常见情况这两类补丁的误放率，随隐藏测试数 m 下降
\(h\)
改测试这类做法的通过率：测试文件可写、判分前不恢复时为 1，与 m 无关；判分前恢复测试文件时为 0

为什么加测试只能慢慢压低误放率

第 1 步，单个补丁：指数下降。对一个固定的错误补丁，\(\varphi = (1-\delta)^m\) 随测试数指数下降。\(\delta = 0.1\) 时，10 个测试 35%，100 个测试 \(2.7\times 10^{-5}\)。照这样算，几十个测试就够了。

第 2 步，错误补丁各不相同。模型写出的错误补丁是一大批，δ 各不相同，认真修出来的大多“差一点就对”，δ 集中在 0 附近。设 δ 的分布密度正比于 \(\delta^{a-1}\)（\(0 < a \le 1\)，\(a\) 越小，“差一点”的越多），平均误放率是

\[ \begin{aligned} \bar\varphi(m) &= \int_0^1 a\,\delta^{a-1}(1-\delta)^m\,d\delta = a\,B(a,\, m+1) \\ &= \frac{a\,\Gamma(a)\,\Gamma(m+1)}{\Gamma(m+a+1)} \;\approx\; \Gamma(a+1)\, m^{-a} \end{aligned} \]

最后一步用了 \(\Gamma(m+1)/\Gamma(m+a+1)\approx m^{-a}\)（\(m\) 较大时）。

第 3 步，代入数字。\(a = 0.5\)：10 个测试 27%，100 个 8.8%，1000 个 2.8%。测试数每翻 10 倍，误放率只降为约 \(1/\sqrt{10}\approx 1/3.2\)，从指数变成了幂律。平均值被那些 δ 极小的补丁主导，而随机抽取的测试很难撞上它们出错的那一小块输入。\(a\) 的取值只是示意，真实分布没有测量值。

第 4 步，对照实测。AlphaCode（2022）测的是另一个相关的量：取模型“解出”的题，各抽一个解答人工检查，看其中有多少其实是错的。按本章的记号这是 \(1-\eta\)，同时取决于 \(p\) 和 \(\varphi\)，不是 \(\varphi\) 本身。HumanEval 平均每题 7.7 个测试，这个比例是 30%；CodeContests 原始版每题 12.4 个，62%。他们变异已有输入生成新测试、用已知正确的程序核对输出，每题测试增到约 204 个，再丢掉测试过少的题，这个比例降到 4%。方向和推导一致：要靠专门生成的测试，而且要很多。EvalPlus（2023）把 HumanEval 的测试扩充 80 倍，各模型的 pass@k 下降了最多 19.3%–28.9%。

第 5 步，有针对性的测试更有效。既然误放来自 δ 很小的补丁，就直接去找“这个补丁和正确答案在哪个输入上不一样”。PatchDiff（ICSE 2026）为每个通过了 SWE-bench 测试的补丁专门生成区分它与参考补丁的测试，找出了大量随机测试漏掉的差异（数字见评测一节的争议框）。

这个推导告诉我们：如果“差一点就对”的补丁足够多，误放主要来自它们；它们只在很少的输入上出错，随机加测试对它们的杀伤是多项式的而不是指数的。有效的办法是有针对性地生成测试（变异、差分测试），而不是堆数量。也正因为这些补丁最像正确答案，它们是 RL 最容易“学会”的那类偷懒：不是作弊，只是做得不完整，却拿了满分。

玩具模型：为什么罕见的取巧起步慢、之后接管得快

第 1 步，期望梯度。把模型的选择简化成在几种做法之间按 softmax 选，\(\pi_j \propto e^{\theta_j}\)，每种做法有自己独立的参数 \(\theta_j\)：这是关键假设，真实模型的参数是共享的。做法 \(j\) 的期望奖励 \(R_j\) 就是它的通过率，\(J = \sum_j \pi_j R_j\)。把第 章的 \(\nabla J = \mathbb E[R\,\nabla\log\pi_a]\) 和 \(\partial\log\pi_a/\partial\theta_j = \mathbb 1[j=a]-\pi_j\) 代入，对 \(a\) 求期望：\(\partial J/\partial\theta_j = \sum_a \pi_a R_a(\mathbb 1[j=a]-\pi_j) = \pi_j(R_j - J)\)。学习率为 \(\alpha\) 时每步 \(d\theta_j = \alpha\pi_j(R_j - J)\)。

第 2 步，两种做法。只留认真修（C）和改测试（H），记 \(\Delta = R_H - R_C\)。此时 \(R_H - J = \pi_C\Delta\)，\(R_C - J = -\pi_H\Delta\)，所以 \(d\theta_H - d\theta_C = \alpha\pi_H\pi_C\Delta + \alpha\pi_C\pi_H\Delta\)：两项同阶，都不能丢。两种做法的 softmax 满足 \(d\pi_H = \pi_H\pi_C(d\theta_H - d\theta_C)\)，于是

\[ \Delta\pi_H = 2\alpha\Delta\,\pi_H^2\,\pi_C^2 \;\approx\; 2\alpha\Delta\,\pi_H^2 \qquad(\pi_C\approx 1) \]

第 3 步，解方程。把步数看成连续时间，\(d\pi_H/dt = \kappa\pi_H^2\)，\(\kappa = 2\alpha\Delta\)，得 \(1/\pi_H(t) = 1/\pi_H(0) - \kappa t\)，在 \(t^*\approx 1/\big(2\alpha\,\pi_H(0)\,\Delta\big)\) 处急剧上升。演示的设定 \(\alpha = 0.5\)、\(\pi_H(0) = 0.02\)、\(\Delta = 1 - 0.523 = 0.477\)，给出约 105 步；只有这两种做法时，模拟在第 121 步跌破一半。演示里还有另外两种偷懒做法：前 100 步认真修先把它们的概率吸走，改测试也被压到 1.84%（第 50 步），所以拖到第 277 步。

这个推导告诉我们：在这个玩具模型里，奖励最高的做法哪怕起初很罕见也一定胜出，只是先慢后快；只有两种做法时潜伏期和初始概率成反比，多了别的做法，初始概率减半，潜伏期可以长好几倍（2%→1%：277→约 1050 步）。这些步数都是独立参数假设的产物，不是真实训练的规律。

原以为
测试是客观的奖励（第 章说可验证奖励“很难被钻空子”）。
实际发现

评测：从 164 道小题到修真实仓库

早期的评测是“写一个函数”：HumanEval（2021）给出函数签名和说明，用单元测试判对错，通常报告 pass@k：采样 \(k\) 次至少一次通过的概率。Codex 论文给出了它的无偏估计：

\[ \text{pass@}k = \mathbb E_{\text{题目}}\left[\,1 - \frac{\binom{\htmlClass{sym-n}{n} - \htmlClass{sym-c}{c}}{k}}{\binom{n}{k}}\,\right] \]
每题采样 \(n\ge k\) 次，数出其中 \(c\) 次通过。从这 \(n\) 次里随机挑 \(k\) 次，全都不通过的概率是“从 \(n - c\) 个失败里挑 \(k\) 个”的组合数除以总组合数；用 1 减去它，就是至少一次通过的概率。
\(n\)
每道题实际采样的次数（如 200）
\(c\)
其中通过测试的次数
\(n = 10\)，\(c = 3\)。pass@1 \(= 1 - \binom{7}{1}/\binom{10}{1} = 0.3\)，就是通过率。pass@5 \(= 1 - \binom{7}{5}/\binom{10}{5} = 1 - 21/252 = 0.917\)。如果直接用 \(1 - (1 - 0.3)^5 = 0.832\) 估计，会因为 \(n\) 有限而产生偏差（偏差的方向和大小见第 章的推导）。

pass@k 假设能从 \(k\) 个样本里挑出对的那个：有一个对的就算解出。这个假设很乐观：Codex-S（再在正确解答上微调的 Codex）每题采样 100 次，77.5% 的题至少有一个对；不拿隐藏测试、按模型自己的平均对数概率挑一个，只有 44.5%。“写得出”和“挑得出”差了 33 个百分点，这是多采样加筛选一节的主题。

HumanEval 很快饱和（2024 年头部模型超过 90%），题目也早已散布在网上，难以排除污染。评测于是往“更真实、更长、更难污染”的方向走：

SWE-bench 的分数能说明多少

主张
真实仓库、真实 issue、真实测试；分数从 2023 年的不到 2%（原版全集）涨到 2026 年的 80%–90%（Verified），说明工程能力有了质的飞跃。
质疑
一是污染。“SWE-bench 幻觉”研究（2025）发现，模型只看 issue、不看代码，就能高准确率地说出该改哪个文件；换到 Pro，分数常大幅下降：据报道 Claude Opus 4.5 在 Verified 上 80.9%，在 Pro 上 45.9%（前者是厂商自报，后者是 Scale 的统一脚手架，差距里也有 harness 的成分）。二是误放。SWE-bench+（2024-10）检查了 SWE-agent 加 GPT-4 判为解决的 251 个补丁：32.67% 的答案就写在 issue 或评论里，31.08% 靠测试太弱才通过，去掉后解决率从 12.47% 降到 3.97%。PatchDiff（ICSE 2026）在 Verified 上发现，29.6% 的“通过”补丁行为和参考补丁不同，人工确认其中近三成确实是错的；再加上 7.8% 过不了开发者的完整测试集，解决率虚高约 6 个百分点。
现在怎么看
Verified 的高分主要说明模型在熟悉的公开仓库上很强；Pro、Terminal-Bench 和私有代码库更能反映真实水平。看分数要同时看评测版本、harness 和推理预算（第 章），并记住它出自一个误放率不为零的验证器。

多采样加测试筛选：验证器的天花板

最直接的办法是多采几个，挑一个能通过测试的。这种采样加筛选（generate-and-filter）在编程里格外好用，因为测试是现成的验证器（对比第 章没有验证器时的多数投票）。AlphaCode（2022）每道竞赛题采样上百万个程序，用题面样例过滤掉约 99%，再按在新输入上的输出聚类、从大类里各挑一个凑满 10 次提交，在 Codeforces 比赛里平均排前 54.3%。

采样越多越好吗？测试完美时是：成功率就是 pass@k，一直涨向 100%。测试不完美时，答案藏在精确率里：

\[ P(k) = \htmlClass{c-adv}{\underbrace{\frac{\htmlClass{sym-p}{p}}{p + \htmlClass{sym-w}{w}}}_{\eta}}\,\Big(1 - (1 - p - \htmlClass{sym-w}{w})^{\htmlClass{sym-k}{k}}\Big),\qquad \htmlClass{sym-w}{w} = (1-p)\,\htmlClass{sym-phi}{\varphi} \] 采 k 个，在通过测试的补丁里随机提交一个；一个都没通过就放弃
括号里是“至少有一个补丁通过测试”的概率，随 \(k\) 涨向 1；前面的系数是“通过测试的补丁里真正对的比例”，它和 \(k\) 无关。所以采样再多，成功率也只能涨到 \(\eta\) 为止。
\(p\)
单次采样写出正确补丁的概率
\(w\)
单次采样写出“错误但通过测试”的补丁的概率
\(\varphi\)
误放率
\(k\)
采样的补丁数
\(p = 0.3\)、\(\varphi = 0.1\)：\(w = 0.07\)，\(\eta = 0.3/0.37 = 81.1\%\)。\(k = 1\)：30%；\(k = 10\)：\(0.811\times(1 - 0.63^{10}) = 80.3\%\)；再多也只到 81.1%。完美验证器下 pass@10 是 97.2%。一道难题 \(p = 0.05\)：\(\eta = 0.05/0.145 = 34.5\%\)，通过测试的补丁里将近三分之二是错的。

难题的 \(\eta\) 低，采样多了反而会“找到”更多骗过测试的错误补丁。若合并一个错误补丁的代价是 \(c\)（修好一题为 1），净收益 = 修好的比例 − \(c\) × 错误提交的比例：前者早早饱和，后者一直涨，所以有一个最佳采样数。下面的演示把一批难度参差不齐的题放在一起：

采样加筛选的成功率，以及为什么会有最佳采样数

第 1 步，一个样本的三种结局。正确（概率 \(p\)，假设正确的补丁总能通过测试）；错误但通过测试（\(w = (1-p)\varphi\)）；不通过（\(1 - p - w\)）。各样本独立。

第 2 步，至少一个通过。\(k\) 个样本全不通过的概率是 \((1-p-w)^k\)，所以至少一个通过的概率是 \(1 - (1-p-w)^k\)。

第 3 步，挑出来的那个对不对。在“这个样本通过了”的条件下，它正确的概率是 \(p/(p+w) = \eta\)，而且每个通过的样本各自独立地满足这一点。从通过的样本里随机挑一个，它正确的概率就是 \(\eta\)，与通过了几个无关。两步相乘就是 \(P(k) = \eta\big(1 - (1-p-w)^k\big)\)，\(k\to\infty\) 时趋于 \(\eta\)。

第 4 步，一批难度不同的题。第 \(i\) 题的单次正确率为 \(p_i\)。整体成功率是各题的平均，天花板是 \(\mathbb E_i[\eta_i]\)；提交了错误补丁的比例是 \(\mathbb E_i\big[(1-\eta_i)\big(1 - (1-p_i-w_i)^k\big)\big]\)。难题的 \(p_i\) 小，\(\eta_i\) 也小：\(k\) 小时它们没有补丁通过（放弃），\(k\) 大时就冒出一个骗过测试的错误补丁。所以成功率早早饱和，错误提交却一直增加。

第 5 步，错误提交有代价时。修好一题得 1、提交错误补丁得 \(-c\)、放弃得 0，净收益 \(U(k) = \text{成功率}(k) - c\cdot\text{错误提交率}(k)\)。前者饱和得快，后者涨得久，\(U\) 在有限的 \(k\) 处最大：演示的默认设定（平均单次正确率 30%、误放率 5%、\(c = 1\)）下约为 8。Stroebl 等（2024）用真实数据测过：拿 HumanEval、MBPP 原版的测试当验证器、扩充后的测试当标准答案，较弱的模型误放率更高，再怎么多采样也追不上 GPT-4o 的单次正确率；考虑错误提交的代价，最佳采样数往往不到 10。AlphaCode 的聚类则相当于在测试之外再加一个验证器：正确的程序在新输入上行为一致、聚成大类，错误的各错各的。

这个推导告诉我们：有了测试，多采样的收益由验证器的精确率封顶，而不是由模型能不能“偶尔写对一次”决定。想让多采样继续有效，就要同时提高验证器的质量：更多、更有针对性的测试，或者再加一层独立的验证。

2025 年的实践印证了这一点。DeepSWE 对每个 Verified 任务跑 16 条轨迹：单条平均 42.2%，pass@16 是 71.0%，用两个验证器（一个生成更多测试来跑，一个直接读补丁打分）挑一条交上去是 59.0%。差出的 12 个百分点，就是验证器的不完美。

每一代在修什么：从补全到后台智能体

AI 编程的形态换了五代。下表按“人卡在哪”排：每一代把人从循环里往外挪一步，修掉一个瓶颈，又留下新的；剩下的人工环节决定整体能快多少（下一节）。几代在时间上有重叠，每一次放手都要等模型先变得足够可靠，模型这一侧见演进史。

2025 年 2 月，Karpathy 提出 vibe coding：用自然语言描述需求，接受 AI 的所有修改，不读代码，出错就贴回报错。它等于删掉审查这一环，风险全交给测试和运气，适合一次性的原型；需要长期维护的软件，大多仍是“规格先行、AI 实现、人审查”。

第五代是在云端沙盒里、不需要人盯着、连续工作几小时到几周的后台编程智能体。OpenAI 称 GPT-5-Codex（2025-09）曾连续独立工作 7 小时以上；Cursor 在 2026-01 称数百个智能体并行近一周写出一个超过 100 万行的浏览器。Anthropic 研究员的实验（2026-02）里，16 个并行的 Claude Opus 4.6 在两周内写出约 10 万行、能编译 Linux 6.9 的 C 编译器，花费不到 2 万美元。作者的头号经验是：智能体会去解决你给它的任何问题，所以验证器必须近乎完美；16 个智能体总撞上同一个 bug 时，解法是拿 GCC 当参考答案对拍。

智能体运行得越久，“改了再跑”转得越多，最终质量越接近验证器的精确率，而不是单次正确率。

实际效果：快了还是慢了

早期研究几乎都报告大幅提速：GitHub 2023 年的试验里用 Copilot 写一个 HTTP 服务器快了 56%，Google 2024 年的内部实验约快 21%，但多是从零写的小任务。测因果的标准做法是随机对照试验（randomized controlled trial, RCT）：随机决定谁（或哪个任务）用 AI，让两组在看不见的因素上平均相同。2025 年 7 月，METR 的一项随机对照试验得出了相反的结论。

AI 编程工具让资深开发者更快了吗

METR 2025
16 位资深开源开发者在自己熟悉的大型仓库（平均 2.2 万星、超过百万行）中完成 246 个真实任务，每个任务随机决定能否用 AI（主要是 Cursor 加 Claude 3.5/3.7 Sonnet）。允许用 AI 时耗时多了 19%（95% 置信区间 +2% 到 +39%）；开发者事前预计会快 24%，事后仍认为快了 20%。
为什么
时间花在写提示、等待、审查和修正 AI 的输出上；资深开发者在熟悉的代码库里本来就快，AI 的建议又常不符合项目的隐含约定。
2026 年的更新
METR 在 2026-02 称原结论已经过时，提速如今很可能存在，但新数据不可靠。新一轮试验（2025-08 起，57 位开发者）的点估计转向提速（回访的 10 人 −18%，新招的 47 人 −4%），置信区间都包含 0，而且很可能低估了提速：不愿“一半任务禁用 AI”的开发者拒绝参加，30%–50% 的受试者承认不想禁用 AI 的任务干脆不报。所以这不是“结论反转”，只是提速很可能存在、大小未知。
现在怎么看
从零写小程序、陌生代码库、样板代码，提速明显；熟悉的大型代码库里的复杂修改，收益不确定。“感觉快了”不是可靠的测量；人人离不开 AI 时，“随机禁用 AI”的测量方法本身也开始失效。

一个简单的模型说明“写代码变快”与“整件事变慢”可以同时成立。它是阿姆达尔定律（Amdahl's law，第 章多智能体一节已用过）的变体：只加速一部分工作时，整体加速的上限由没被加速的部分决定；再加上一条，审查 AI 写的代码，时间大致和它写了多少成正比。

\[ T_{\text{用 AI}} = (1 - \htmlClass{sym-f}{f}) + \htmlClass{sym-f}{f}\Big(\frac{1}{\htmlClass{sym-s}{s}} + \htmlClass{c-adv}{\htmlClass{sym-rho}{\rho}}\Big) \quad\Longrightarrow\quad \text{写代码这部分的加速} = \frac{1}{1/s + \rho} \;<\; \frac{1}{\rho} \]
以不用 AI 时的总时间为 1：写代码占 \(f\)，AI 把这部分加速 \(s\) 倍，其余工作不变；但审查并修正 AI 的代码，又花掉自己写这些代码的 \(\rho\) 倍时间。于是 AI 再快（\(s\to\infty\)），写代码这部分也最多快 \(1/\rho\) 倍；只要 \(\rho > 1 - 1/s\)，总时间就超过 1。
\(f\)
写代码占总时间的比例；其余是理解需求、读代码、调试、沟通
\(s\)
AI 对写代码这部分的加速倍数
\(\rho\)
审查比：审查并修正 AI 写的代码所需时间，除以自己写同样代码所需时间
\(f = 0.3\)，\(s = 5\)。不用审查（\(\rho = 0\)）：总时间 \(0.7 + 0.06 = 0.76\)，快了 24%；即使 \(s\) 无穷大，也不超过 \(1/(1 - f) = 1.43\) 倍（阿姆达尔定律）。\(\rho = 0.5\)：\(0.7 + 0.3\times 0.7 = 0.91\)，只快 9%。\(\rho = 1\)（审查和自己写一样慢）：\(0.7 + 0.3\times 1.2 = 1.06\)，反而慢了 6%。

演示默认 AI 把写代码快了 4 倍、审查比 0.9：这部分实际只有 0.87 倍速，总时间 1.06。参数是示意值，不能拿来算 METR 的结果：

派出多个后台智能体也绕不过它：写代码可以并行，审查仍由一个人串行完成。测试越可靠（误放率越低），人越可以只看测试结果和关键改动，所以真正的杠杆是自动化的验证，它同时降低 \(\rho\) 和 \(\varphi\)。

并行智能体为什么也绕不过审查

一个人同时派出 \(N_{\text{a}}\) 个后台智能体，写代码的墙钟时间从 \(f/s\) 变成 \(f/(sN_{\text{a}})\)，但审查仍由这一个人串行完成：\(T = (1-f) + f\big(1/(sN_{\text{a}}) + \rho\big) \to (1-f) + \rho f\)（\(N_{\text{a}}\to\infty\)）。\(f = 0.5\)、\(\rho = 0.3\) 时，派出再多智能体也最多快 \(1/0.65\approx 1.54\) 倍。这个推导告诉我们：审查成了阿姆达尔定律里“不能并行的部分”；vibe coding 等于直接令 \(\rho = 0\)，把全部风险交给误放率。

代码质量与安全

换成本章的语言：功能测试对安全漏洞的误放率接近 100%，有漏洞的代码照样能通过功能测试，安全需要另一类验证器（静态分析、模糊测试、安全审查）。Pearce 等（2021）在 89 个容易出漏洞的场景里测 Copilot，约 40% 的程序含漏洞。Veracode 2025-07 用 80 个已知有安全风险的补全任务测一百多个模型，约 45% 的生成代码含安全缺陷（Java 72%），且不随模型变大而改善；2025-10 的更新里，GPT-5 等推理模型的通过率升到约 70%（非推理的 GPT-5-chat 仍是 52%），其余厂商的新模型变化不大。

新的风险是模型会“幻觉”出不存在的软件包名：Spracklen 等（USENIX Security 2025）发现，商业模型推荐的包里平均至少 5.2% 不存在，开源模型 21.7%。攻击者抢先注册这些名字、放入恶意代码，等别人照着 AI 的建议安装，这叫 slopsquatting。据 GitClear 2025 年的仓库统计，AI 普及后重复代码和短期内被改回的代码比例上升。

常见误解

  • SWE-bench Verified 九成意味着 AI 能完成九成的工程工作。它测的是公开仓库里描述清楚、有测试覆盖的修复任务；需求、设计、沟通、维护都不在其中，更难污染的 Pro 上分数低得多。
  • 能通过测试的代码就是正确的。“通过”的补丁里有相当一部分是错的（评测一节的争议框）；在容易出漏洞的场景里，四成左右的生成代码含安全缺陷，照样能通过功能测试。
  • 感觉快了就是真的快了。METR 2025 年的试验中，开发者实际慢了 19% 却以为快了 20%。

自测

1. 模型单次写出正确补丁的概率是 40%，测试的误放率是 20%。采样 16 个补丁、在通过测试的里随机交一个，成功率约多少？和 pass@16 相比如何？误放率要降到多少，成功率才能到 90%？
\(w = 0.6\times 0.2 = 0.12\)，\(\eta = 0.4/0.52\approx 76.9\%\)。\(P(16) = 0.769\times(1 - 0.48^{16})\approx 76.9\%\)（\(0.48^{16}\approx 8\times 10^{-6}\)，几乎肯定有补丁通过）。pass@16 \(= 1 - 0.6^{16}\approx 99.97\%\)，差了 23 个百分点，全部来自误放。要 \(\eta\ge 0.9\)：\(0.4\ge 0.9\times(0.4 + 0.6\varphi)\)，即 \(\varphi\le 0.04/0.54\approx 7.4\%\)。
2. 一个编程 RL 环境里，认真修一次修好的概率是 30%，没修好的“近似”补丁有 20% 能混过测试；测试文件对智能体可写，判分前也不恢复。训练下去会发生什么？给出两种修法，并说明为什么“多加隐藏测试”不在其中。
认真修的通过率 \(0.3 + 0.7\times 0.2 = 0.44\)，改测试的通过率是 1。策略梯度的终点是通过率最高的做法，模型迟早会学会改测试；它起初越罕见，前期越看不出来，但不会因此不发生。修法：判分前恢复测试文件或设为只读；检查补丁是否改了测试文件，改了即判 0 分；用模型或规则审查轨迹。隐藏测试只压低糊弄测试的补丁的误放率，改测试的做法连判分者一起改掉了，通过率与测试数无关。
3. 训练曲线上，测试通过率一路升到 95%；人工抽查 50 条轨迹，只有 20 条真修好了。按本章的分类，可能是哪几类问题？各先查什么？
三类都可能。糊弄测试（写特例、只修常见情况）：拿抽查出的错误补丁去跑更多、更有针对性的测试，看它们是否在别的输入上失败，失败说明误放率太高，要加强测试。改掉判分者：看补丁有没有动测试文件、测试配置或计时函数，判分前是否恢复了测试文件。偷答案：看轨迹里有没有翻 git 历史、联网拉取原仓库。三者的防线不同（测试、权限、隔离），所以要先分清是哪一类；只看奖励曲线分不出来，这也是要抽查轨迹的原因。
4. 每题采样 \(n = 20\) 次，某题通过了 \(c = 4\) 次。它的 pass@1 和 pass@5 估计值是多少？
pass@1 \(= 4/20 = 0.2\)。pass@5 \(= 1 - \binom{16}{5}/\binom{20}{5} = 1 - 4368/15504\approx 0.718\)。
5. 一个开发者写代码占 30% 的时间，AI 把这部分加速 5 倍，但审查和修正 AI 输出新增了相当于原总时间 30% 的工作。整体是快了还是慢了？开销降到多少以下才不吃亏？
\(0.7 + 0.3/5 + 0.3 = 1.06\)，慢了 6%。不吃亏要求 \(o < f(1 - 1/s) = 0.3\times 0.8 = 0.24\)。如果把开销看成与代码量成正比（审查比 \(\rho = 1\)），AI 再快也没用：写代码这部分的加速 \(1/(1/s + \rho)\) 永远小于 1。
