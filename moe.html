混合专家（MoE）：参数很多，但每次只用一小部分

2026 年的前沿开源模型几乎都是 MoE：Kimi K3 总参数 2.8T，每个 token 只激活 104B；DeepSeek V4-Pro 是 1.6T 总参数、49B 激活。MoE 让 模型容量（知识） 和 每个 token 的计算量 不再绑在一起。

思路：把 MLP 拆成很多个专家

第 3 章讲过，MLP 占了 Transformer 约 2/3 的参数，而且每个 token 独立计算。MoE 把一个大 MLP 换成 E 个小 MLP（专家），再加一个很小的 路由器（一个 d×E 的线性层）。每个 token 进来时，路由器给每个专家打分，只把它送给得分最高的 k 个专家，输出按门控权重加权求和：

y = Σi ∈ TopK(g(x)) gi(x) · Experti(x)    g(x) = softmax(x · Wrouter)E 个专家、每次选 k 个：参数量 ≈ E 份，计算量 ≈ k 份

专家会自发出现一定程度的分工，比如某些专家更常处理代码、某些更常处理中文标点。但这种分工不像“数学专家”“历史专家”那样清晰，更多是 token 层面、句法层面的分工。

MoE 的几个难点

  • 负载均衡：路由器容易“偏心”，少数专家被挤爆，其余专家闲置甚至从来没被训练（路由坍缩）。传统做法是加一个 辅助损失，惩罚负载不均；但辅助损失会干扰主任务。DeepSeek-V3 提出 无辅助损失的均衡：给每个专家一个只用于选择、不参与加权的偏置 b，负载过高就调低，过低就调高。上面的演示就是这个方法。Kimi K3 的 Stable LatentMoE 在潜空间里做路由，用 “Quantile Balancing” 做均衡，超出容量的 token 软丢弃而不是硬丢弃。
  • 容量与丢 token：分布式训练时每个专家在每个设备上有固定容量（capacity factor × 平均负载）。超出容量的 token 会被丢弃，直接走残差。
  • 通信：专家分布在不同 GPU 上（专家并行 EP），每层都要做两次 all-to-all，把 token 发给专家所在的卡，再收回来。这往往是 MoE 训练和推理的主要瓶颈（第 10 章）。
  • 细粒度专家 + 共享专家（DeepSeekMoE, 2024）：把专家切得更小更多，例如 256 个里选 8 个，组合方式更多，专业化更细；再加 1–2 个所有 token 都走的 共享专家，负责通用知识，避免每个路由专家都重复学一遍。

总参数 vs 激活参数

MoE 带来一个关键的不对称：显存要装下全部参数，但每个 token 的计算只和激活参数有关。所以 MoE 推理通常受显存和带宽限制，这也是第 9 章量化的一个重要用武之地：Kimi K3 的专家权重用 MXFP4，就是因为专家占了绝大部分参数。

本地部署的小技巧。MoE 每个 token 只访问一小部分专家，所以可以把大部分专家权重放在 CPU 内存里，只把注意力和共享部分放进显存（llama.cpp 的 --n-cpu-moe 等参数）。Apple Silicon 的统一内存也适合 MoE：容量大，带宽够用。这也是 Meta 说 Muse Spark Open（816B）可以在两台 Mac Studio 上运行的原因。
